# ブラウザ自動化をやめ、全サイトHTTP取得にする

**状態: 採用（2026-09-02・Phase 3 で実施）**
**関連: [ADR 0003](./0003-local-filtering.md)（ローカル判定への転換）が前提**

v1 でブラウザ自動化（go-rod）を使い、v2 の計画でも Playwright を前提にしていた
5サイト（ATHOME / EHEYA / NIFTY / APAMAN / SMOCCA）を、**すべて httpx + lxml の
HTTP取得で実装する**。`playwright` は依存から外す。

## 背景

再設計計画は Phase 3 を「Playwright展開」とし、この5サイトはブラウザが要ると
していた。根拠は v1 の実装（`cmd/main.go:82` で go-rod を使っていた）である。

Phase 3 の着手時に**実測で確かめたところ、5サイトすべてが素のHTTPで
サーバレンダリング済みのHTMLを返した**（2026-09-01 実測）。

| サイト | HTTP取得 | 掲載データの在処 |
|---|---|---|
| ATHOME | 200 / 920KB | DOM（`div.p-property--building`） |
| EHEYA | 200 / 447KB | `<script id="__NEXT_DATA__">` のJSON |
| NIFTY | 200 / 988KB | DOM（`table.result-bukken-table`） |
| SMOCCA | 200 / 1.08MB | DOM（`div.item_list01`） |
| APAMAN | 200 / 203KB | DOM（`article.mod_box_section_bdt`） |

## なぜ v1 はブラウザが必要だったのか

**v1 は検索フォームを操作していたから**である。v1 は設備条件を含む多数の条件を
サイトの検索フォームへ入れて絞り込んでいた（→ ADR 0003 で全廃した方針）。
チェックボックスやセレクトを操作するにはブラウザが要る。

v2 がサイトへ渡すのはエリア・種別・価格上限の3つだけで、**URLを直接組み立てる**。
フォーム操作が要らなくなった時点で、ブラウザを使う理由も消えていた。
「v1 がブラウザを使っていた」は「v2 でもブラウザが要る」を意味しない。

## 決定

1. 5サイトとも `httpx` + `lxml` で実装する
2. `m_sites.fetch_method` は全12行が `HTTP` になる
   （`tests/test_schema_conventions.py::test_全サイトがHTTP取得` が回帰テスト）
3. `pyproject.toml` から `playwright` を外す

## 帰結

**良くなること**

- ブラウザバイナリ（約115MB）のインストールが不要になり、
  タスクスケジューラからの実行が軽くなる（Phase 5 の運用設計が単純になる）
- 1ページの取得が数百ミリ秒で済む。ブラウザ起動・描画待ちが無い
- 取得と解析がフィクスチャで完全に再現でき、テストがネットワーク無しで回る

**悪くなること・残るリスク**

- **サイトがクライアントレンダリングへ移行すると壊れる。** 特に EHEYA は
  Next.js の Pages Router に依存しており、App Router へ移ると
  `__NEXT_DATA__` が消える。壊れたときに黙って0件にならないよう、
  `__NEXT_DATA__` が無ければ例外にしてある
- **ブラウザなら通るボット検知は通せない。** ただし Phase 3 の実測では、
  MINIMINI の reCAPTCHA は素の Chromium でも通らず（→ 課題#18）、
  ATHOME のパズル認証も同様にクリック操作を要求する（→ 課題#20）。
  **どちらもブラウザに替えても解決しない**ため、この決定で失うものは無い

## 却下した案

**Playwright を残して将来に備える**: 依存の重さ（ブラウザ115MB）を
「いつか要るかもしれない」で抱え続けることになる。実際に要るようになった時点で
戻せばよく、そのときは戻す先（アダプタ1本）が明確になっている。
