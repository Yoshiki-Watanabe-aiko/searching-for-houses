## #1 ABLE・SMOCCA が市区町村未指定だと0件になる

- 状態: **解決済み**（2026-09-01。SMOCCA のアダプタ自体は Phase 3）
- 内容: ABLE・SMOCCAは市区町村の指定が必須で、都道府県のみの指定では検索結果が0件になる。
- 対応履歴:
  - 2026-07-10: `docs/詳細設計書/01_検索条件マッピング設計.md`の調査で判明。
  - 2026-09-01: v2 の方針を確定。YAML の `search.cities` が空のとき、この2サイトについては
    `m_cities` から都道府県内の全市区へ自動展開する（`m_city_site_values` に行があるものが対象）。
    Phase 2（HTTP展開）で実装する。
  - 2026-09-01: Phase 2 で `src/house_search/scrape/area.py` として実装。
    アダプタが `requires_city` を宣言し、`search.cities` が空でも都道府県内の全市区へ展開する。
    対象は ABLE・SMOCCA に加え、同じく市区必須と判明した GOO・賃貸EX も含む。
    ⚠ **当初方針の「`m_city_site_values` に行があるものが対象」は撤回した。**
    この4サイトの市区の検索値は **JIS5桁コードそのもの**で `m_cities.jis_code` から導出でき、
    マッピング表に縛ると対象4都県で 67/253市区しか指定できなかった
    （東京都は23区のみで多摩地域が丸ごと漏れる）。JIS導出に切り替え、
    さらに `jis_code` 自体を実測で補完して **216/253市区**が指定できるようになった。
    残りの未登録分は課題#16。
  - 2026-09-02: Phase 3 で市区必須のサイトが増えた。実測の結果、
    **NIFTY・APAMAN・SMOCCA も都道府県ページには掲載が載らない**（エリア索引になる）。
    NIFTY はサイト固有スラグ（`adachiku`）なので `m_city_site_values` を引き、
    APAMAN は **JIS5桁の下3桁**（13121 → `121`）、SMOCCA は JIS5桁をそのまま使う。
    ATHOME・EHEYA は都道府県ページでも掲載が返るため `requires_city=False`。

## #5 「賃貸EX」サイトの追加対応要否が未決定

- 状態: **解決済み**（2026-09-02・Phase 5 で本採用）
- 対応履歴:
  - 2026-07-10: 発見・記録。ユーザー判断待ち。
  - 2026-09-01: **対応する**方針で確定。`CHINTAI_EX` として `m_sites` に登録済み
    （`is_active=false`）。Phase 2 で base_url・エリア指定方式を確定し、
    観測モードでユニーク物件率を実測してから通知を有効化する。
  - 2026-09-01: Phase 2 で調査・実装完了。`base_url=https://chintai-ex.jp`、
    市区一覧は `/search/city/{JIS5}`、ページ送りは `/page/{N}` の**パス形式**。
    ⚠ **robots.txt が `Disallow: *?*` でクエリ付きURLを全面的に禁じている**ため
    価格上限をサイト側へ渡せず、市区の全掲載を取ってローカル判定する。
    ⚠ **同じURLでも一覧レイアウトが3通り返る**（実測）ので、
    `parse_list` はタグではなくクラス（`js-bukken`）で拾って中身で分岐する。
    `is_active=false` のまま観測モードで運用し、
    `scan --site CHINTAI_EX --seed` と名指ししたときだけ動く。
    実測（足立区・葛飾区・八王子市の各1ページ）: 一覧175件・詳細11件・設備平均12.9件。
    ユニーク物件率は Phase 4 の名寄せで測る。説明文の扱いは課題#19。
  - 2026-09-02: Phase 4 で**ユニーク率91%**を実測（11掲載中10件がユニーク。
    他サイトと一致したのは `モント竹ノ塚`＝スモッカとの1件のみ）。
    ⚠ **サンプル11掲載は少なすぎる**ので本採用の判断はまだできない。
    Phase 5 の初回全件スキャン後に `dedup-stats` で測り直して決める。
    説明文の扱い（課題#19）は先に解決した。
  - 2026-09-02: **Phase 5 で本採用した**（`is_active=true`）。初回全件スキャン
    8,429掲載で測り直した結果、**全体のユニーク率は26%**（850掲載中627件が
    他サイトと重複）まで落ちた。ここだけ見ると不採用に見えるが、
    **エリア帯を都心45分圏に絞ると63%・69代表**と GOO（127代表）に迫る寄与になる。
    全体の26%は216市区を舐めて市区必須サイト（ABLE・APAMAN・GOO・SMOCCA）と
    重なった結果であり、通勤圏では独自性がある（→ ADR 0013）。
    ⚠ あわせて `max_pages_per_run` を 50 → 5 に下げた。観測モードでは
    「市区の全掲載を取る」前提だったが、エリア帯で86市区へ絞ったので
    5ページ（1市区100件）で足りる。50のままだと `--full` で 86×50=4,300ページになり
    **賃貸EXだけで3.6時間**かかる。

- 内容: Phase 2 のアダプタ実装中、HOME'S の挙動が段階的に変わった。

  WAF のチャレンジはレート起因で緩む場合があるため、しばらく観測する。

  - 2026-09-01: Phase 2 で起票。実測の充足率は「物件6件 / 詳細4件 / 設備平均14.8件」。

    （AWS WAF のチャレンジ本文は出ない）。`m_sites.min_interval_sec` は **2.5秒**で、
    実測より速く叩いている。
    対応: `HomesScraper.parse_list` / `parse_detail` が空ボディと WAF チャレンジを
    **明示的な例外にする**ようにした（従来は `lxml` の `Document is empty` という
    原因の分からないメッセージだった）。

## #25 リトライ対象外の4xxで「連続失敗による打ち切り」が発火しない

- 状態: **解決済み**（2026-09-02・Phase 5）
- 内容: `SiteFetcher.get` は 405・403 のような非リトライ4xxで
  `raise_for_status()` がそのまま例外を投げ、**その下の `failures` /
  `consecutive_failures` の加算に到達していなかった**。
  このため要件定義書 §13 が謳う「連続失敗でサイト打ち切り」が永久に発火せず、
  初回全件スキャンで **NIFTY の 405 を271回叩き続けた**
  （5時間43分のエラー555行のうち542行が NIFTY）。
- ⚠ **連鎖したデッドコード**: 404 も同じ経路で例外になるため、
  `suumo.py` の `response.status_code == 404` による成約判定に**到達できなかった**。
  直前の `except Exception: return False`（判定保留）に吸われるため、
  **404 を返す掲載は永久に `active` のまま残る**。
- 対応: 404 は例外にせず `response` を返し（呼び出し側が判定する）、
  403・405 などの拒否系は `failures` に数えて5回連続で `SiteAborted` にする。
  `tests/test_fetch.py` に4件の回帰テストを追加した。
- ⚠ **NIFTY の405は恒久的な仕様ではなかった。** 1リクエストだけ実測したところ
  既定UA・Referer無しでも 200 で取得できた（2026-09-02）。
  短時間の連続アクセスに対する一時的な制限とみられる。
  相手が拒否しているのに手を引けないことが問題であって、405 自体ではない。
- ⚠ **405 の正体は 2026-09-03 に判明した。** 本文が
  `<title>Human Verification</title>` の検知ページで、**メソッド不許可ではない**
  （→ 課題#38）。「一時的な制限」という現象の見立ては正しかったが、
  原因はボット検知の出入りだった。
- 対応履歴:
  - 2026-09-02: 初回スキャンのエラー集計から発覚・起票・同日対応。

## #29 サイト側の絞り込みに無効値を渡すと HTTP 200 のまま0件になる

- 状態: **解決済み**（2026-09-03。4サイトの配線と検出2層が入った → ADR 0015）
- 内容: SUUMO の賃料上限 `ct` は**選択肢が決まっており、端数を渡すと
  掲載0件になる**。実測（2026-09-02・千代田区）:

  | ct | 掲載 |
  |---|---:|
  | 15.6（`price_max_hint=156000` から生成） | **0件** |
  | 16.0 | 100件 |
  | 指定なし | 160件 |

- ⚠ **この事象の質の悪さ**: HTTP 200 で返り、HTMLも正常で、例外にもならない。
  **掲載が0件になるだけ**なので `scan` は「取得 0」と報告して正常終了する。
  ATHOME のボット検知（課題#20）と同じ形で「取れているつもり」になる。
- 表面化しなかった理由: 運用中の `price_max_hint=90000` が
  **偶然 `ct=9.0` という有効な値**になっていた。エリア帯の分割で
  23区帯を 156,000 にした瞬間に SUUMO が0件になった。
- 影響していたサイト:
  - **SUUMO** `ct`: `:.1f` で端数をそのまま渡していた → 整数の万円へ切り上げ
  - **HOMES** `cond[monthmoneyroomh]`: コメントは「0.5刻みのため丸める」と
    書いてあったが**実際は丸めていなかった** → 0.5刻みへ切り上げ
  - **GOO** `ru`: `-(-x // 10_000)` で既に整数へ切り上げており無事だった
  - ABLE・賃貸EX・APAMAN・EHEYA・NIFTY・SMOCCA: そもそも上限を渡さない
- ⚠ **残っている問題は「検出できないこと」**。今回は帯を分けた直後に
  実測したから気づけたが、仕組みとしては何も検出しない。
  対応方針の候補: (a) `scan` が「詳細取得済みの掲載があるのに一覧0件」の
  サイトを警告する / (b) 一覧0件が2回続いたらエラーチャンネルへ通知する
  / (c) `coverage` に一覧の取得件数を出す。
- 対応履歴:
  - 2026-09-02: エリア帯の初回スキャン中に SUUMO が items_seen=0 で
    完了しているのを見つけて起票。同日中に SUUMO・HOMES を修正し、
    `tests/test_scrape_{suumo,homes}.py` に切り上げの回帰テストを追加した。
    ⚠ **検出の仕組みは未着手。**
  - 2026-09-03: **Phase 5B で SUUMO について検出手段を整備した**（→ ADR 0015）。
    サイト側フィルタを MUST に限って拡張するにあたり、この事故が増える面を
    先に塞ぐ必要があった。実測で**誤りには3つの現れ方**があると分かった。

    | 送った値 | 結果 |
    |---|---|
    | `et=10`（選択肢内） | 41,405件 |
    | **`et=12`（選択肢に無い）** | **`title` が「エラー｜SUUMO(スーモ)」の11KBのページを HTTP 200 で返す**（掲載0件） |
    | `zzz=1`（存在しないキー） | 62,030件のまま。**黙って無視される** |

    ① 丸めを型で強制し、選択肢を外す値をそもそも作れないようにした

## #35 乗車区間の駅名索引が「掲載のある都道府県」に固定され、地方外で区間が貯まらない

- 状態: **解決済み**（2026-09-03）
- 内容: `fetch-commutes` が乗車区間（`t_rail_segments`）の駅名を引く索引を
  **`listing_prefecture_codes`（掲載のある都道府県）で固定**していた。
  実運用の掲載は1都3県しかないため、`--region` で他の地方を取ると
  経路に出てくる駅が索引に無く、区間が1本も貯まらない。
  沖縄18駅の取得で「**乗車区間 72本を駅名と結び付けられず捨てた**」（＝全件）。
- 影響: **O-D の所要時間（`t_station_commutes`）には実害が無い**（正しく保存される）。
  貯まらないのは `t_rail_segments` で、**目的地を変えたときの再計算**に使う資産。
  ADR 0017 が「目的地が変わっても取得をやり直さずに済む」根拠にしていたもの。
- ⚠ **原因は2つあり、主因は索引の範囲ではなかった。** 貯まった経路の原文4,885件を
  再解析して範囲別に測ったところ、次のことが分かった。

  | 条件 | 芝公園ゆき | 沖縄 | 東京ゆき |
  |---|---:|---:|---:|
  | 修正前 | 90.1% | **0%** | 7.7% |
  | 注記除去のみ | **94.8%** | 0% | 7.7% |
  | 注記除去＋地方の索引 | 94.8% | **100%** | **100%** |

  1. **駅名の注記を落としていなかった**（主因）。NAVITIME は乗換駅に路線注記を付け
     （`本八幡〔新宿線〕` / `溝の口〔東急線〕` / `町屋〔千代田線〕`）、副名称を
     **角括弧**で返す（`押上[スカイツリー前]`）。`strip_station_note` は既にあったが
     **応答の駅名照合にしか使っておらず**、区間の駅名解決には通していなかった。
     これだけで芝公園ゆき20,189本中**942本**が救えた
  2. **索引の範囲が用途と合っていなかった**。沖縄が全滅したのは
     「県庁前」が**千葉県にもある**ため（掲載都道府県の索引では一意に決まらない）
- ⚠ **全国に広げるのは誤り。** 同名異駅（三田・大手町・日吉）が一意でなくなり、
  芝公園ゆきの解決率は **94.8% → 66.3%** へ落ちる（実測）。
  「一意に決まらない名前は捨てる」という安全側の挙動は保ったまま、
  **範囲だけを目的に合わせる**のが正解だった。
- 対応:
  1. `make_station_resolver` を切り出し、`note_variants` で**注記を落とした形も試す**
     （原文を先に試す。マスタ側に括弧付きの駅名が実在するため）
  2. `--region` 指定時は索引を `region.pref_cds` にする（`_segment_index_prefectures`）。
     ⚠ `pref_cds` は `frozenset` なので**並べてから渡す**（反復順が実行ごとに揺れる）
  3. **`re-segment` コマンドを追加**。保存済みの経路原文（`t_navitime_routes.route_text`）
     から区間を作り直す（ネットワーク不要）。設備の `re-extract` と同じ位置づけで、
     **ADR 0017 が原文を残していた本来の用途**。取り直すと芝公園ゆき1,155駅で4.8時間かかる
- 実測（2026-09-03・`re-segment` 適用後）:

  | 目的地 | 経路の原文 | 捨てた区間 | 結果 |
  |---|---:|---:|---|
  | 芝公園 | 4,801件 | 1,050本 | 累計 2,798 → **2,923本** |
  | 県庁前（沖縄） | 72件 | **0本** | ゆいレール **18区間**（修正前は0） |
  | 東京（関東） | 12件 | **0本** | 7本 |

  残る1,050本は `小川町`（東京・都営新宿線 / 埼玉・東武東上線）・`霞ヶ関`・`入谷` など
  **真の同名異駅**とバス停（`木更津駅東口`）で、捨てるのが正しい挙動。
- ⚠ **`re-segment` を流すと `t_rail_segments.samples` が加算される**（同じ観測を数え直すため）。
  `ride_minutes` は `LEAST` なので値は壊れないが、`samples` は「何回観測したか」ではなく
  「何回反映したか」になる。統計の目的にしか使っていないので許容した。
- 対応履歴:
  - 2026-09-03: 沖縄18駅の取得ログ（「乗車区間 72本を…捨てた」）から起票、同日対応。
    ⚠ **関東1,898駅の取得はまだ3駅しか進んでいなかったため、取り直しの損失はゼロだった。**
    先に直せたのは、取得を地方ごとに分けてあった（→ ADR 0018 決定3）ためでもある。

- 状態: **解決済み**（2026-09-03・Phase 5E。実地で動作を確認済み）
- 内容: HOMES と ATHOME は**1回の実行で取れるリクエスト数に上限**があり、

     goo の `「品の木・ハイランドホテル前」バス停` のようなバス停名には掛からない
  2. **UR アダプタ**: `parse_access` が `station_info` に**「駅」を残す**ようにした
     （`北習志野 / 船橋日大前 / 習志野` → `北習志野駅 / 船橋日大前駅 / 習志野駅`）。
     ⚠ UR は原文（`JR中央線｢高尾｣駅バス7分`）に「駅」があるのに、抽出で落としていた
- ⚠ **matcher の修正は再取得なしで反映できる**（`resolve-stations`）。
  UR の修正は `station_info` を作り直すので**再取得が要る**（対象1件）。
- 対応履歴:
  - 2026-09-04: 課題#37 の調査で発覚、同日対応。回帰テストに ATHOME・UR の実表記を焼き込んだ。

## #42 日をまたぐ経路で検索日の検証が偽陽性になり、遠方の駅を取りこぼす

- 状態: **対応中**（2026-09-04 に案(a) で修正・727テスト緑。⚠ **実サイトでの検証が残る**）
- 内容: `fetch-commutes` は ADR 0017 決定5 に従い、応答の前後便リンクに載る検索日が
  要求と違えば例外にする（`月指定を YYYYMM で渡すと黙って無視され現在時刻になる』事故の防止）。
  ところが**08:30発で当日中に着かない経路**では前後便リンクの日付が翌日になり、
  正常な応答でも `検索日が要求と違います: 要求 2026-09-09 / 応答 2026-09-10` で弾かれる。
- 実測（2026-09-03・北海道411駅）: **失敗41駅のうち38駅がこれ**。
  根室・厚岸・浜中・落石など**根室本線／釧網本線の末端**に集中している
  （札幌から片道7時間超の区間）。残る3駅（占冠・トマム・市役所前）は別の理由
  （`応答に出発駅・到着駅のパラメータが見つかりません`）。
- ⚠ **決定5 の検証そのものは外さない。** 深夜に実行したとき全件が始発帯の値になる
  という実害を防いでいる仕組みで、これを外すと「取れているつもり」に戻る。
- 影響: 実運用の検索パターン（1都3県・芝公園ゆき）は全駅が日帰り圏なので**影響なし**。
  効くのは全国網羅（→ ADR 0018）で、遠方の地方ほど取りこぼしが増える見込み
  （四国・九州の末端でも起きうる）。⚠ **失敗した駅は回帰式の値のまま残る**ので、
  黙って精度が落ちるのではなく `source='rail_graph'` として区別できる。
- 対応方針の候補:
  (a) **到着が翌日になる経路を許容する**（要求日 ＋1日 までを正常とみなす）。
      ⚠ 「現在時刻に落ちた」誤りとの区別が必要で、要求日より**前**の日付は引き続き弾く
  (b) 遠方の地方だけ `--depart-at` を早める。⚠ 出発日時は `t_navitime_routes` の
      一意キーの一部なので、変えるとその地方は取り直しになる（→ ADR 0017 決定7）
  (c) そのまま許容する（末端の駅に住む前提が無いなら実害は小さい）
- 対応履歴:
  - 2026-09-04: 6地方の取得（`logs/fetch_commutes_20260903_205957.out.log`）の
    進捗確認で、北海道の失敗内訳を数えて起票。
  - 2026-09-04: **ユーザー判断で案(a) を採用し実装した**（`parse_search`・727テスト緑）。
    応答の検索日が **要求日 〜 要求日＋1日** なら正常とみなす。
    ⚠ **要求日より前は引き続き弾く。** 出発日には未来日を渡すので、書式を誤って
    現在時刻へ落ちた応答は必ず要求より前になり、ADR 0017 決定5 の検出力は失われない。
    回帰テストは3本（翌日は通す／翌々日は例外／要求より前は例外）。
    フィクスチャの `beforeday` を差し替えて日をまたぐ応答を作っている。
