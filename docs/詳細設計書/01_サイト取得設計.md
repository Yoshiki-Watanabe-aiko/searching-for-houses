# サイト取得設計

**最終更新**: 2026-09-02（Phase 3）
**実装**: `src/house_search/scrape/`

v1 の `01_検索条件マッピング設計.md`（廃止済み）を置き換えるもの。
v2 ではサイトの検索フォームへ渡すのを**エリア・物件種別・価格上限の3つだけ**に限定し、
サイト別コードは「取得と解析」だけを担う（→ [ADR 0003](../adr/0003-local-filtering.md)）。

---

## 1. サイトへ渡す条件

| 渡すもの | 由来 | 理由 |
|---|---|---|
| エリア（都道府県・市区町村） | `search.prefectures` / `search.cities` | 母集団を絞らないと取得量が非現実的になる |
| 物件種別 | `property_type` | 賃貸と売買でURLの系統が違う |
| 価格上限 | `search.price_max_hint` | 同上。MUST上限の2〜3割増しをバッファとして渡す |

**設備条件・間取り・面積・築年数・徒歩分数はサイトへ渡さない。**
WANT条件（オートロック無しでも減点で残ってほしい）をサイト側フィルタに渡すと、
対応サイトでは物件が除外されて順位に現れず、非対応サイトでは素通りする。
ランキングを入れる以上、この2つは両立しない。

`price_max_hint` にバッファを持たせるのは、管理費を別計上するサイトで
「賃料は上限内だが管理費込みだと超える」物件を取りこぼさないため。
上限判定そのものはローカルの MUST（`rent_total_max`）で行う。

## 2. 2段判定によるコスト緩和

一覧ページに載る項目だけで MUST を先に評価し、**`fail` の掲載はDBにも入れず詳細も取りに行かない**。

```
一覧取得 → MUST(1段目) → fail なら破棄
                       → pass/unknown なら upsert → 詳細取得 → 抽出 → MUST(2段目) → 採点
```

- 1段目で判定できる項目は `MetricRegistry` の `available_on_list=True`
  （賃料・間取り・面積・築年・徒歩）
- 判定できない項目（`features` / `floor_min` / `monthly_cost_max`）は `unknown` になり、
  **`unknown` では詳細取得をスキップしない**
- 実測（2026-09-01・SUUMO 4都県）: 一覧177件 → 1段目通過22件。詳細取得を **87%削減**

詳細取得は1回の実行あたりサイト単位で上限を設ける
（既定40件 / `--full` は400件。`scrape/scan.py` の `DEFAULT_DETAIL_LIMIT`）。
取り残しは `detail_fetched_at IS NULL` のキューに残り、次回実行で拾われる。

## 3. エリア検索方式（サイト別）

実装は `src/house_search/scrape/area.py`。アダプタが2つの性質を宣言し、
`resolve_areas` がそれを見て対象エリアを組み立てる。

| 宣言 | 意味 |
|---|---|
| `requires_city` | 都道府県だけでは一覧が0件になるか。`True` なら `search.cities` が空でも全市区へ展開する |
| `city_value_source` | 市区の検索値の出どころ。`jis`＝JIS5桁コード / `mapping`＝`m_city_site_values` の登録値 |

| サイト | 市区必須 | 値の出どころ | 一覧URLの形 |
|---|:---:|---|---|
| SUUMO | — | JIS5桁 | `/jj/chintai/ichiran/FR301FC001/?ar=&bs=040&ta=&sc={JIS5}` |
| HOMES | — | マッピング | `/chintai/{tokyo/chiyoda-city}/list/` |
| GOO | ✅ | JIS5桁 | `/rent/{地方}_ap/area_{都道府県}/{JIS5}.html` |
| ABLE | ✅ | JIS5桁 | `/{都道府県}/area/{JIS5}/list/` |
| CHINTAI_EX | ✅ | JIS5桁 | `/search/city/{JIS5}` |
| ATHOME | — | マッピング | `/chintai/{tokyo/adachi-city}/list/` |
| EHEYA | — | JIS5桁 | `/{都道府県}/area/{JIS5}/search/` |
| NIFTY | ✅ | マッピング | `/rent/{都道府県}/{adachiku}_ct/` |
| APAMAN | ✅ | JIS5桁の**下3桁** | `/{都道府県}/{121}/` |
| SMOCCA | ✅ | JIS5桁 | `/search/{都道府県}/city/{JIS5}` |
| MINIMINI | — | スラグ | 未実装（reCAPTCHA → 課題#18） |

### 3.1 JIS5桁を `m_cities.jis_code` から導く理由

市区の検索値が JIS5桁そのものであるサイトは、`m_city_site_values` に行が無くても
`m_cities.jis_code` から値を作れる。マッピング表に縛ると**取りこぼしが大きい**:
対象4都県（東京/千葉/埼玉/神奈川）の253市区に対し `m_city_site_values` の行は
**67件しかなく**、東京都は23区だけで多摩地域が丸ごと落ちていた。

`m_cities.jis_code` も初版は947件中789件が NULL だったため、Phase 2 で
エイブルのエリア索引（`/{都道府県}/area/`）から実測して473件を補完し、
26件（大阪市・福岡市の区でコードがずれていた）を訂正した。
結果、対象4都県で **216/253市区**が指定できる。残りは課題#16。

### 3.2 市区の自動展開（課題#1）

`requires_city` のサイトは `search.cities` が空でも都道府県内の全市区へ展開する。
展開後に1つも値を解決できなかった場合、**都道府県へフォールバックせず空のまま返す**
（都道府県で引いても0件になるだけなので、`scan` が理由を残してスキップする）。
`requires_city` でないサイトは逆に、市区を解決できなければ都道府県単位へ落とす。

> **Phase 3 で EHEYA・SMOCCA の形式が確定した（どちらも JIS5桁）。**
> `m_city_site_values` の初版はこの2サイトについて、東京23区の行が JIS5桁、
> それ以外の行がスラグという矛盾した状態だった。実URLを確かめた結果
> **JIS5桁が正**で、`m_cities.jis_code` から導出する（この表は引かない）。
>
> 逆に **ATHOME・NIFTY は初版が JIS5桁で誤り**だった。実際はサイト固有スラグで、
> JISからは導出できない。各サイトのエリア索引から実測した値を
> `db/seed/08_city_site_values_slugs.sql` に置いてある
> （ATHOME は東京都のみ。理由は 課題#21）。
>
> APAMAN だけは JIS5桁の**下3桁**という第3の形式だった（新宿区 13104 → `104`）。
> JISから導出できるのでマッピング表は要らない。

## 4. SUUMO（Phase 1 実装済み）

### 4.1 URL

```
一覧: https://suumo.jp/jj/chintai/ichiran/FR301FC001/?ar={地方}&bs=040&ta={JIS2}&ct={万円}&sort=2&pc=30&pn={頁}
詳細: 一覧のリンク（/chintai/jnc_XXXXXXXX/?bc=YYYYYYYY）をそのまま使う
```

- `bs=040` が賃貸。`sort=2` は新着順
- `ct` は**万円単位・小数1桁**（90,000円 → `ct=9.0`）
- **`tc=`（設備条件）は送らない。** v1 は10条件を `tc=` で渡していたが v2 では全廃した
- `pc=30` が1ページの件数。これ未満しか返らなければ最終ページ

### 4.2 一覧のDOM

SUUMO は「1建物 = 複数住戸」の入れ子構造で、**住戸ごとに1掲載**になる。

| 項目 | セレクタ | 備考 |
|---|---|---|
| 建物 | `div.cassetteitem` | |
| 建物名 | `.cassetteitem_content-title` | |
| 住所 | `.cassetteitem_detail-col1` | |
| 駅情報 | `.cassetteitem_detail-text`（複数） | 徒歩分数は**最短**を採る |
| 築年・階建 | `.cassetteitem_detail-col3` | 「築40年 2階建」 |
| 住戸行 | `.js-cassette_link` | |
| 物件ID | `input[name=bc]` の `value` | URLの `bc=` と同値 |
| 所在階 | クラス無しの `td` | 「N階」に一致するセルを拾う |
| 賃料 | `.cassetteitem_price--rent` | |
| 管理費 | `.cassetteitem_price--administration` | **v1 は取得していなかった** |
| 敷金 / 礼金 | `.cassetteitem_price--deposit` / `--gratuity` | |
| 間取り / 面積 | `.cassetteitem_madori` / `.cassetteitem_menseki` | |

⚠ **管理費・敷金・礼金の「-」は「無し」を意味するので 0 として扱う。**
`None` のままにすると `rent_total`（賃料＋管理費）が「管理費不明」となり、
実際には管理費0円の物件が MUST 判定で `unknown` に落ちる。

実測の充足率（2026-09-01・49掲載）: 賃料・面積・間取り・築年・徒歩・住所・管理費・敷金・礼金
はいずれも **100%**、所在階は 100%。

### 4.3 詳細のDOM

- **設備ブロック**: `ul.inline_list` のうち**読点区切りの語が最も多いもの**を採る
  （契約期間・備考など別用途の `ul.inline_list` が混ざるため、位置では選ばない）
- **th/td の項目**: 所在地 / 駅徒歩 / 構造 / 階建 / 階 / 築年月 / 向き / 駐車場 / 入居 /
  契約期間 / 条件 / 建物種別

⚠ **構造化フィールドはアダプタ側で正規化してから `raw_features_text` に載せる。**
「駐車場: 近隣205m16500円」は語彙が無く辞書で照合できないため、
値が `-` 以外なら「駐車場あり」という派生トークンへ寄せる。
欄の意味づけ（`-` が無しを意味する 等）はサイト固有なのでアダプタが吸収し、
辞書側は語彙の対応だけを持つ。
**建物種別（アパート/マンション）は対応する条件が無く未知表記を汚すだけなので載せない**
（`type_specific_attrs` には残す）。

## 5. Phase 2 で追加したサイト

いずれも実HTMLフィクスチャ（`tests/fixtures/{site}/`）でパーサを回帰テストしている。

### 5.1 LIFULL HOME'S

| 項目 | 内容 |
|---|---|
| 一覧 | `/chintai/{エリアスラグ}/list/?cond[sortby]=newdate&cond[monthmoneyroomh]={万円}` |
| ページ | `?page=N`（建物30件/ページ） |
| 建物 | `div.moduleInner.prg-building`。名前 `.bukkenName` / スペック表 `div.bukkenSpec th` |
| 住戸 | `tr.prg-room`。`data-kykey` が物件ID、`data-href` が詳細URL |
| 金額 | `td.price` の `span.priceLabel`＝賃料、その tail＝管理費、`<br>` の tail＝「敷/礼/保証/敷引」 |

⚠ **敷金・礼金が月数表記**（「1ヶ月」）。円へ直すには賃料が要る（`parse_months_fee`）。
⚠ **築年数に「築」が付かない**（「8年 / 8階建」）。共通の `parse_age_years` では読めない。
⚠ `tr.prg-room` には**業者名だけの行**（`memberDataRow`）が混ざる。`data-kykey` の有無で除く。
⚠ **詳細ページの人気条件アイコンは非該当も並ぶ。** `<span class="sr-only">(該当)</span>` で
選別しないと、辞書が「オートロック(非該当)」から「オートロック」を拾う。
⚠ 詳細の設備は Tailwind のユーティリティクラスで組まれ class 名に意味が無いため、
**ラベル文字列**（「設備・サービス」「キッチン/バス・トイレ」等）で引き当てる。
口コミも `dt/dd` を使うのでラベルの白名簿が要る。

**取得できるかは不安定。** 既定の自己申告UAだと 403、ブラウザ相当UAだと 200 だったが、
実スキャンを重ねると AWS WAF のボットチャレンジ（202＋空ボディ）に切り替わった → 課題#17。

### 5.3 エイブル

| 項目 | 内容 |
|---|---|
| 一覧 | `/{都道府県}/area/{JIS5}/list/?o=1` |
| ページ | `&i=N`（30件/ページ） |
| 建物 | `section.m-list_cassette`。名前 `h2` / th-td に 住所・交通・築年・階建・構造 |
| 住戸 | `tr.detail-inner`。`a.js-detailLink[data-bkkey]` が物件ID |

⚠ **賃料上限のクエリ（`ct`）が効かない。** 実測で `ct=9` を付けても 23.9万円の掲載が返る。
代わりに `o=1`（賃料が安い順）で並べ、限られたページ数でも MUST を通る価格帯が

⚠ **詳細リンクの href は `javascript:void(0)`。** 住戸ごとの実URLは
`onclick` の `clickBukkenInfoArea('...')` の中にしかない。
建物見出しの `a.js-detailLinkUrl` にも同形のURLがあるが建物あたり1本しか無い。
⚠ 面積が **㎡（U+33A1）**、敷金が「23.9万」と円を省く、管理費が「--」。
いずれも共通パーサ側で吸収した（NFKC正規化・`万円?`・記号だけの欄は0円）。
⚠ 詳細の「築年」は「築20年」で年月が無い。年月は「築年/築年月」にだけ入る。

### 5.4 賃貸EX

| 項目 | 内容 |
|---|---|
| 一覧 | `/search/city/{JIS5}` |
| ページ | `/page/N`（**パス形式**） |
| 詳細 | `/dwelling/show/{ハッシュ}` |

⚠ **robots.txt が `Disallow: *?*` でクエリ付きURLを全面的に禁じている**
（`/search/results` も禁止）。価格上限をサイト側へ渡せないので、
市区の全掲載を取ってローカル判定する。ページ送りがパス形式なのは幸い。
⚠ **同じURLでも一覧レイアウトが3通り返る**（実測）。

`parse_list` はタグではなく `js-bukken` クラスで拾い、`th` の有無で分岐する。
圧縮行では住所・駅・階建・築年月が建物ヘッダ側にしかないので親を辿る。
⚠ 圧縮行の住所は「足立区竹の塚６」と**都道府県が付かない**。
`resolve_city` は前置の都道府県が無いとき、**全国で一意な市区名だけ**を引き当てる
（「北区」のように複数県にある名前は解決しない）。
⚠ 詳細は同一物件の他社掲載と近隣物件が続けて並ぶため、`th/td` は最初の出現だけを採る。
⚠ 「本物件について」は設備を説明する生成文で語彙が最も多い（抽出数が3倍になる）一方、
未知表記に文断片が入る → 課題#19。

## 5A. Phase 3 で追加したサイト

**5サイトとも HTTP 取得**（→ [ADR 0010](../adr/0010-http-only-fetch.md)）。
v1 と再設計計画は Playwright 前提としていたが、実測ではいずれも
サーバレンダリング済みHTMLを返した。v1 がブラウザを使っていたのは
検索フォームを操作していたためで、URLを直接組み立てる v2 では不要だった。

### 5A.1 アットホーム

| 項目 | 内容 |
|---|---|
| 一覧 | `/chintai/{エリアスラグ}/list/?SORT=7&PRICETO={コード}` |
| ページ | `/list/page{N}/`（**パス形式**・建物30件/ページ） |
| 建物 | `div.p-property--building`。名前 `h2.p-property__title--building` |
| 住戸 | `div.p-property__room--detailbox`。`a[href]` の `/chintai/{数字}/` が物件ID |

⚠ **建物ヘッダの項目名がテキストではなくアイコン**（`dl.p-property__information-hint`
の `dt i.u-icon--map-mini` 等）。ラベル文字列では引けないのでアイコンのクラスで振り分ける。
⚠ **賃料上限はセレクトのコード体系**（`PRICETO=kc113`）。3万円の `kc101` から
0.5万円刻みの連番。選択肢に無い額は**1つ上の帯へ切り上げる**（取りこぼしを作らないため）。
⚠ 「部屋番号・階」の欄は掲載によって号室（`２０５`）だったり階（`2階`）だったりする。
⚠ **完成前の建物は築年数の括弧が付かず年月だけ**（`3階建 2026年12月`）。年月から数える。
⚠ **パズル認証のボット検知がある**（→ 課題#20）。200 のまま認証ページが返るため、
掴んだら**黙って0件にせずエラーにする**。

### 5A.2 いい部屋ネット

| 項目 | 内容 |
|---|---|
| 一覧 | `/{都道府県}/search/` または `/{都道府県}/area/{JIS5}/search/` |
| ページ | `?page={N}`（建物20件/ページ） |
| 掲載データ | **`<script id="__NEXT_DATA__">` のJSON**（`buildingSearchResult.buildings`） |
| 詳細 | `/detail/{propertyFullId}/`。同じくJSONの `property` |

⚠ **DOMを読まない。** HTMLのクラス名は CSS Modules のハッシュ付き
（`styles_cassette__UCHok`）でビルドのたびに変わる。JSON が正典。
⚠ `__NEXT_DATA__` が無ければ**例外にする**。App Router へ移行するとこの経路は消えるため、
「取れているつもりで0件」を最も避けたい。
⚠ **賃料上限をクエリで渡せない**（`?detail.priceMax=` も `?priceMax=` も無視される実測）。
⚠ 設備は `propertyFeatures[].label` に並ぶ。**`remarks`・`salesPoint` は生成文なので載せない**。

### 5A.3 ニフティ不動産

| 項目 | 内容 |
|---|---|
| 一覧 | `/rent/{都道府県}/{市区スラグ}_ct/` |
| ページ | `/{N}/`（**パス形式**・建物40件/ページ） |
| 建物 | `li.result-bukken-list`。住戸 `tbody.click-area` |
| 詳細 | `a[data-detail-link]` の `/rent/…/detail_{ハッシュ}/` |

⚠ **他社サイトの掲載を集約するポータル。** 詳細リンクが外部ドメイン
（`sumaisagashi-madoguchi.com` 等）へ向く掲載が混ざるので**取り込まない**。
⚠ そのため **1ページの掲載数では最終ページを判定できない**（掲載数が建物数を下回る）。
0件のときだけ打ち切る。
⚠ **築年数に「築」が付かない**（`1年7ヶ月`）。
⚠ 住所の行に項目名が無く、`svg title` が「地図マーカー」であることだけが目印。
⚠ 値に案内文言が続く（`無 質問 駐車場について詳しく教えてほしい`）。「質問」以降を切る。
⚠ 詳細は主要スペックが `dt/dd`、細目が `th/td` と**2系統に分かれている**。

### 5A.4 アパマンショップ

| 項目 | 内容 |
|---|---|
| 一覧 | `/{都道府県}/{JIS下3桁}/` |
| ページ | `?page={N}`（建物20件/ページ） |
| 建物 | `article.mod_box_section_bdt`。ヘッダ `div.box_head_result` |
| 詳細 | `/{都道府県}/{市区}/b{建物CD}/{住戸CD}/` |

⚠ **robots.txt が全パスを禁止している**（`Disallow: /`）。
ユーザーの明示的な判断で取得している（→ [ADR 0011](../adr/0011-apaman-robots-exception.md)）。
取得間隔は他サイトより長い4秒。
⚠ **ヘッダ行の列位置が使えない。** ヘッダは先頭に余分な空セルがあり
データ行より1列多い（ヘッダ8列 / データ行7列）。列位置で対応させると
間取りの欄に「お気に入り」を読む。クラス名が付いている `td.chinryo`（賃料）を
起点に前後の相対位置で読む。
⚠ 詳細は項目名が `span.heading` の系統（所在地・交通・築年月・建物階）と
`th/td` の系統（賃料・設備・構造）に**二分されている**。
⚠ 同じ住戸がPR枠と通常枠の両方に出ることがある。物件IDで重複を落とす。
⚠ 「お問い合わせ」リンク（`/inquiry/bukkenentry/{ID}/`）は詳細ページではない。

### 5A.5 スモッカ

| 項目 | 内容 |
|---|---|
| 一覧 | `/search/{都道府県}/city/{JIS5}`（**1ページ90件・ページ送り不可**） |
| 建物 | `div.item_list01`。詳細 `/bukken/detail/{ハッシュ}` |

⚠ **robots.txt がページ送りを禁止**（`Disallow: /*/page/`）。`is_last_page` を常に
True にして2ページ目を取りに行かせない。`/search/results` も禁止のため
**賃料上限も渡せない**（→ 課題#22）。
⚠ **一覧のレイアウトが2種類ある。** 通常表示は1住戸=1行の表で、列位置は
ヘッダ行のラベルから決める。グループ表示（`building-group-container`）は
同一建物の住戸を1つの `td` に畳み、賃料・管理費・敷金・礼金まで同じセルへ入れる。
⚠ **金額セルの `<br>` だけを区切りにする。** `itertext` で分けると
`<span><span>12.8</span>万円</span>` が「12.8」と「万円」に割れて金額として読めない。
⚠ 建物欄に築年数が載らない（`地上3階建 / 2014年04月 / 賃貸アパート`）。築年月から数える。
⚠ 所在地に「◯◯区の賃貸を探す」の導線が付く。

## 6. レート制御・robots.txt

`src/house_search/scrape/fetch.py`。設定は `m_sites` から読む。

| 項目 | 既定 | 備考 |
|---|---|---|
| リクエスト間隔 | 2.5秒 ± 30%のジッタ | `m_sites.min_interval_sec` |
| 1回の実行のページ数 | 5 | `m_sites.max_pages_per_run`（`--full` 時のみ使う） |
| 日次リクエスト上限 | なし | `m_sites.daily_request_cap` |
| リトライ | 429/5xx を最大3回・4秒から倍々 | |
| 打ち切り | 5回連続失敗でサイト中止 | `SiteAborted` |

- **User-Agent は既定で `.env` の `USER_AGENT`**（自己申告）。
  アダプタが `user_agent` を宣言したサイトだけ差し替える。
  LIFULL HOME'S は robots.txt が当該パスを許可しているのに自己申告UAを 403 で拒否するため、
  このサイトにだけブラウザ相当のUAを使う。**取得間隔と robots.txt の尊重は変えない**
- **能動的なボット検知は突破しない。** MINIMINI の reCAPTCHA（課題#18）、
  HOME'S の AWS WAF チャレンジ（課題#17）、ATHOME のパズル認証（課題#20）が該当する。
  Phase 3 で MINIMINI を素の Chromium でも試したが通らなかった。
  通すにはフィンガープリント偽装が要るため、**ブラウザに替えても方針は変わらない**
- ⚠ **ボット検知のページは 200 で返ることがある。** そのまま解析すると
  掲載0件になるだけでエラーにならず「取れているつもり」で気づけない。
  検知ページを判別できるサイトは**アダプタが例外にする**（ATHOME で実装済み）
- **robots.txt を無視するのは APAMAN だけ**（`SiteFetcher.ignore_robots`）。
  アダプタが明示的に宣言したサイトにしか効かず、既定は `False`。
  取得間隔・日次上限・バックオフはこのフラグでも緩めない
  （→ [ADR 0011](../adr/0011-apaman-robots-exception.md)）
- **robots.txt はオリジンごとに起動時1回だけ取得**し、Disallow のURLは取りに行かない
- robots.txt が取れない場合も取得は続ける（控えめな間隔は維持する）
- SUUMO の robots.txt 実測（2026-09-01）: `/jj/chintai/ichiran/FR301FC001/`（一覧）と
  `/chintai/bc_*/`（詳細。`/printout/` を除く）は `User-agent: *` に対して**許可**。
  `Crawl-delay` は bingbot にのみ 30秒の指定があり `*` には無い

## 9. 取得可否の実測とサイト追加候補（2026-09-03）

実装済み10サイトが**想定どおり取れているか**を実機で測り直し、
あわせて未対応サイトを洗い出した記録。数値はすべて実測で、推測は含まない。

### 9.1 実装済み10サイトの取得可否

足立区の一覧1ページを取得して `parse_list` まで通した結果（2026-09-03）。

| サイト | 単発 | 掲載 | 連続取得の耐性 |
|---|---|---:|---|
| SUUMO / GOO / ABLE / CHINTAI_EX / EHEYA / APAMAN / SMOCCA | OK | 20〜87件 | 制限を確認せず（従来どおり全市区を回せる） |
| **NIFTY** | OK | 25件 | **10市区を3秒間隔で連続取得し全件成功** |
| **HOMES** | OK | 40件 | **10秒間隔でも6リクエスト目から HTTP 202＋空ボディ** |
| **ATHOME** | OK | 63件 | **6秒間隔で5リクエスト目からボット認証ページ** |
| MINIMINI | — | — | アダプタ未実装（reCAPTCHA → 課題#18） |

⚠ **単発の疎通確認では制限を再現できない。** 上の3サイトはいずれも
1リクエスト目が正常に返るため、「1回叩いて200が返った」ことを根拠に
「取得できている」と判断してはいけない。**市区を変えながら連続で叩いて初めて分かる。**

#### HOMES は間隔を広げても効かない

課題#17 で `min_interval_sec` を 2.5 → 10.0 秒へ広げたが、
**10秒間隔でも6リクエスト目から HTTP 202＋空ボディ**になった。
課題#17 が記録する「4秒間隔で6件目」と**同じ位置**である。

| リクエスト | 経過 | 結果 |
|---:|---:|---|
| 1〜5 | 2〜40秒 | HTTP 200・670〜730KB・43〜49件 |
| 6〜10 | 48〜95秒 | **HTTP 202・0バイト** |

⚠ **絞りはリクエスト数で掛かっており、間隔では回避できない。**
間隔を広げてもスキャンの所要時間が伸びるだけなので **2.5秒へ戻した**。

#### ATHOME は4リクエストまでなら取れる

| リクエスト | 結果 |
|---:|---|
| 1〜4 | HTTP 200・610KB〜1.7MB・51〜219件 |
| 5〜10 | HTTP 200・8KB（認証ページ） |

「まったく取れない」のではなく**1回の実行で4市区ぶん**は取れる。

#### NIFTY の 405 は「Human Verification」のボット検知

⚠ **同じ日のうちに解消し、また出た。** 午前は10市区を3秒間隔で全件成功したが、
夕方に取り直しを走らせると全市区で 405 になり、両帯とも `aborted` で打ち切られた。

**405 の本文は `<title>Human Verification</title>` の2,117バイトのページ**である
（2026-09-03 実測）。メソッド不許可ではなく、HOME'S の AWS WAF・ATHOME の
パズル認証・MINIMINI の reCAPTCHA と**同じ種類の能動的なボット検知**だった
（→ 課題#38）。⚠ **ブラウザ相当UAでも同じ**なので、HOME'S のような
「UAの選別」ではない。突破はしない。

⚠ **単発の疎通確認で「解消した」と判断してはいけない。**
上の「10市区連続成功」も、検知が出ていない窓に当たっただけだった。

### 9.3 UR賃貸住宅の構造（2026-09-03 実測・Phase 5F 着手前）

**掲載の粒度が他サイトと違う。** 他サイトが「1掲載＝1住戸」なのに対し、
UR は **団地（建物）と住戸が別の階層**になっており、静的HTMLで取れるのは団地まで。
住戸は3つのJSON API（すべて **POST**）から取る。

⚠ **本節の数値はすべて実測**。初版（設計案の段階）には実測で覆った記述が3つあり、
実装前に測ったので取り違えずに済んだ。**どれもエラーにならない類の誤りだった。**

| 初版の記述 | 実測 |
|---|---|
| 検索APIは「`pageIndex=0`（1ページ20件）」 | **ページ送りは無い**。`pageIndex` は黙って無視され、そのエリアの**全団地が1応答で返る**（area=06 は117件） |
| 住戸APIの応答に `year` / `kouzou` / `traffic` / `place` / `feature` がある | **すべて `None`**。これらは3つ目のAPI（`detail_room`）にある |
| `vacancy=1` で空室のある団地に絞れる | **黙って無視される**。空室情報は既定で入っている |

#### 3段構成（すべて POST・`chintai.r6.ur-net.go.jp`）

| 段 | エンドポイント | 単位 | ページ送り | 役割 |
|---|---|---|---|---|
| ① | `/chintai/api/bukken/search/list_bukken/` | 団地 | **無し**（全件返る） | エリア内の全団地。空室数・賃料レンジ・交通 |
| ② | `/chintai/api/bukken/detail/detail_bukken_room/` | 住戸 | **有り**（5件/ページ） | 空室の住戸一覧。賃料・間取り・面積・階 |
| ③ | `/chintai/api/bukken/detail/detail_room/` | 住戸 | 無し（1件） | **設備原文・築年・敷金・保証人要件** |

⚠ **①と②でページ送りの有無が逆**。同じサイトの同じ体系のAPIなので、片方の挙動を
もう片方へ流用すると静かに壊れる（①で `pageIndex` を回すと同じ団地を何度も取り、
②で回さないと5件目以降の住戸が永久に取れない）。

**既存パイプラインへの対応づけ**: ①＋② が「一覧」、③ が「詳細」に相当する。
③ は `detail_fetched_at IS NULL` のキューに乗るので、`--detail-limit` がそのまま効く。

#### ① 検索API `list_bukken`

```
rent_low / rent_high / floorspace_low / floorspace_high
tdfk=13（都道府県コード） area=01〜06（UR独自のエリア区分） block / danchi / shisya
pageIndex / orderByField / orderBySort
→ [{ id:"20_2600", name:"館ヶ丘", skcs:"八王子市", roomCount:13,
     rent:"41,500円～...", commonfee:"（4,500円）",
     access:"<li>JR中央線｢高尾｣駅バス7分 徒歩1～11分</li>...",
     bukkenUrl:"/chintai/kanto/tokyo/20_2600.html", roomUrl, image }, ...]
```

実測（東京都 `tdfk=13` / `area=06`・基準117団地）。⚠ **判定方法の妥当性を先に
担保してから測った**（→ 課題#29）。存在しないキー `zzz=1` が無視されることに加えて、
**効くと分かっているキー（`tdfk`）を動かして差が出ることも同時に確かめる**。

| 送った値 | 結果 |
|---|---|
| 基準 | 団地117・空室のある団地38・空室101室・賃料下限 41,500〜166,300円 |
| `zzz=1`（対照） | **基準と完全同一**（存在しないキーは黙って無視される） |
| `tdfk=11`（対照） | 春日部市など**埼玉の団地**が返る（パラメータが届く経路は生きている） |
| `vacancy=1` | **基準と完全同一**（無視される） |
| `pageIndex=1` / `99` | **基準と完全同一**（ページ送りが無い） |
| `floorspace_low=30` | **基準と完全同一**（無視される。面積はサイト側へ渡せない） |
| `rent_high=99999` | 団地117のまま・**空室のある団地 18**・**空室 69室**・賃料下限の上端 145,200円 |
| `rent_high=100000` | **99999 と同一**（端数で0件にならない） |

⚠ **危うく誤診するところだった。** 最初 `area=01` で測ったところ7通りすべてが
同一バイト数で返り、`zzz=1` の対照も「同一」だったので**判定方法として妥当**と
読めてしまう。実際は `area=01` が全20団地・空室0の小さなエリアで、
**どのパラメータも効いていなかった**だけである。
**対照は「効かないはずのキー」だけでなく「効くはずのキー」も置く。**

⚠ **`rent_high` は団地を絞らず `roomCount` を絞る。** 団地の件数は117のまま、
空室のある団地が 38 → 18 に減る。②を叩く団地数がそのまま半減するので、
**取得リクエスト数に直接効く**（サイト側MUSTとして渡す価値がある → ADR 0015）。
⚠ **端数が使える**ので SUUMO の `ct` のような0件事故は起きない（実測で確認）。

#### ② 住戸一覧API `detail_bukken_room`

`id "20_2600"` を `shisya=20` / `danchi=260` / `shikibetu=0` に分解して渡す。

```
shisya & danchi & shikibetu & orderByField=0 & orderBySort=0 & pageIndex=0
→ [{ id:"001120513", name:"1-12号棟513号室", rent:"47,200円", commonfee:"4,500円",
     type:"2DK", floorspace:"42&#13217;", floor:"5階", floorAll:"5階",
     shikikin:"2か月", requirement:"ナシ", allCount:"13", rowMax:"5",
     roomDetailLink:"/chintai/kanto/tokyo/20_2600_room.html?JKSS=001120513",
     year:None, kouzou:None, traffic:None, place:None, feature:None }]
```

実測（館ヶ丘 `20_2600`・`allCount=13`）:

| pageIndex | 返った住戸 |
|---:|---|
| 0 | 5件 |
| 1 | 5件 |
| 2 | 3件（累計13＝`allCount`） |
| 3 | **`null`**（JSON配列ではなく null） |

- **1ページ5件**（`rowMax:"5"`）。総数は `allCount`
- ⚠ **末尾を超えると `null` が返る。** 空配列ではないので、`for row in data` が
  `TypeError` になる。最終ページ判定は「累計 ≧ `allCount`」で行い、`null` は防御的に空扱いにする
- ⚠ **`roomCount`（①）と `allCount`（②）は一致した**が、①の `roomCount` は
  `rent_high` を送ると絞り込み後の数になる。②は絞り込みを受け付けないので、
  **`rent_high` を送ったときは①の `roomCount` と②の `allCount` がずれる**（未実測・要注意）
- 住戸 `id` は「棟＋部屋番号」の符号化（`001120513`＝1-12号棟513号室 /
  `000100408`＝10号棟408号室）。⚠ **団地をまたぐと衝突しうる**形なので、
  `external_id` は **`{団地id}_{住戸id}`**（例 `20_2600_001120513`）にする。
  実測3団地13住戸では衝突なしだが、これは一意性の証明にならない

#### ③ 住戸詳細API `detail_room`

```
id=001120513 & shisya=20 & danchi=260 & shikibetu=0 & sp=
→ [{ facility:"自動お湯張り機能、…、バス・トイレ別、洗面所独立、洗面化粧台、追い焚き、
       洗濯機置場（室内）、全居室収納、収納（物入）、バルコニー",
     feature_pickup:["バス・トイレ別","2階以上","敷地内駐車場","追い焚き","南向き","光配線"],
     feature:"最寄りの幼稚園・保育園が徒歩10分以内、…、近くに緑あり",

```

- **`facility` が設備原文そのもの**で、辞書照合（`raw_features_text`）にそのまま使える。
  「バス・トイレ別」「洗濯機置場（室内）」「追い焚き」など既存辞書が拾う語彙が揃っている
- ⚠ **`year` は築年数（年）であって築年月ではない**（`51` ＝ 築51年）。
  `t_listings.built_on` は日付なので、そのまま入れられない
- ⚠ **同じキー名でも②と③で中身が違う。** ③では `type` / `floorspace` / `commonfee` が
  `None` で、代わりに `madori` / `madoriYuka` / `commonfee_sp` に入る。
  **②のパーサを③へ流用してはいけない**
- `requirement:"ナシ"` が保証人要件。`shikikin:"2か月"`（礼金・仲介手数料・更新料は制度上ゼロ）

#### 団地ページHTML（`www.ur-net.go.jp`）

`bukkenUrl`（例 `/chintai/kanto/tokyo/20_2600.html`）は静的HTMLで、
**所在地が番地まで**出る（`東京都八王子市館町1097`）。構造（鉄筋コンクリート造）・
交通・戸数もここにある。

⚠ **同じページに「所在地」が2つあり、先に出るのは営業センターの住所**
（`東京都八王子市東町9-10ＥＣＳ第35ビル2階`）。素朴に1つ目を拾うと
**全団地が同じ住所になり、名寄せが壊れる**（しかもエラーにならない）。
⚠ **住戸詳細ページ（`..._room.html?JKSS=...`）はJSで描画される**ので静的HTMLからは取れない
（`rep_madori-yuka` などの空要素になる）。③のAPIを使う理由がここにある。

#### 交通（徒歩分）の表記

①の `access` は `<li>` の並びで、実測107本の内訳は次のとおり。

| 型 | 件数 | 例 |
|---:|---:|---|
| バス経由 | 50 | `JR中央線｢高尾｣駅バス7分 徒歩1～11分` |
| 徒歩レンジ | 45 | `JR八高線｢北八王子｣駅 徒歩9～12分` |
| 徒歩単一 | 12 | — |

- ⚠ **徒歩がレンジなのは団地に棟が複数あるから。** 単一値を前提にしているパーサへ
  そのまま渡せない
- ⚠⚠ **バス経由の「徒歩1～11分」は駅からではなくバス停からの徒歩。**
  他サイトの `walk_minutes` は駅徒歩なので、これを徒歩◯分として扱うと
  **MUST の `walk_minutes_max` を不当に通過する**（半数がこの型なので影響が大きい）。
  バス経由の行は徒歩分として採らないか、バス分を加算する

403 が黙って全許可扱いになる。** この一点はユーザーが承知のうえで取得を選んだ
（取得間隔・日次上限・打ち切りは他サイトと同じものを守る）。ADR 0011 の
APAMAN 例外と同型の判断なので **ADR に残す**。

#### 取得リクエスト数の見積もり

- 連続取得時のスロットリング・検知の有無（本番想定間隔で10〜20リクエスト）。

## 10. 市区ローテーション（Phase 5E・→ 課題#36）

取得数に上限があるサイト（HOMES 5・ATHOME 4 リクエスト/回 → §9.1）を、
**1回の実行では上限ぶんの市区だけ取り、次回は続きの市区から**始める仕組み。
帯82市区なら HOMES が約1.4日・ATHOME が約1.8日で一巡する（取得タスクは2時間ごと）。

実装は `src/house_search/scrape/rotation.py`（DBに触らない純関数）と
`pipeline/persist.py` の `claim_city_rotation` / `advance_city_rotation`。

### 10.1 前提: 巡る先が揃っていないと成立しない

⚠ **`resolve_areas` は検索値の無い市区を黙って落とす。** スラグ系サイトで
`m_city_site_values` に行が無いと、その市区は対象から消えるだけでエラーにならない。
この状態でローテーションを回すと、**その市区を永久に取らないまま「一巡した」ことになる。**

Phase 5E の着手前に実測したところ、回せる市区がそもそも足りなかった。

| サイト | 収集前（帯82市区） | 収集後 |
|---|---:|---:|
| HOMES | 50 / 82 | **82 / 82** |
| ATHOME | 32 / 82 | **81 / 82**（東京都府中市のみ残る） |
| NIFTY | 82 / 82 | 変更なし |

収集は `scripts/tools/collect_city_slugs.py`、投入は
`db/seed/09_city_site_values_phase5e.sql`（新規318行）。

**収集の設計上の要点:**

- **索引URL**は両サイトとも `/chintai/{都道府県ローマ字}/city/`
- ⚠ **市区の同定は索引に埋まっている JIS5桁で行う。** HOMES は
  `id="city-13101-label-part-1"`、ATHOME は `name="areaList[11245]"`。
  **部分文字列一致は使わない**（Phase 2 で名古屋市に北名古屋市の `23234` が
  混入した原因 → ADR 0014）。JIS とリンク文字列の両方が引けて食い違う行は捨てる
  （実測では食い違い0件）
- ⚠ **属性のクォートは `"` と `'` が混在する。** ATHOME の市区リンクは
  `href='/chintai/saitama/fujimino-city/list/'` で、`"` 決め打ちだと
  **71市区のうち10市区しか拾えない**。⚠ **エラーにならず件数が減るだけ**
- ⚠ **取得したHTMLを必ず保存する**（`--cache-dir` / `--from-cache`）。
  上の解析ミスに気づいたとき、保存があったので**取得予算を1回も使わずに直せた**。
  設備の `re-extract`・経路の `re-segment` と同じ考え方
- ⚠ **収集そのものもリクエスト数を絞る**（HOMES 3・ATHOME 3。ATHOME は15秒間隔）。
  課題#21（3秒間隔で47都道府県を回して検知が発動）を繰り返さないため

### 10.2 カーソル

`t_site_scan_cursors`（`(site_id, pattern_name)` PK）。

| 列 | 用途 |
|---|---|
| `last_city_jis` | 最後に取得した市区のJIS5桁。次回はこれより大きい最初の市区から |
| `last_scanned_at` | 最後に枠を使った日時。NULL=未実行（最優先で回す） |
| `last_run_id` | 最後に枠を使った実行ID。同一実行の二重消費を防ぐ印 |

⚠ **カーソルは位置番号でなく JIS5桁で持つ。** 市区リストは YAML 編集で増減する
（課題#32 で実際に4市区を外した）ため、番号だと編集のたびに別の市区へ飛ぶ。
`resolve_areas` は `jis_code` 順に決定的へ並ぶので、
「カーソルより大きい最初の JIS から n 件、末尾に達したら先頭へ戻る」で周回できる。
カーソルの市区自体が YAML から外れても「その次」を探すのでずれない。

⚠ **`m_sites` へ列を足さない。** 監査カラムを最終列に保つDB規約から列追加は
テーブル再作成を伴うが、**テーブル新設にはそのコストが掛からない**
（Phase 5C・5D と同じ判断）。

### 10.3 帯が2つあることによる二重消費

⚠ **HOMES は両帯の `sites:` に載っている。** 素朴に実装すると1回の `scan` で
5+5=10 リクエストが飛び、**後半の帯が全部 202 になる**。

そこで**1回の実行では1帯だけ**が枠を使う。

1. `claim_city_rotation` がカーソル行を登録する（無ければ作る）
2. 同じ `run_id` の行がそのサイトに既にあれば**譲る**
3. `last_scanned_at` が最も古い行（NULL が最優先・同着はパターン名順）が枠を取る
4. 取った側は `last_scanned_at` と `last_run_id` を更新する

`scan` は1プロセスで全パターンを回すので、1回目の実行で両帯の行が登録され、
以後は交互に回る（実測で確認済み）。

### 10.4 取得側の制約

- **`--full` でも1ページに固定**する。上限はリクエスト数に掛かっているので、
  2ページ目を取ると一覧の市区がそのぶん減る
- **詳細取得は0件に固定**する。予算を一覧で使い切るため。詳細キューには残るので、
  予算の回復窓を実測してから「N回に1回の詳細回」を入れるかを決める（→ 課題#36）
- ⚠ **カーソルは取得を試みる前に進める。** スロットリングやボット検知で失敗した
  市区を再試行し続けると、そこから先へ永久に進めない。
  実測でこれが効いた（ATHOME は3・4件目が認証ページだったがカーソルは進んだ）
- ⚠ **サイト側フィルタの対照取得（→ 課題#29）は予算を1つ余分に使う。**
  一覧が0件だったときだけ走るので通常は増えないが、
  ローテーション中に0件の市区に当たると上限を1つ超える

### 10.5 実測（2026-09-03）

| 確認したこと | 実測 |
|---|---|
| 帯1が枠を取り、帯2は譲る | 帯1 取得95件・新規18件 / 帯2「他パターンが取得枠を使用中」 |
| 次の実行で帯が交代する | 2回目は帯1が譲り、帯2のカーソルが `11105` へ進んだ |
| カーソルが JIS で進む | HOMES 帯1 `13105`（文京区まで）/ ATHOME 帯1 `13104` |
| 失敗しても次へ進む | ATHOME は3・4件目が認証ページだったがカーソルは進んだ |
| 掲載が貯まる | HOMES **10件 → 28件** |

⚠ **予算は時間で回復する（プロセス単位ではない）。** 2分後に2回目を流したら
HOMES の5リクエストが**全て 202**になった。取得タスクは2時間ごとなので実運用では
回復窓に収まる見込みだが、**窓の長さそのものは未測定**（→ 課題#36）。

⚠ **ATHOME は23区帯で MUST 1段目を1件も通らなかった**（取得131件 → 通過0件）。
`SORT=7`（賃料が安い順）で1ページ目だけを見るため、千代田区・中央区では
**30㎡未満の 1K/1R ばかりが返る**。`supports_site_filters` を宣言しておらず
面積下限をサイト側へ渡せていないのが原因で、ローテーション自体の不具合ではない。
直すには ATHOME の面積・間取りキーを実サイトで測る必要がある
（推測で書かない → 課題#29）。

### 11.2 市区スラグは追加リクエスト0で全国ぶん採れる

サイトマップ `sitemap_rent_room_list_map_ja.xml`（1リクエスト・821KB）に
**市区一覧URLが1,000件**入っている。

```
/properties/chintai/area/shizuoka/hamamatsu-shi-chuo-ku-22138
/properties/chintai/area/tokyo/adachi-ku-13121
```

⚠ **末尾に JIS5桁が埋まっている**ので、ADR 0014 の原則どおり**部分文字列一致を使わずに**
市区を同定できる。しかも浜松市は**2024年の区再編後のコード**（22138/22139/22140）で、
`m_cities` と一致する。

⚠ **収集にエリア索引を舐める必要が無い**（ATHOME で検知を発動させた 課題#21 の手順が不要）。

### 11.3 一覧の構造は「建物カードの中に住戸が並ぶ」

```
ApartmentItem_apartment-item__…            ← 建物（アパート）
  レオパレスアクト六木
  東京都足立区六木４−６−９
  つくばエクスプレス「八潮駅」徒歩28分
  2階建てアパート / 2009年12月築
  RoomItem_room-item__…                     ← 住戸（1件=1掲載）
    6.4万円（共益費 6,500円）／敷金 不要 / 礼金 1ヶ月
    1K｜23.18㎡｜201号室
    → /properties/chintai/tokyo/adachi-ku-13121/act-mutsugi-44286/201
```

- **UR と違い、建物と住戸が同じHTMLに載る**ので任意フック（ADR 0019）は要らない。
  `parse_list` が建物×住戸を展開すればよい
- ⚠ **CSS Modules のハッシュ名**（`ApartmentItem_apartment-item__cWhGE`）。
  EHEYA と同じ不安定さだが、**`__` より前の接頭辞は安定**なので
  `starts-with(@class, 'ApartmentItem_apartment-item__')` で拾う。
  ⚠ **より安定なのは住戸URLの形**（`/properties/chintai/{県}/{市区}-{JIS}/{建物}-{ID}/{号室}`）
- ⚠ **駅名が鉤括弧つき**（`「八潮駅」`）。課題#41 の修正が入っていないと**駅が1件も同定できない**
- ⚠ **交通欄にバス便が混ざる**（`「綾瀬駅」バス26分 六木四丁目下車 徒歩3分`）。
  matcher の「下車」パターン（HOME'S 向け）がそのまま効く
- `external_id` は `{建物ID}_{号室}`（例 `44286_201`）を推奨

### 11.4 ⚠ 総件数の表示を最終ページ判定に使わない

一覧に「255件」（足立区）「209件」（銚子市）と出るが、**ページ数と合わない**。

| 市区 | 総件数表示 | ページ数 | 1ページの住戸 | 積 |
|---|---:|---:|---:|---:|
| 足立区 | 255 | 13 | 18 | 234 |
| 銚子市 | **209** | 11 | **4〜8** | **44〜88** |

銚子市は積が総件数の1/3以下になる。**満室を含む総戸数**の可能性が高いが**未確定**。

⚠ **最終ページの判定は「そのページの住戸が0件」で行う。**
`?page=12`（最終ページ超え）は **HTTP 200・建物0件**で返る（実測）。
既存の `is_last_page(count)` の枠にそのまま乗る。

### 11.5 サイト側へ渡せる MUST（→ ADR 0015）

⚠ **キーと選択肢は一覧ページの検索フォームからそのまま採れた**（`<select name=...>`）。
ATHOME・HOMES・GOO・APAMAN と同じで、**実サイトは検証にだけ使えばよい**。

実測（足立区 `adachi-ku-13121`）。⚠ **総件数がページ数と合わないので、
GOO・APAMAN・ATHOME と同じく「返る掲載の中身」で確かめた。**

| 送った値 | 建物 | 賃料 | 面積 | 徒歩 |
|---|---:|---|---|---|
| 基準（指定なし） | 13 | 6.4〜12.3万 | 19.87〜28.15㎡ | 6〜30分 |
| **`zzz=1`（対照）** | 13 | 6.4〜12.3万 | 19.87〜28.15㎡ | 6〜30分 |
| `sizeFrom=30` | 16 | 10.6〜17.8万 | **30.46〜56.04㎡** | 4〜16分 |
| `rentTo=70000` | 2 | **6.4〜6.7万** | 23.18〜26.02㎡ | 14〜28分 |
| `walkTo=20` | 11 | 6.7〜12.3万 | 19.87〜27.8㎡ | **6〜23分** |

- `zzz=1` が基準と**完全同一**＝存在しないキーは黙って無視される。判定方法の妥当性は担保できた
- **`rentTo`（円・5,000円刻み）と `sizeFrom`（㎡・5刻み）は効く。** 不等号の向きも正しい
- ⚠⚠ **`walkTo=20` は徒歩23分を返すので配線しない。** 交通欄に複数駅が並ぶため
  「いずれか1駅が20分以内」の意味である可能性が高いが、**測っていないので断定しない**。
  ローカルの `walk_minutes`（最短）と食い違うと ADR 0015 の不変条件
  （サイト側フィルタは MUST より厳しくしない）を破りうる
- ⚠ **`propertyAgeTo` は `99`＝新築という特殊値を持つ**（3/5/10/15/20/25/30年と同じ `select` に同居）。
  数値として丸めると新築を指してしまうので、配線するなら別扱いが要る。**今回は配線しない**
- 並び順 `sort`: 1=家賃が安い順 / 2=高い順 / 5=面積が広い順 / 13=駅まで近い順 / 16=築年数が新しい順。
  ⚠ **1ページしか見ないわけではない**（ページ送りが自由）ので、ATHOME のような
  「安い順の1ページ目が最小の部屋で埋まる」問題（課題#39）は起きない

### 11.6 詳細ページ

`/properties/chintai/{県}/{市区}-{JIS}/{建物}-{ID}/{号室}`。一覧の住戸リンクをそのまま使える。

取れる項目: 建物名 / 住所（番地まで）/ 交通 / 間取り・面積 / 建物構造 / 所在階・階数 /
総戸数 / 種別・築年数（`アパート/築16年（2009年12月）` → `built_on` が作れる）/
**現況（`空室`）** / 諸費用。

設備はカテゴリ別のタグ列で並ぶ:

```
バス・トイレ  バス・トイレ別、浴室乾燥機、温水洗浄便座、室内洗濯機置き場
セキュリティ  TVドアホン、スマートロック
放送・通信    インターネット対応、LEONET
その他        給湯、エアコン、駐輪場
```

- ⚠ **`text_content()` をそのまま設備原文にしてはいけない。** RSC ペイロードの
  `<script>` が本文に混ざり、翻訳リソース（`"searchByFeature":"特徴からお部屋を検索"`）まで
  拾ってしまう。**script を除いてから**設備ブロックだけを取る（課題#19 の別の形）
- `LEONET`（自社インターネット）・`スマートロック` は辞書未登録の見込み。
  未知表記として集めてから追加を判断する（→ 課題#15）

### 11.7 ⚠ 掲載終了が 404 で判別できない

存在しない住戸URL・存在しない建物URLのいずれも **HTTP 200・465KB** で
検索トップ相当（`<title>【レオパレス21】賃貸マンション・アパート・マンスリーマンション検索`）を返す。

⚠ **`is_sold` を404で判定できない**ので、タイトルか建物カードの有無で判別する。
SUUMO のエラーページ・ATHOME の認証ページと同じ扱い（判別できるものはアダプタが見る）。

### 11.8 ⚠ 実地の確認: 配線は貫通したが実データでは MUST 1段目の通過が0件

`scan --seed --site LEOPALACE` の実測（2026-09-04）。

| 帯 | 取得 | MUST1段目通過 |
|---|---:|---:|
| 東京23区賃貸 | 39 | **0** |
| 近郊60分圏賃貸 | 38 | **0** |

**原因は実装ではなく在庫の性質**だった。フィルタなしで取得した261住戸
（千葉県19市区＋足立区）の内訳:

| 間取り | 件数 | 割合 |
|---|---:|---:|
| **1K** | 251 | **96.2%** |
| 1R | 9 | 3.4% |
| 1DK | 1 | 0.4% |
| **1LDK 以上** | **0** | **0%** |

面積は最小17.39㎡・**中央21.9㎡**・最大31.05㎡で、**30㎡以上は4件（1.5%）**。

⚠ **レオパレス21は単身者向けの 1K / 1R しか持たない。** 検索パターンの
`must.layouts`（1LDK / 2K / 2DK / 2LDK / 3DK / 3LDK）を**構造的に1件も満たさない**。

⚠ **UR（Phase 5F）とは質が違う。** UR は「3DK を `layouts` に足せば1件通る」
という話だったが、レオパレスは**間取りと面積の両方で外れている**ので、
`layouts` に 1K を足しても `area_min: 30.0` で96%が落ちる。

サイト側フィルタを併用した実測でも同じ結論になる（足立区・`rentTo=130000&sizeFrom=30`）:

```
1K 35.84㎡ 賃料107,000+管理6,500 徒歩11分
1K 34.39㎡ 賃料106,000+管理6,500 徒歩13分
1K 33.34㎡ 賃料115,000+管理6,500 徒歩16分
```

9件すべてが `rent_total_max`（23区は100,000円）と `layouts` の**両方**で落ちた。
**30㎡以上の住戸は10万円超**なので、賃料と面積が両立しない。

⚠ **`m_sites` で SHAMAISON（シャーメゾン）を「自社物件のみのため対象外」と
している理由が、レオパレスにも当てはまることが実測で確認できた。**
「自社物件系は既存サイトと在庫が重ならないので価値が高い」という Phase 5G の
前提（→ 課題#37）は、**重ならないことと欲しい物件があることは別**という形で覆った。

⚠ **有効のまま置くと毎回の `scan` で 82市区×2帯を無駄に叩く**（実測で約2分・77住戸取得して0件）。
