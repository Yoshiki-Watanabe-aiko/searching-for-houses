# 絞り込みをサイト側フォームからローカル判定へ移す

**状態: 採用（2026-09-01）**

各サイトの検索フォームへ渡すのは **エリア・物件種別・価格上限（バッファ付き）の3つだけ**とし、
設備条件・間取り・面積・築年数・徒歩分数の判定と採点はすべてローカル（DB＋Python）で行う。
サイト別のコードが担うのは「取得と解析」に限る。

## 背景・検討した選択肢

**この転換はランキング導入と論理的に不可分である。**
WANT条件（例: オートロック無しでも減点で残ってほしい）をサイト側フィルタに渡すと、

- 条件に対応しているサイトでは物件が**除外されて順位に現れない**
- 対応していないサイトでは条件が**素通りする**

という非対称が生じ、サイト横断のランキングが成立しない。
ランキングを入れる以上、設備条件のURL反映は全サイトで使ってはならない。

加えて v1 の実測では、10サイト中6サイト（HOMES/GOO/APAMAN/MINIMINI/EHEYA/SMOCCA）が
設備条件をURLに反映できず、**条件が黙って無視されて全件通知される**状態だった。
課題#1〜#3 はいずれもこの「サイト側で絞る」方針に起因している。

サイト側フィルタを維持したまま非対応サイトだけローカル判定する折衷案も検討したが、
サイトごとに判定基準が変わる（＝スコアの比較可能性が失われる）ため採らなかった。

## Consequences

- **取得件数が増える。** 緩和策は2段判定:
  1. 賃料・間取り・面積・築年・徒歩は全サイトの**一覧ページに載っている**。
     ここで MUST 判定し `fail` の物件は詳細ページを取得しない
  2. 既知物件（`external_id` 一致）は詳細を再取得しない
  3. 市区町村指定で母集団自体を縮小できる
- MUST判定は `pass` / `fail` / `unknown` の3値にする。**詳細取得をスキップするのは `fail` のみ。**
  売買の管理費・修繕積立金・権利形態は一覧に出ず詳細を見ないと判定できないため、
  Phase 1 の賃貸実装から3値で作る（`MetricRegistry.available_on_list` で明示）
- 設備条件はサイトのタグではなく**詳細ページ本文の辞書マッチング**で得る。
  辞書のカバレッジがそのまま判定精度になるため、原文（`raw_features_text`）を保存して
  再抽出できるようにする
- 副産物として課題#1（ABLE/SMOCCA の市区必須）は市区自動展開で解消し、
  課題#2（未実装条件の追加）・課題#3（ATHOME設備AND検索）は「対応不要」でクローズできる
- `m_sites` から旧 `site_condition_map`（サイト×条件の対応表）が消える
