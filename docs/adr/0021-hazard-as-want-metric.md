# ハザード評価は「減点」ではなく WANT の数値metricとして載せる

**状態: 採用（2026-09-05・Phase 5I 後半）**
**関連: 課題#46／[ADR 0020](./0020-address-master-chome-guard.md)（住所マスタ）／
要件定義書 §5・§6・§11／詳細設計書 `03_スコアリング設計.md`**

ユーザー要望は「ハザードマップの危険度をDBに入れ、それを基に**得点を計算**したい。
**減点数**を持たせたい」だった。実装は減点ではなく、既存の WANT（加点）モデルに
数値metricとして載せる形を採る。

---

## 決定1: 真の減点は実装しない（加点で等価に表現できる）

`score = 100 × Σ(wᵢ × sᵢ) / Σ(wᵢ)` から点を差し引くと、**0〜100点という数字の意味が壊れる**
（同じ理由で `any_of` を導入した → 要件定義書 §6）。

⚠ **加点で不足はない。** 安全な物件が満点を取る配点は、分母 Σw に乗る以上、
危険な物件から見れば**同じ点数の減点と数学的に等価**である。実測では母集団の
32.2%（近郊帯）〜92.6%（23区の土砂）が「区域外＝満点」なので、
体感としても「危険な丁目の掲載だけが沈む」形になる。

副次的な利点として、**スコアエンジン・内訳JSONB・ダイジェスト・決定性テストが無改修**で済む。

## 決定2: 土砂災害も feature ではなく numeric にする

課題#46 の当初案は「連続量（浸水深）は numeric、ゾーン型（土砂）は
`source='DERIVED'` の feature」としていた。**面積比が取れたので numeric に統一する**
（2026-09-05 ユーザー承認）。

| 論点 | numeric が優る理由 |
|---|---|
| 未解決の扱い | 欠損として**分母から外れる**。feature の unknown は分母に残って0点になり、住所が町名までしか無いサイトの掲載が不当に沈む |
| 更新のコスト | feature は抽出時に書かれるので `sync-hazards` のたびに全件再抽出が要る |
| 表現力 | 二値ではなく階調がある（土砂は「丁目の端に5%だけ掛かる」形が大半） |

## 決定3: 主力は面積加重平均ランク。最大ランクは足切り専用にする

⚠ **最大ランクは外れ値に引っ張られる。** 実測（2026-09-05）:

| 丁目 | 面積比 | 最大ランク | 面積加重平均 |
|---|---:|---:|---:|
| 千葉県市川市菅野5丁目 | 100% | **6**（20m以上） | **2.52**（0.5〜3mが主） |
| 東京都北区浮間5丁目 | 100% | 5 | 3.99 |

菅野5丁目のランク6は水路際のごく一部で、大半は 0.5〜3m。丁目内 max を採ると
**この丁目が最悪扱いになる**。`flood_rank_avg` を WANT へ、`flood_rank_max` は
足切り（MUST）専用に置く。

⚠ **面積比は帯によって判別力が無い。** 23区は **3,124丁目のうち浸水想定に一切
掛からないのが2丁目だけ**で、`flood_area_ratio` は99.1%が0.25以上に固まる。
台地の杉並・世田谷でも平均面積比 0.56〜0.74 だった。`flood_rank_avg` なら
25%点0.71・中央2.0・最大4.0と階調が出る。

## 決定4: 「区域外（0.0）」と「未解決（None）」を最後まで混ぜない

**本フェーズで唯一「黙って壊れる」経路がここ。** 混ぜると
「危険なのに情報が無いから減点されない」掲載が「安全」と同じ扱いになり、
**例外にならないまま順位だけが狂う**。3層で担保する。

| 層 | 担保 |
|---|---|
| 生成（`build_hazard_levels.py`） | 恒等式 assert（照合済みキー × 種別 × 方式 ＝ 行数） |
| 読み込み（`load_hazard_rows`） | 同じ恒等式＋値域＋種別の綴り検査 |
| **採点** | `0.0` → 満点の hit ／ `None` → `missing` で分母から除外 ／ 足切りは unknown |

⚠ 実装では `float(value or 0)` のような書き方を禁じる（0.0 が falsy なので未解決に化ける）。
`persist._opt_float` と `tests/test_hazard_scoring.py` がこれを固定している。

## 決定5: グループ内で最も細かい住所の評価を採り、無ければ町へ落とす

設備の和集合・通勤時間の最短と同じく、**名寄せしたグループ全体で情報が最大になるもの**を採る。
サイトによって住所の粒度が違うため（→ ADR 0012）。

- 丁目で引けなければ `m_address_points.town_key` 経由で町の評価へ落とす。
  ⚠ **SQL の文字列操作で「N丁目」を剥がさない。** 住所マスタの物理列を引く
  （正規表現で削る実装は、丁目の無い町で番地を削って別の町を指す → ADR 0020 と同じ失敗）
- ⚠ **ハウスコムは住所が町名までしか無く（414件の全件）**、この経路が無いと
  そのサイトの掲載が丸ごと未解決になる

実測の解決率（**分母は掲載全体** → 課題#41）: 23区帯 **99.9%** / 近郊帯 **99.7%**。
未解決はほぼ UR（住所が市区までしかない）。

## 決定6: 足切り（MUST）は当面設定せず、加点だけで始める

⚠ **厳しくする方向は取り直し不要**（既存データの採点が絞られるだけ）だが、
**緩める方向は取り直しになる**（MUST 1段目で fail した掲載はDBに残らない → ADR 0013）。
エリア帯で採った「広く取ってから締める」手順に倣い、まず順位への反映を見てから決める
（2026-09-05 ユーザー判断）。

⚠ 足切りを入れるときは `unknown_policy` を `drop` へ倒さないこと。
未解決は「危険」ではなく「情報が無い」なので、落とす側に倒すと
**町名までしか出さないサイトの掲載が黙って消える**。

## 決定7: weight は既存から削らず追加する。best/worst は帯で共通にする

| metric | weight | best | worst |
|---|---:|---:|---:|
| `flood_rank_avg` | 15 | 0 | 4 |
| `landslide_area_ratio` | 5 | 0 | 0.1 |

重み合計は 228 → **248**（ハザードの占める割合 8.1%。徒歩10より重く通勤25より軽い）。
**既存項目の weight を変えないので、それらの相対関係は保たれる。**

⚠ **best/worst は帯で共通**にした。賃料・通勤のように帯ごとに相場が違う metric とは事情が違い、
「浸水しない＝満点」の意味を帯をまたいで揃えたいため。0点張り付き率（→ 課題#31）は
`flood_rank_avg` が 23区 0.2% / 近郊 0.0%、`landslide_area_ratio` が 0.3% / 6.8% で
いずれも weight が死ぬ水準ではない。

⚠ **23区では `flood_rank_avg` の満点が1件も出ない**（区域外の丁目がほぼ無いため）。
これは実態の反映であって不具合ではない。満点が出ないことは相対比較を妨げない
（問題になるのは0点の張り付きのほう）。

## 実行時に外部を叩かない（通勤時間より徹底する）

ポリゴンの交差判定はオフラインの生成スクリプトで終わっており、
`scan` / `rescore` は `m_hazard_levels` を JOIN するだけ。
⚠ **`rescore` がネットワーク不要・軽量依存のまま保たれる**ことが要件で、
`tests/test_no_geo_runtime_deps.py` が `src/` から shapely / pyshp を
import していないことを固定している。

採点データの読み込みは JOIN 追加で **2.31秒 → 5.18秒**（実測・両帯合計）。
⚠ 値ごとにスカラーサブクエリを5本並べると同じキー解決を5回繰り返すので、
**2段の LATERAL**（キーを1つ決める → 9行を横に畳む）にしてある。

## 却下した案

| 案 | 却下の理由 |
|---|---|
| スコアから実際に減点する | 0〜100点の意味が壊れる。加点で数学的に等価（決定1） |
| 丁目の代表点がポリゴン内かで判定する | **12分の1しか拾えない**（東京都のA33で80丁目 vs 交差判定1,140丁目）。⚠ 例外にならず静かに過小評価される |
| ハザードの所在地属性（A33_006）で突き合わせる | ①A31（洪水）には住所属性が無い ②A33 も県によって欠損する（原典の注記）。**県ごとに黙って穴が空く** |
| 丁目内の最大ランクを WANT の主力にする | 外れ値に引っ張られる（決定3） |
| 洪水と土砂で同じ集計方式を使う | 該当率が 72.9% と 18.9% で分布が正反対。1つの方式では両方に判別力を出せない |
