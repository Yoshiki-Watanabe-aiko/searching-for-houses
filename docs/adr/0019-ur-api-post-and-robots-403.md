# ADR 0019: UR賃貸住宅を宣言ベースの任意フックで取り込み、APIホストの robots.txt 403 を記録したうえで進む

- **状態**: 採用
- **日付**: 2026-09-03（Phase 5F）
- **関連**: [ADR 0011](./0011-apaman-robots-exception.md)（robots の例外）/
  [ADR 0015](./0015-site-side-must-filters.md)（サイト側MUST）/
  [ADR 0003](./0003-local-filtering.md)（判定と採点はローカル）/
  課題#37・詳細設計書 §9.3

## 背景

実装済み10サイトはすべて民間の仲介ポータルで、**公社系の掲載が母集団に1件も入っていない**。
UR賃貸住宅は他ポータルに掲載されないため**重複が極めて少なく**、
礼金・仲介手数料・更新料が不要で保証人も要らない。追加の価値が最も高いと判断した（課題#37）。

ところが UR は既存の枠に3点で収まらない（すべて 2026-09-03 の実測 → 詳細設計書 §9.3）。

1. 取得が **JSON API への POST**（`SiteFetcher` は GET しか持っていなかった）
2. **団地（建物）と住戸が別階層**で、一覧を作るのに2回のAPIが要る
3. 設備・築年は**3つ目のAPI**（`detail_room`）にしかない

加えて、APIホスト `chintai.r6.ur-net.go.jp` の **robots.txt が HTTP 403 を返す**（不在ではない）。

## 決定

### 決定1: `SiteScraper` は変えず、**任意フック**を宣言したアダプタにだけ委譲する

`pipeline.scan` が `getattr(scraper, "collect_listings", None)` /
`getattr(scraper, "fetch_detail", None)` を見て、宣言していれば
一覧の収集／詳細の取得だけを差し替える。

| フック | 置き換える範囲 | 置き換えない範囲 |
|---|---|---|
| `collect_listings` | `list_urls` → `page_url` → `parse_list` の一覧収集 | MUST 1段目・upsert・0件バックストップ・名寄せキー |
| `fetch_detail` | `fetcher.get(detail_url)` ＋ `parse_detail` | 詳細キュー・`--detail-limit`・設備抽出・保存 |

**却下した案**:

- **`SiteScraper` Protocol にメソッドを足す** — 既存10アダプタ全部に実装義務が生じる。
  `supports_site_filters`（ADR 0015）・`city_rotation_limit`（課題#36）で
  実績のある「クラス属性の宣言＋呼び出し側の `getattr`」を踏襲する
- **フックが `(listing, detail)` の対を返す** — 詳細まで一覧の段で取ることになり、
  **`--detail-limit` が効かなくなる**。UR は帯2で住戸が数百あるので、
  1回の実行で数百リクエストを一覧フェーズに押し込むことになる。
  ③を詳細キューに乗せれば既存の分割がそのまま効く
- **団地ページのHTMLを解析する** — 住戸単位の空室は静的HTMLに載らない。
  住戸ページ（`..._room.html?JKSS=...`）はJSで描画され、
  `rep_madori-yuka` のような**空要素**しか取れない

### 決定2: `SiteFetcher.get` の本体を `request(method, url, *, data)` へ一般化する

`get` / `post` は薄いラッパにし、**レート制御・robots判定・バックオフ・
連続失敗の打ち切り・日次上限はそのまま共有する**。メソッドが違うだけで
相手にかける負荷は同じなので、POST 用に別経路を作らない
（ADR 0017 が NAVITIME で `SiteFetcher` を再利用したのと同じ考え方）。

### 決定3: robots.txt が読めなかったときは「**記録されたうえでの全許可**」にする

`_load_robots` は取得に失敗すると空ルール（＝全許可）で進む。
⚠ **標準の `RobotFileParser.read()` は 401/403 を `disallow_all` にする**ので、
この実装は**標準より許可側に倒れている**。UR のAPIホストが実際に 403 を返すため、
黙って通り過ぎるのをやめて**オリジンごとに1回だけ警告を記録**する。

**`ignore_robots` は立てない。** ADR 0011（APAMAN）は `Disallow: /` を
**承知のうえで無視する**という判断だったが、UR は違う。

| | APAMAN（ADR 0011） | UR（本ADR） |
|---|---|---|
| robots.txt | 取得でき、`Disallow: /` と**明示的に禁じている** | **読めない**（403）。禁止も許可も表明されていない |
| 判断 | 禁止を承知で無視する | 表明が無いので従来どおり進むが、**記録に残す** |
| フラグ | `ignore_robots = True` | `ignore_robots = False` のまま |

⚠ **同居する `www.ur-net.go.jp` の robots.txt は HTTP 200 で読める**
（禁止は `/chintai/*/result/?skcs=` 等の駅・沿線検索だけで、団地ページは許可）。
住戸ページURLはこちらのホストなので、通常どおり robots 判定を通る。

取得間隔（3.0秒）・ページ上限・日次上限・連続失敗の打ち切りは他サイトと同じものを守る。

### 決定4: 市区は**サイトへ渡さず、応答の `skcs` でローカルに絞る**

UR のエリアは独自の `area=01..`（JIS5桁でもサイト固有スラグでもなく、
**市区の粒度ですらない**）。市区で検索する手段が無いので、その都県の
**全 area を列挙して応答の `skcs`（市区名）で落とす**。

⚠ `skcs` は政令指定都市で行政区まで入り（`さいたま市中央区`・`横浜市港北区`）、
**`m_cities.canonical_name` と同表記**なので検索パターンの `cities` とそのまま突き合わせられる。

`area` 区分の静的な対応表は作らない。UR が区分を変えても**気づけないまま
市区が落ちる**（`resolve_areas` が検索値の無い市区を黙って落とすのと同じ失敗 → 課題#36）。
実測では欠番が無いので **01 から順に叩き、空応答が2回続いたら止める**。

### 決定5: 賃料上限（`rent_high`）は渡す。面積・間取り・徒歩は渡さない

ADR 0015 の「サイト側へ渡してよいのは MUST だけ」に沿う。実測で効くのは `rent_high` だけだった。

| 送った値 | 結果 |
|---|---|
| `rent_high=99999` | 団地117のまま・**空室のある団地 38 → 18**・空室 101 → 69室 |
| `rent_high=100000` | 99999 と**同一**（端数で0件にならない） |
| `floorspace_low=30` | **基準と完全同一**（黙って無視される） |
| `vacancy=1` / `pageIndex` | **基準と完全同一**（黙って無視される） |

⚠ **`rent_high` は団地を絞らず `roomCount` を絞る。** ②③を叩く団地がそのまま半減するので、
**取得リクエスト数に直接効く**（1エリアあたり約132 → 約86）。
⚠ **端数が使える**ので SUUMO の `ct` のような0件事故は起きない（実測で確認）。

一覧URLを持たないので既存の `site_filters` 機構（クエリ文字列の付与）は使えず、
`supports_site_filters = False` のままアダプタ内で送る。

### 決定6: 初期費用の有利さは**合成トークン**で既存の WANT へ載せる

UR は礼金・仲介手数料・更新料がゼロで、`requirement="ナシ"` なら保証人も不要。
⚠ **`rent_total`（賃料＋共益費）だけで他サイトと比べると、この有利さがスコアに1点も現れない。**

設備原文（`raw_features_text`）へ「礼金なし／仲介手数料なし／更新料なし／保証人不要」を
足し、既存の条件 `PRICE_NO_REIKIN` / `PRICE_NO_GUARANTOR` に**辞書を変えずに**載せる
（EHEYA の `_FLAG_TOKENS` と同じ手法）。

⚠ **「敷金なし」は足さない。UR も敷金は2か月取られる。**
⚠ ただし**この2条件は現行の両帯 WANT に入っていない**ので、
`configs/*.yaml` に weight を足さない限り順位には反映されない（→ 下記の帰結）。

## 帰結

### 良くなること

- 他ポータルに載らない団地が母集団に入る。**重複が構造的に少ない**
- ②③の取得が既存の詳細キュー・`--detail-limit`・設備抽出・名寄せにそのまま乗る
- `post` が生えたことで、今後 POST が要るサイト（課題#37 の残り5サイト）も
  レート制御を共有できる
- robots.txt を読めなかったことがログに残る。**全サイトに効く**改善

### 悪くなること・引き受けたリスク

- ⚠ **住所が市区までしか取れない。** ①にも③にも住所欄が無く、番地まで欲しければ
  団地ページHTMLを団地ごとに1リクエスト追加することになる。
  そのため UR の掲載は **`dedup_key` が作れず単独で残る**。
  UR は他サイトと重ならないので名寄せの実害は無いが、
  **UR 内の同一住戸の重複は抑制されない**（実測では住戸IDが一意なので発生しない見込み）
- ⚠ **交通欄の半数がバス経由**で、その「徒歩◯分」は**バス停からの徒歩**である。
  駅徒歩として扱うと MUST の `walk_minutes_max` を不当に通過するため、
  バス経由の行からは徒歩分を採らない（駅名だけ拾う）。
  結果として**バス便の団地は `walk_minutes` が unknown になる**
- ⚠ **築年数（`year`）は築年月ではない**ので `built_on` に入れられず、
  `type_specific_attrs.ur_age_years` に残すだけになる。
  現行の MUST に築年は無いので判定には影響しないが、
  **WANT の `age_years` は欠損として再正規化される**
- 一覧の取得が重い。帯2（4都県）は①②で概ね200リクエスト・3秒間隔で約10分

### 測っていないこと（承知のうえで進む）

- `rent_high` を送ったときの ①`roomCount` と ②`allCount` のずれ
  （②は `allCount` を信じる実装にして影響を避けてある）
- 住戸IDが全団地で一意か（3団地13住戸では衝突なし＝一意性の証明ではない。
  団地IDを前置しているので**衝突しても事故にならない**）
- **連続取得時のスロットリング・検知の有無。**
  ⚠ HOMES・ATHOME・NIFTY はいずれも**1リクエスト目が正常に返る**ので、
  単発では再現しない。本番間隔での観測は実装後に行う
