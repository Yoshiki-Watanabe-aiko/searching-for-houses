# スコアリング設計

**最終更新**: 2026-09-01（Phase 1）
**実装**: `src/house_search/scoring/` / **レジストリ**: `src/house_search/config/metrics.py`

MUST（未充足なら除外）＋ WANT（重み付き加点）の合計スコアで物件をランク付けする。

---

## 1. 入力（PropertyView）

採点は **ORM の行ではなく不変オブジェクト `PropertyView` を介す**。
これによりスコアが「DB保存済みの属性＋抽出済み features からの純関数」に保たれ、
`rescore` が**ネットワーク不要のDBバッチ**で完結する。

`detail_fetched` が False のときは設備が「未確認」であることを意味し、
WANT の設備項目は `miss` ではなく `unknown` になる（0点なのは同じだが、
通知に「未確認N項目」と出して判断材料にする）。

### 間取りの正規化

`1SLDK` → `1LDK`、`ワンルーム` → `1R`。
サービスルーム表記の `S` を無視するのは、**1SLDK は 1LDK に納戸が付いた形**で、
1LDK を許容するなら除外する理由がないため。

## 2. MUST判定（3値）

`pass` / `fail` / `unknown` の3値。**詳細ページの取得をスキップするのは `fail` のみ。**

| 判定 | 意味 |
|---|---|
| `pass` | 全項目が充足 |
| `fail` | 1つでも未充足。詳細取得もランキングも対象外 |
| `unknown` | 判定不能な項目がある。`must.unknown_policy` で `keep`/`drop` を選ぶ |

- 悪いほうが勝つ（1つでも `fail` があれば全体は `fail`）
- 必須設備は**詳細未取得なら `unknown`、取得済みで不足していれば `fail`**
- `list_stage_only=True` にすると `available_on_list=False` の項目を `unknown` にして、
  一覧だけで判定できる範囲に限定する（→ 2段判定）

⚠ **MUST項目名から metric 名を機械的に導かない。**
`area_min` → `area` になって取り違えるため、`_VALUE_METRIC` で明示的に対応づける。

## 3. WANTスコア

```
s     = clamp((worst - x) / (worst - best), 0, 1)
score = 100 × Σ(wᵢ × sᵢ) / Σ(wᵢ)
```

`best` と `worst` の大小関係が方向を表すので、`Direction` を別途参照する必要はない
（「低いほど良い」なら `best < worst`、「高いほど良い」なら `best > worst`）。

単位の異なる条件は `s` で無次元化されるため、**weight だけで相対優先度を表現できる**。

### 3.1 設備条件（feature）

該当すれば weight 満点。3状態を持つ。

| status | s | 分母 | いつ |
|---|---|---|---|
| `hit` | 1.0 | 含む | 抽出結果に条件コードがある |
| `miss` | 0.0 | 含む | 詳細取得済みで、条件コードが無い |
| `unknown` | 0.0 | **含む** | 詳細未取得（未確認） |

`unknown` を分母から外さないのは、**未確認のまま満点扱いにするほうが誤りが大きい**ため。
中間値の補完はしない。

### 3.2 `any_of`（排他グループ）

```yaml
- { any_of: [STRUCT_RC, STRUCT_SRC], weight: 6 }   # どちらか1つ満たせば満点
```

**同時に満たしえない条件へ別々に weight を振ると破綻する。**
RC と SRC にそれぞれ weight 6 を振ると、RC物件は「12点満点中6点」になる。
片方は必ず `miss` になるのに分母には両方が乗るため、
**全物件のスコア上限が構造的に下がり weight 予算が無駄になる**
（順位は壊れないが 0〜100点という数字の意味が濁る）。

`code` と `any_of` は排他で、`any_of` は2つ以上の異なるコードを要求する。
内訳・ソートで使う識別子は `"STRUCT_RC|STRUCT_SRC"` のようにコード昇順で安定させる。

### 3.3 数値条件（numeric）

**値が取れなければ欠損として分子・分母の双方から除外し、再正規化する。**
0点扱いにすると価格未定の新築マンションが不当に沈む。
内訳には `"missing": true` を記録する。

## 4. 種別ごとに使える metric

`MetricRegistry`（`config/metrics.py`）が一元管理し、YAMLは読み込み時に突き合わせて検証される。

| metric | 方向 | 賃貸 | 新築M | 中古M | 新築K | 中古K |
|---|---|:---:|:---:|:---:|:---:|:---:|
| `rent_total`（賃料＋管理費） | 低いほど良 | ○ | - | - | - | - |
| `price` | 低いほど良 | - | ○ | ○ | ○ | ○ |
| `monthly_cost`（管理費+修繕積立金） | 低いほど良 | - | ○ | ○ | - | - |
| `area_sqm`（専有面積） | 高いほど良 | ○ | ○ | ○ | - | - |
| `building_area_sqm` | 高いほど良 | - | - | - | ○ | ○ |
| `land_area_sqm` | 高いほど良 | - | - | - | ○ | ○ |
| `age_years` | 低いほど良 | ○ | - | ○ | - | ○ |
| `walk_minutes` | 低いほど良 | ○ | ○ | ○ | ○ | ○ |

- **戸建てに `area_sqm` を流用しない**（専有面積が存在せず土地・建物の2軸になる）
- **坪単価・㎡単価は metric にしない**（price と area に既に weight を配れる以上、
  二重に重みが掛かって解釈が濁る。`price_per_sqm` は表示用の派生カラム）

## 5. 決定性

**同じ入力からは必ず同じスコア・同じ内訳順序が出ること**を保証する。

- 設備は条件コード（`any_of` は結合キー）順、数値は metric 名順に**ソートしてから加算**
- 順位の同点は**物件IDの昇順**で決める
- `PYTHONHASHSEED` を変えたサブプロセス間で一致を検証する
  （`tests/test_scoring.py::test_スコアと内訳順序はPYTHONHASHSEEDに依存しない`）。
  同一プロセス内で2回回しても `set` の反復順は変わらないので検出できない

## 6. 説明可能性

`t_property_scores.score_breakdown`（JSONB）へ全項目を保存する。

```json
{"code": "SEC_AUTOLOCK", "name": "SEC_AUTOLOCK", "kind": "feature",
 "weight": 8, "s": 1.0, "points": 8.0, "status": "hit"}
{"code": "rent_total", "name": "賃料＋管理費", "kind": "numeric",
 "weight": 40, "s": 0.6, "points": 24.0, "status": "hit", "value": 58000}
```

- 即時通知: スコア・パターン内順位・得点上位3項目・未確認項目数
- ダイジェスト: 順位・スコア・価格・間取り/面積・市区・URL

## 7. 再スコアリング

スコア関連設定（`property_type` と `want`）のSHA256を `config_hash` として保存する。
**検索範囲や通知先を変えただけではハッシュは変わらない**ので、
無関係な変更で全件再スコアが走らない。

```powershell
uv run house-search rescore              # 全パターン
uv run house-search rescore --pattern "東京賃貸一人暮らし"
```

重みの調整はネットワーク不要でいつでもやり直せる。
`any_of` へまとめるかどうかもスコアの出方を変えるためハッシュに反映される。

## 8. 現行の重み配分（東京賃貸一人暮らし）

2026-09-01 ユーザー確定「案A バランス型 / 数値45%」。設定は `configs/chintai_alone.yaml`。

| 区分 | weight合計 | 比率 |
|---|---:|---:|
| 設備（22項目） | 110 | 55% |
| 数値（4 metric） | 90 | 45% |

上位: 室内洗濯機置場10 / バス・トイレ別9 / コンロ2口以上9 / オートロック8 /
洗面所独立7 / 宅配ボックス7 / エアコン6 / RC・SRC造6（`any_of`）

数値: `rent_total` 40（5万で満点・7万で0点）/ `area_sqm` 20（45㎡・30㎡）/
`age_years` 15（新築・築30年）/ `walk_minutes` 15（3分・20分）

**`worst` は MUST の上限／下限に一致させてある。** MUSTぎりぎりの物件は該当metricが
0点になり、余裕のある物件ほど加点される。

v1 で条件に挙げていた `FEAT_WITH_PHOTO` / `FEAT_WITH_LAYOUT` は **WANT から除外した**。
掲載の充実度であって物件の質ではなく、加点すると写真の無い優良物件が
平凡だが写真付きの物件の下に沈むため。
