# サイト別アダプタ（一覧・詳細の解析）の注意

CLAUDE.md の「実装上の注意」から領域別に分けたもの（→ CLAUDE.md の表）。
実際に踏んだ落とし穴なので、該当する処理を書く・直す前に読む。

- SUUMO の管理費・敷金・礼金欄の「-」は**0円**の意味。`None` にすると
  `rent_total` が「管理費不明」になり MUST 判定が `unknown` に落ちる
- **詳細ページに「非該当」条件を並べるサイトがある**（HOMES の `sr-only`、goo の `td` が `-`）。
  そのまま `raw_features_text` に載せると辞書が非該当の条件を拾う
- ⚠ **一覧の DOM が同じでも詳細ページは別物でありうる**（→ 課題#4）。SUUMO 新築マンションは
  一覧では棟（プロジェクト）と個別住戸が**完全に同じ DOM**なのに、**詳細は見出しクラスも
  項目数も違う**（棟は設備ブロックが無く `th`/`td` が9項目だけ）。
  ⚠ **棟の h2「建物の特徴」は広告のキャッチコピー**なので、設備原文に入れると
  **その棟に無い設備が拾われて設備数が黙って水増しされる**。
  ⚠⚠ **設備の見出しクラスで絞ってはいけない**（→ 課題#4・2026-09-09）。詳細ページは
  **テンプレートが2種類**あり、同じ物件種別でも `h3.secTitleInnerR` と
  `h3.secTitleInnerK` が混在する（実測12件・中古K/中古M/新築Kのいずれでも両方あった）。
  ⚠ **種別では決まらない**——「中古は R・新築マンションは K」は種別ごとに1件ずつ
  観測した誤った一般化で、**実データの多数派は K** だった。
  ⚠ **外しても「原文が空になるだけ」で例外にならず件数も減らない**（築年月・管理費は
  付くので詳細ページ自体は読めている）。実測で原文が付いていたのは中古K 17%・
  中古M 23%・新築K 44% で、設備 weight 50〜60 ぶんが構造的に沈んでいた。
  クラスではなく**見出しの文言**（「特徴ピックアップ」「設備仕様」）で拾う
- ⚠ **地番を住居表示として扱わない。** SUUMO 新築の棟は所在地が
  `板橋区板橋１-3001、3002（地番）`。残すと実在しない住所として正規化されうる
  （→ ADR 0020 の番地誤認と同型）
- **能動的なボット検知は突破しない。** MINIMINI は reCAPTCHA（課題#18・**素のブラウザでも通らない**）、
  HOME'S は AWS WAF（課題#17）、ATHOME はパズル認証（課題#20）、
  **NIFTY は「Human Verification」を HTTP 405 で返す**（課題#38・**405 はメソッド不許可ではない**）。
  ⚠ **検知ページは HTTP 200 で返る。** そのまま解析すると掲載0件になるだけでエラーにならず
  「取れているつもり」で気づけないので、判別できるサイトはアダプタが例外にする
- **UR賃貸は3段のJSON API（POST）**。①団地一覧 ②住戸一覧 ③住戸詳細。
  ⚠ **①と②でページ送りの有無が逆**（①は `pageIndex` を黙って無視して全件返し、
  ②は1ページ5件で末尾を超えると **`null`** を返す。空配列ではないので反復すると `TypeError`）。
  ⚠ **②と③は同じキー名でも中身が違う**（③は `type`/`floorspace`/`commonfee` が `None` で
  `madori`/`madoriYuka`/`commonfee_sp` に入る）。
  ⚠ **割引適用の住戸は `rent` が空文字で賃料が `rent_normal` に入る。**
  見落とすと `price` が NULL → MUST が `unknown` へ落ち、
  `unknown_policy: keep` の下で**賃料不明の掲載がランキングに並ぶ**（例外にならない）。
  ⚠ **市区で検索できない**（UR独自の `area=01..` しか無い）ので、都県の全 area を取って
  応答の `skcs`（市区名）でローカルに絞る。`skcs` は政令市で行政区まで入り
  `m_cities.canonical_name` と同表記
- **UR の交通欄はバス経由が半数。** その「徒歩◯分」は**バス停からの徒歩**なので
  駅徒歩にすると `walk_minutes_max` を不当に通過する。⚠ ただし1行に
  `徒歩16～19分 または バス3分 徒歩2～5分` と並ぶ形があり、**行ごと弾くと
  本物の駅徒歩を捨てる**。「または」で選択肢に割ってから1つずつ見る。
  ⚠ 徒歩がレンジなのは団地に棟が複数あるため（下限を採る）
- ⚠⚠ **SUUMO 売買の一覧は新着・更新順（`?po=1&pj=2`）で取る**（→ 課題#4・2026-09-07）。
  既定順は1ページ目に新着が **1/20** しか載らず、増分スキャン（1ページ目だけ）が
  新着を**黙って取りこぼす**。`po=1&pj=2` で 20/20 が新着になる（総件数は不変）。
  ⚠ 賃貸の `sort=` は robots が禁じるが売買の `po`/`pj` は当たらない（実 robots で固定）。
  ⚠ ページ送りは `&page=N`（`?` を重ねると page が黙って無視される）
- ⚠⚠ **権利形態の判定は `scrape.base.leasehold_flag` の1箇所で行う**（→ 課題#65）。「借地」の語だけを
  見ると `賃借権（旧）、2025年9月29日～…`・`地上権（旧）、新規20年` を所有権として通す（例外にならない）。
  売買4本の「所有権のみ」（`freehold_only`）は `type_specific_attrs` の原文（`敷地の権利形態`・
  `土地の権利形態`・`販売期の権利形態`）から**採点のたびに導く**ので、規則を直したら `rescore` だけでよい。
  ⚠ 新築マンションの**棟は詳細に権利形態の欄が無く**、一覧の販売期の注記で借地だけが分かる
  （注記が無いことは所有権の証拠にしない＝unknown → keep）
- ⚠⚠ **土地の「建築条件付きを除く」（`exclude_build_condition`）は `scrape.base.build_condition_of` で導く**
  （→ 課題#61・2026-09-15）。原文 `建築条件` があれば原文から、無ければ保存済みの `build_condition` へ落とす
  （⚠ アダプタは `-` を原文として残さない）。グループの1件でも付なら付。
  ⚠ `一部建築条件付`（区画分譲・23件）は None（unknown → keep）。⚠ 同じ区画を「条件付きで安く／条件外しで高く」
  の2掲載で出す形があり、代表（最安）が条件付きだと条件外しの選択肢もグループごと消える（既知の限界）
- ⚠⚠ **SUUMO 土地のアダプタ（`suumo_tochi.py`）を戸建ての派生にしない**（→ 課題#61）。戸建ては
  新築の索引に混ざる `/tochi/` を**捨て**、土地は `/tochi/` **だけ**を採る。継承すると0件になるだけで
  例外にならない。⚠ **建築条件付きは詳細の仕様表の「建築条件」欄（`付` / `-`）で判定する**（一覧の
  本文には `建築条件なし` のタグや購入サポートのバッジが混ざる）。⚠ 未知表記は**全ファミリの辞書**と
  照合されるので、他ファミリの辞書にある語（角地・都市ガス）は土地の未知表記に出ない。土地の辞書を
  育てるときは `report-unknown` だけでなく `raw_features_text` を直接数える
- 面積の単位は ㎡（U+33A1）・m²・`m<sup>2</sup>` とばらつく。
  `parse_area_sqm` は NFKC 正規化してから読む
- ⚠ **金額も NFKC 正規化してから読む**（→ 課題#51）。正規表現の `\d` は全角数字に
  マッチするが `\.` と `[,]` は**半角しか受けない**ため、全角の区切りを含むと
  **例外にならないまま値だけが狂う**（`３，０００円` → **0** /
  `１４．３万円` → 30,000 / `１．５ヶ月` → **5ヶ月分**）。
  ⚠ とくに管理費0円は `rent_total` にそのまま足されて MUST を通る
  （`None` なら unknown に落ちるのに）。面積だけ正規化していた非対称が原因
- ⚠⚠ **金額は上位の単位だけを拾って下位桁を落とさない**（→ 課題#4・課題#53）。
  同じ欠陥を2度踏んでいる（`1億2,800万円` → **28,000,000** /
  `1万3020円` → **10,000**）。⚠ **NULL なら気づけるが「それらしい値」が入るので、
  例外にも件数の減少にもならないまま MUST を通って順位だけが狂う。**
  ⚠ **正規表現を増やして「どちらを先に試すか」で解こうとしない**——
  順序は合っていたのに次の単位の組を見落としたのが課題#53 の原因。
  億・万・円は**ひとつの正規表現の中で連結して読む**
- ⚠ **一覧に返る掲載が実行のたびに入れ替わるサイトがある**（CHINTAI.net）。
  同じURLを続けて取っても中身が違うので、GOO・APAMAN・ATHOME で使った
  「返る掲載の中身でフィルタの効きを確かめる」が**通じない**。
  **総件数の表示だけが安定した判定材料**になる。⚠ 並び順を指定しても揺れは止まらず、
  決定的な「安い順」は棟あたり最安1住戸しか返さないので母集団が半減する
  （ハウスコムの `?sort=0` と同じ）。⚠ **新着を確実に拾うことはできない**
- ⚠ **hidden input の数値は「生値」なので `parse_yen` が読めない。**
  CHINTAI.net の `chinRyo` は `118000`（円）で、`parse_yen` は「円」の字を要求するため
  **None を返す**。素朴に書くと**全件 price が NULL** になり、`rent_total` が NULL →
  MUST が `unknown` → `unknown_policy: keep` の下で**賃料不明の掲載がランキングに並ぶ**。
  ⚠ **例外にならないので実データで動かすまで気づけない**（UR の割引住戸と同じ形）
- ⚠ **設備欄に「用語集の解説文」が展開されるサイトがある**（CHINTAI.net の
  `.detail_specTable`）。「システムキッチン…レンジフード…」「IHクッキングヒーターよりも
  火力が強い」のように**その住戸に無い設備名**が本文に出てくる。辞書照合は部分一致なので
  **設備数が黙って水増しされる**（HOMES の `sr-only` と同型）。タグ列だけを使う
- **1ページしか見ないサイトを賃料の安い順に並べると、構造的に最小の部屋しか見えない。**
  ATHOME は市区ローテーションで1ページ目だけを見るため、23区帯では30㎡未満の
  1K/1R ばかりが返り MUST 1段目の通過が0件だった（→ 課題#39）。面積下限を
  サイト側へ渡して解消した。HOMES が新着順（`cond[sortby]=newdate`）なのは同じ理由。
  ⚠ 同じ制約を持つ SMOCCA（1ページ90件 → 課題#22）にも当てはまる論点
- ⚠ **交通欄は「徒歩表記から切り出す」のではなく DOM の専用要素から取る。**
  本文を「◯◯駅まで徒歩N分」で探して切り出すと、**その形を持たないバス便が交通欄ごと落ちる**
  （ホームメイト `東武バス 東金町五丁目停まで徒歩3分、バス乗車してＪＲ常磐線 金町駅まで17分`。
  実測で236掲載中45件＝19% → 詳細設計書 §13.10）。⚠ **駅も同定できず通勤時間が unknown になる**が
  例外にならない。⚠ **分母を「交通欄が取れた掲載」にすると98.4%で健全に見える**ので、
  同定率は**掲載全体**を分母に測る（課題#41 と同じ形）。
  ⚠ **バス便を含まないフィクスチャでは検出できない**（足立区の25棟は全件が駅徒歩型だった）
- **アダプタは `station_info` に「駅」を残す。** 落とすとアンカーが消えて同定できない
- ⚠ **`station_info` の空白を落とさない。** `matcher` は鉤括弧の囲みを外してから
  「駅」の左を遡るので、路線名との間に区切りが無いと**路線名ごと駅名にしてしまう**
  （`常磐緩行線「綾瀬」駅徒歩8分` → `常磐緩行線綾瀬`）。実在しない駅名になるので
  マスタに当たらず**通勤時間が unknown になるだけで例外にならない**。
  住所の空白は落としたい（他サイトと表記を揃えて `dedup_key` を一致させる）ので、
  **落とす対象を項目ごとに分ける**（D-room で実際に踏んだ）
- **築年月が取れないサイトは `t_listings.age_years` へ渡す**（`ScrapedDetail.age_years`）。
  UR の API は築年月ではなく**築年数**（`year`）を返す。`type_specific_attrs` に置くだけでは
  採点から見えず、weight 15 が永久に unknown になる
