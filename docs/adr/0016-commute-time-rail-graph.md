# 通勤時間は駅データ.jp の接続情報から自前で算出する

**状態: 採用（2026-09-03・Phase 5C）**
**関連: [ADR 0013](./0013-area-bands.md)（エリア帯）／課題#24・#31**

ランキングに立地の観点を入れる。スコアには賃料 40・面積 20 の重みがある一方、
**どこに住むかには1点も配点されておらず**、上位が「安くて広い郊外」で埋まっていた
（課題#24）。エリア帯の導入で相場の違う範囲を混ぜる問題は解けたが、
**帯の中でどこが通いやすいか**は依然として順位に反映されない。

---

## 前提が実測で覆った

当初の方針は「Google Maps Routes API（TRANSIT）で駅ペアを1回計算してDBキャッシュ」
だった。APIキー・課金設定まで済ませ、クライアントを実装して叩いたところ、
**HTTP 200 のまま本文が `{}` になり続けた**。

| 呼び出し | 結果 |
|---|---|
| Routes API TRANSIT・川崎→芝公園 | `{}` |
| Routes API TRANSIT・新宿→大手町 | `{}` |
| **Routes API TRANSIT・タイムズスクエア→ウォール街（米国）** | **`{"routes":[{"duration":"1275s"}]}`** |
| Routes API **DRIVE**・川崎→芝公園 | `{"routes":[{"duration":"1820s"}]}` |
| レガシー Directions API・新宿→大手町 | `REQUEST_DENIED`（キーのAPI制限） |

**同じキー・同じ座標で米国の TRANSIT は動き、日本だけ空**になり、日本でも DRIVE なら返る。
公式の [Map coverage details](https://developers.google.com/maps/coverage) にも日本は
driving / walking しか無く transit の欄が存在しない（「公共交通の経路は一覧に載らない」と注記）。
Directions API でも[日本は ZERO_RESULTS になる報告](https://discuss.google.dev/t/directions-api-transit-mode-returns-zero-results/378267)がある。

代替として調べた駅すぱあと API は、**フリープランに経路探索が含まれない**
（確認用URLのみで所要時間の数値が取れない）。有料プランは月額契約が要る。

⚠ **この事象は「200 で返る失敗」の4例目**である（SUUMO のエラーページ・
ATHOME の認証ページ・課題#29 の無効パラメータに続く）。`{}` を `no_route` として
**明示的に記録する**設計にしていたため、3件取得した時点で異常に気づけた。
握りつぶしていれば「通勤時間が全件 unknown」のまま完了と report していた。

---

## 決定

**駅データ.jp の駅間接続情報（`join*.csv`・10,189リンク）をグラフとして扱い、
ダイクストラで経路を求め、距離と乗換回数から所要時間を回帰式で見積もる。**

### モデル

| 要素 | 内容 |
|---|---|
| ノード | 駅（`station_cd`。路線ごとに別ノード）＋ 乗換用のグループ仮想ノード |
| 乗車の辺 | 隣接駅。重みは「直線距離 × 迂回係数 1.15 ÷ 表定速度 35km/h」 |
| 乗換の辺 | 同一 `station_g_cd` の駅どうしを仮想ノード経由で結び 5分のペナルティ |
| 探索 | 目的地からの単一始点最短路。**全国8,743グループが1回・0.1秒**で出る |
| 所要時間 | `8.7 + 1.14 × 距離km + 5.6 × 乗換回数`（分） |

**経路の選び方と所要時間の見積もり方を分けている。** 前者は相対比較にしか使わない重み、
後者が実測で校正した回帰式である。

### なぜ一律の表定速度では駄目なのか

⚠ **距離が伸びるほど過大になる。** 優等列車（快速・急行）を表現できないため。

| | 平均誤差 | 最大誤差 |
|---|---:|---:|
| 一律35km/h（無補正） | 18.2分 | **72.0分** |
| 単純スケーリング（×0.713） | 6.7分 | 19.9分 |
| **距離＋乗換＋定数（採用）** | **5.6分** | **16.0分** |
| 距離＋√距離＋乗換＋定数 | 4.8分 | 13.4分 |

4パラメータ版のほうが当てはまりは良いが、12サンプルに対して過学習であり、
定数項が −14.9 と解釈できない値になるため採らない。採用した3パラメータは
すべて現実的な意味を持つ（1kmあたり1.14分＝実効52km/h、乗換5.6分、初乗り待ち8.7分）。

### 係数の校正

NAVITIME の乗換案内から**実測12ペア**（芝公園ゆき・2026年9月9日(水) 08:30発）を採り、
最小二乗で決めた。robots.txt は経路検索のパスを禁じておらず（`Disallow` は `/ja`・
`/affi`・`/pcstorage/cntlog` のみ）、ClaudeBot 向けの `Crawl-delay: 10` に合わせて
11秒間隔で12件だけ取得している。継続的な取得はしない。

⚠ **NAVITIME の月指定は `2026/09` 形式**。`202609` を渡すと**黙って無視され現在時刻**で
検索される。最初の取得は深夜に走ったため全件が始発帯（04:28〜05:28発）の値になっていた
（横浜→芝公園が46分。朝08:30なら42分）。**これも例外にならない類の誤り**である。

## 何を諦めたか

- **実ダイヤを反映できない。** 急行・直通運転・待ち時間・混雑は式に入らない
- **新幹線が使えない。** 駅データ.jp 無料版は新幹線の駅を1件も収録していない
  （路線は `line` に存在するが駅が0件）。本庄早稲田のような新幹線専用駅は同定できない
  （実測48件・いずれもエリア帯の外）
- **完了条件を変えた。** 当初の「サンプル10駅ペアで実測と±5分以内」は
  Google の実データを前提にしていた。自前計算では平均5.6分・最大16.0分になるため、
  **「上位15件が通勤の実感と合うか」**で判定する

**求めているのは順位付けに足る精度**であって分単位の正確さではない。
課題#24 の「立地の観点が無い」を埋めるには十分と判断した。

## 同名駅の曖昧さをどう扱うか

掲載の駅表記から駅を同定するとき、同名の駅が複数あると一意に決まらない。

- **都道府県で絞る**と激減する。1都3県をまとめて引くと「小川町」（埼玉/東京）
  「霞ケ関」（埼玉/東京）「永田」（千葉/埼玉）「平和台」（東京/千葉）「入谷」（東京/神奈川）が
  すべて曖昧になるが、掲載の所在地で絞れば一意に決まる（実測で ambiguous 168件→23件）
- **残る曖昧さは路線名でも座標でも解決しない。** 都道府県で絞った後に残るのは
  浅草・早稲田・弘明寺の3組（10,322掲載中23件・0.2%）で、いずれも徒歩数分の距離にある
  同名駅である。同じ掲載の別の駅で補えることが多く、実装コストに見合わない

同定率は **99.4%**（10,259/10,322掲載）。

## 採点への配線

| 項目 | 内容 |
|---|---|
| MUST | `commute_minutes_max`（両帯とも60分）。`available_on_list=False` なので一覧では判定せず、未解決は unknown |
| WANT | `commute_minutes` weight 25。`walk_minutes` を 15→10 に下げて捻出した |
| best/worst | **帯ごとに母集団の分布へ合わせる**（帯1: 20〜45分 / 帯2: 35〜60分） |

⚠ **best/worst を MUST の上限に機械的に合わせない**（課題#31 の教訓）。
帯1の母集団は 18〜47分なので、worst を 60分にすると全件が上半分に固まり
weight 25 が死ぬ。実測で**両帯とも0点張り付きは0件**になることを確認した。

⚠ **通勤時間はグループ内の最短を採る**（設備の和集合と同じ考え方）。
サイトによって挙げる駅が違うため、名寄せしたグループ全体から拾わないと情報が減る。

## 駅マスタをGit管理下に置けない

設備抽出辞書（`data/feature_dictionary.yaml`）とサイト検索パラメータ
（`data/site_search_params.yaml`）は Git管理YAMLを正典にして差分レビューできるが、
**駅データ.jp のCSVは再配布不可**なのでそれができない。

`data/train_master/` を `.gitignore` し、README だけを追跡している。
`sync-stations` というコマンドの形は他の正典と揃えたが、
**「正典の変更履歴が追えない」点だけが先例と異なる**。再取得の手順は README に書いた。

⚠ 駅の接続情報（`join*.csv`）は `resolve-commutes` と `scan` が実行時に読む。
CSVが無い環境では通勤時間を更新できないので、`scan` はエラーとして記録したうえで
**処理を止めない**（通勤時間が unknown になるだけ）。
