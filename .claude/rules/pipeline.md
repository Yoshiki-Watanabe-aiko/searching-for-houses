# 一覧の保存・詳細キュー・任意フックの注意

CLAUDE.md の「実装上の注意」から領域別に分けたもの（→ CLAUDE.md の表）。
実際に踏んだ落とし穴なので、該当する処理を書く・直す前に読む。

- **`m_sites.is_active = false` のサイトは通常の `scan` では取りに行かない。**
  `--site` で名指ししたときだけ動く（賃貸EX の観測モードの入口）
- **GET＋HTML の枠に収まらないサイトは任意フックで委譲する**（→ ADR 0019）。
  `pipeline.scan` が `collect_listings` / `fetch_detail` の宣言を `getattr` で見て、
  **一覧の収集／詳細の取得だけ**を差し替える。MUST 1段目・upsert・詳細キュー・
  `--detail-limit`・設備抽出・名寄せは既存経路を通る。
  ⚠ **`SiteScraper` Protocol にメソッドを足さない**（既存10アダプタに実装義務が生じる）。
  ⚠ **フックに「一覧＋詳細」を対で返させない**（`--detail-limit` が効かなくなる）
- ⚠⚠ **一覧の UPSERT は種別が違う既存行を更新しない**（`ON CONFLICT … WHERE` → 課題#61・#62）。
  一意キーが `(site_id, external_id)` なので、無いと既存行を別の種別の値で上書きし種別は元のまま残す
  （SUUMO は新築と中古で `nc_` を使い回す。本番で新築マンション80位が中古の値で採点されていた）。
  ⚠ **同じファミリで既存行が掲載終了（sold / removed）なら、新しい種別で引き継ぐ**
  （`persist.classify_existing` → `_RETAKE`。旧種別の値・設備・採点を消し、「再掲載」として新着を出す）。
  ⚠ ファミリ違いは掲載終了でも引き継がない。⚠ `t_listings` に列を足したら `RETAKE_*_COLUMNS` の
  どれかへ入れる（テストが全列の分類を固定している。入れ忘れると旧種別の値が黙って残る）
- ⚠ **詳細ページ由来の項目は、パーサを直しても既存データが直らない。**
  詳細キューは `detail_fetched_at IS NULL` の行しか拾わないので、**取得済みの掲載は
  二度と再取得されない**（一覧由来の項目は毎回の upsert で上書きされるので直る）。
  ⚠ 設備（`re-extract`）・経路（`re-segment`）と違い、**住所・交通欄には
  保存済み原文から作り直す仕組みが無い**。直すには該当行の `address` と
  `detail_fetched_at` を NULL にして取り直させる（2026-09-05・ホームメイト → 課題#44）。
  ⚠ **`COALESCE(EXCLUDED.x, t_listings.x)` なので、一覧側の修正でその項目が NULL に
  なるケースでも古い値が残る**（この形は実データでは未確認）
- ⚠⚠ **詳細キューを「新しい順」だけで引かない**（→ 課題#54）。新規流入が
  上限（既定40件/回）に近いと**古い掲載に枠が永久に回らない**。実測で SUUMO の
  1,342件が3日ぶん滞留し、**設備0件のまま順位が付いていた**（近郊帯4位＝ダイジェスト）。
  ⚠ **例外にならず件数も減らない**——設備は miss＝0点で分母に残るので、
  weight 118/263 ぶん**静かに沈むだけ**。「古い順に枠の半分」との和集合で引く。
  ⚠ **並べてから切る**（素朴に和集合を作って `LIMIT` すると古い側が落ちる）
- ⚠ **「再取得された」と「修正後のコードで再取得された」を取り違えない。**
  `last_seen_at` はコードの版を教えてくれない。デプロイ時刻と突き合わせること
  （2026-09-05 に実際に誤診した → 課題#44）
- **`refresh_dedup_keys` は一覧の upsert 直後と詳細の保存後の両方で呼ぶ。**
  階数・住所は詳細ページで初めて埋まる掲載があり、片方だけだとキー充足率が上がらない
