# 設備抽出辞書設計

**最終更新**: 2026-09-01（Phase 1）
**実装**: `src/house_search/extract/` / **辞書**: `data/feature_dictionary.yaml`

サイト側の検索フォームで絞り込む代わりに、詳細ページ本文から**全サイト同一の判定器**で
設備を取り出す（→ [ADR 0003](../adr/0003-local-filtering.md)）。

---

## 1. パイプライン

```
詳細ページ
  ↓ サイトアダプタ（設備ブロック＋構造化フィールドの正規化）
t_properties.raw_features_text   ← 原文のまま保存（HTML全体は保存しない）
  ↓ NFKC正規化 → 小文字化 → 辞書照合
t_property_features              ← 抽出結果
  ↓ どのパターンにも当たらなかったトークン
t_unknown_tokens                 ← 辞書育成の入力
```

**原文保存が要。** 辞書を改善したら再スクレイピングせず、DB内の原文から
`house-search re-extract` で全件やり直せる。これがないと辞書運用が回らない。

---

## 2. 辞書の持ち方

**Git管理YAML（正）→ `sync-dict` で `m_condition_synonyms` へ同期**。
Git履歴でdiffレビューでき、実行時はDB参照でJOINできる。

```yaml
version: 1
chintai:                       # 賃貸ブロック
  SEC_AUTOLOCK:
    patterns: ["オートロック"]
    negative_patterns: ["オートロックなし", "オートロック無"]
    site_overrides:
      SUUMO: ["オートロック付"]
common:                        # 共通ブロック（賃貸＋売買の3ファミリへ展開）
  EQUIP_ELEVATOR:
    patterns: ["エレベーター"]
buy: {}                        # 売買固有ブロック（証明書・性能評価系）
```

- **`chintai` / `common` / `buy` の3部構成**（→ 課題#4・Phase 6 手順5）。
  設備の語彙は賃貸と売買でほぼ共通なので、実測で**賃貸辞書の30条件が売買の設備原文に
  ヒットした**。共通のものは `common` に置き、CHINTAI / MANSION_BUY / KODATE_BUY の
  3ファミリへ展開する。`buy` は売買固有の語彙（証明書・性能評価系）だけ
- ⚠ **どのセクションに置くかは人が選ばない。** `m_condition_property_types` が
  マンション売買にも紐づけているかで機械的に決まる（2026-09-06 実測で `chintai` 83条件の
  うち **58条件**が該当）。⚠ `buy` へ表記をコピーする案は採らない——同じ語を2箇所で
  保守することになり、**賃貸側を直したとき売買側が黙って古くなる**
- ⚠ **戸建てに紐づかない16条件（エレベーター・角部屋・RC/SRC 等）も `common` から
  KODATE_BUY へ展開される**が許容する。①戸建ての原文にその語が出ることは稀
  ②`want.features` に書かなければ採点に影響しない ③戸建て売買は未取得（Phase 8）。
  先回りして `chintai_mansion:` のような組合せセクションを作ると、
  ファミリの組合せぶんセクションが増えて破綻する
- ⚠⚠ **`m_condition_synonyms` の一意性制約に `property_family` を含める。**
  外すと同じ表記を2ファミリへ入れた時点で `sync-dict` が UniqueViolation で落ちる。
  ⚠ **`buy` が空だった間は表面化しなかった**（複数ファミリ展開は Phase 6 手順1 から
  実装されていたが、実際に流したのは 2026-09-06 が初めて）
- パターンは**読み込み時に照合と同じ正規化を通す**ので、全角/半角・大文字小文字を
  気にせず自然な表記で書いてよい
- 同期は**完全同期**（YAMLに無い行は削除）。差分追加だけにすると辞書から外した
  パターンがDBに残り続け、YAMLのdiffレビューが意味を失う
- マスタに無い条件コード・サイトコードはその行を捨てて**警告し、終了コード1で終わる**
  （黙って落とすと辞書の綴り間違いに気付けない）

Phase 1 初版: **80条件 / 257パターン**（賃貸）。

## 3. 照合の仕組み

### 3.1 本文全体への部分一致

照合は**正規化済みの本文全体への部分一致**で行う。トークンに切ってから照合しない。

サイトによって区切り文字が「、」「／」「・」とばらつくため、
中黒で切ると「バス・トイレ別」「敷金・礼金不要」「BS・CS」のように
**語そのものに区切り文字を含む条件を取りこぼす**。
トークン化は未知表記の収集にだけ使う。

### 3.2 否定パターン

肯定パターンより**否定パターンを先に見る**。1つでも当たったらその条件は不成立。

⚠ **部分文字列の包含関係に注意。** 「src造」は「rc造」を部分文字列に含むため、
`STRUCT_RC` の否定に `src造` / `鉄骨鉄筋コンクリート` を入れないと
SRC物件が RC としても抽出される。`any_of` でまとめていても、両方 hit すると
内訳の説明が誤りになる。

### 3.3 正規化

`NFKC` → 小文字化 → 空白圧縮。`ＴＶ`→`tv`、`18㎡`→`18m2`、`ｵｰﾄﾛｯｸ`→`オートロック`。

## 4. 型付き列からの導出（DERIVED）

**閾値条件は文字列照合では表現できない**ため、型付き列から直接判定する。

| 条件 | 導出元 | 判定 |
|---|---|---|
| `LOC_FLOOR_1` | `floor_num` | `== 1` |
| `LOC_FLOOR_2UP` | `floor_num` | `>= 2` |
| `LOC_TOP_FLOOR` | `floor_num` / `total_floors` | 一致かつ `total_floors > 1`（平屋は除く） |
| `FEAT_NEW` | `age_years` | `<= 3` |

`t_property_features.source` に `DERIVED` を記録する。
辞書照合の結果と `merge_features` で統合し、**導出を先に渡して優先させる**
（`LOC_TOP_FLOOR` は「最上階」というタグでも取れるが、列からの判定のほうが確実）。

## 5. 未知表記の運用ループ

```
house-search report-unknown        # 出現回数順に一覧
  ↓ data/feature_dictionary.yaml に追記
house-search sync-dict             # DBへ反映
house-search re-extract            # 既存物件に反映（ネットワーク不要）
```

トークン化は「、」「,」「/」「／」「｜」「;」「改行」で切る（**中黒は切らない**）。
2〜40文字で、数字・記号だけでないものを記録する。

**辞書のどのパターンにも当たらず、かつどのパターンの部分文字列でもないもの**を未知とする。

実測の例（2026-09-01・SUUMO 36物件）: `全居室6畳以上` / `陽当り良好` / `洗面化粧台` /
`クロゼット` / `シャワー付洗面台` / `閑静な住宅地` など。
これらは**148条件のマスタに対応する条件が存在しない**ため未知のまま残る。
条件そのものを増やすかは運用しながら判断する。

## 6. 辞書で扱わないもの

| 対象 | 理由 |
|---|---|
| `LOC_FLOOR_1` / `LOC_FLOOR_2UP` / `FEAT_NEW` | 閾値条件のため列から導出（§4） |
| `FEAT_WITH_PHOTO` / `FEAT_WITH_LAYOUT` / `FEAT_TODAY_NEW` | 掲載メタ情報であり本文に現れない |
| `NEARBY_*`（コンビニ400m以内 等） | 距離計算が要る。Phase 1 では対象外 |
| `AREA_*` / `PRICE_RENT_MIN/MAX` 等 | 検索軸そのもので設備ではない（`is_extractable=false`） |
