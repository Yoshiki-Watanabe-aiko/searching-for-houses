# サイト側フィルタを MUST に限って復活させる

**状態: 採用（2026-09-03・Phase 5B）**
**関連: [ADR 0003](./0003-local-filtering.md) を**補強**（撤回しない）／課題#29**

ADR 0003 は「サイトに渡すのはエリア・物件種別・価格上限の3つだけ。判定と採点は
すべてローカル」と決めた。この決定は**いまも正しい**が、**射程を広く取りすぎていた**。

---

## ADR 0003 が本当に禁じているもの

ADR 0003 の論拠はこうだった。

> WANT条件（オートロック無しでも減点で残ってほしい）をサイト側フィルタに渡すと、
> 対応サイトでは物件が除外されて順位に現れず、非対応サイトでは素通りする。

これは **WANT についての議論**である。WANT は「満たさなくても対象から外れない」
条件なので、サイト側で落とすと定義そのものが壊れる。

**MUST は違う。** MUST を満たさない掲載は、ローカルで `fail` と判定され
**DBにも入らず採点もされない**（2段判定・→ 再設計計画 §3.2）。
サイト側で落としても結果は1件も変わらない。変わるのは取得量だけである。

---

## 決定

**MUST の数値条件と間取りに限り、サイト側のフォームへ渡してよい。**

### 渡してよいもの

| 軸 | 丸めの向き |
|---|---|
| `area_min` | 切り下げ（緩める） |
| `area_max` | 切り上げ |
| `walk_minutes_max` | 切り上げ |
| `age_max` | 切り上げ |
| `layouts` | 全項目を表現できるときだけ送る |

### 渡してはいけないもの

- **`must.features`（設備条件）は永久に送らない。** 辞書抽出とサイトのタグ付けは
  判定が食い違い、こちらが `unknown` として残したい掲載をサイトが落としてしまう。
  MUST の `unknown_policy: keep` が機能しなくなる
- **WANT は一切送らない**（ADR 0003 のとおり）
- **賃料上限は軸にしない。** `search.price_max_hint` の経路が既に担っており
  （課題#29 を修正済みの実績がある）、軸を足すと同じURLパラメータに供給源が2つできる。
  バッファ幅の判断をユーザーの手に残す意味もある

### 丸めの向きは軸から機械的に決める

サイトへ渡す値は必ず「ローカルのMUSTと同じか、より緩い」集合を返さなければならない。
判定の正はローカルにあり、サイト側フィルタは母集団削減の最適化にすぎないからである。

向きをサイトごとの定義に持たせると必ず間違えるので、`scrape/params.py` の
`AXIS_BOUND` で軸ごとに1回だけ決める。**サイト定義には書けないようにしてある。**

⚠ 逆向きに丸めると掲載を取りこぼすが、**取りこぼしは例外にならず件数が減るだけ**
なので、実データを見ても気づけない。ユニットテストで「丸めた値は必ず要求より緩い」
ことを固定している。

### 正典は Git 管理の YAML、実行時はDB

`data/site_search_params.yaml` を正典とし、`sync-site-params` で
`m_site_search_params` へ同期する。設備抽出辞書（`feature_dictionary.yaml` →
`m_condition_synonyms`）と同じ構成である。

実測値の変更をdiffレビューできること、実行時にDBから引けることの両方が要る。

### 既定は無効。パターンごとに明示的に有効化する

```yaml
search:
  site_filters:
    enabled: true
    axes: ["area_min", "walk_minutes_max", "layouts"]
    exclude_sites: []
```

⚠ **`enabled: false` に戻せば全サイトが即座に従来の動作へ戻る。**
無効値の事故（後述）が起きたときの一次対応がこれである。

## 無効値を渡すと HTTP 200 のまま0件になる

これが本ADRの最大のリスクで、課題#29 そのものである。

実測（2026-09-03・SUUMO 足立区）:

| 送った値 | 結果 |
|---|---|
| `et=10`（選択肢内） | 41,405件 |
| **`et=12`（選択肢に無い）** | **`title` が「エラー｜SUUMO(スーモ)」の11KBのページを HTTP 200 で返す。掲載0件** |
| `zzz=1`（存在しないキー） | 62,030件のまま。**黙って無視される** |

つまり誤りには3つの現れ方があり、**どれも例外にならない**。

1. 値が選択肢外 → 0件（またはエラーページ）
2. キーが存在しない → 何も起きない（絞れていないことに気づけない）
3. 不等号の向きが逆 → 全く違う集合が返る

### 対策

| 層 | 内容 | 状態 |
|---|---|---|
| 丸めの型付け | 選択肢を外す値をそもそも作れないようにする。プロパティ的なテストで固定 | ✅ 実装済み |
| エラーページの例外化 | SUUMO のエラーページを `parse_list` が判別して例外にする。`scan` は1ページの失敗でサイトを止めないので、エラーとして記録され実行サマリに出る | ✅ 実装済み |
| 実測での確定 | キー名・選択肢・不等号の向きを**実サイトで測ってから** YAML に書く。「存在しないキーは件数が変わらない」ことを先に確かめ、判定方法自体の妥当性を担保する | ✅ 実施済み |
| 対照取得 | 一覧が0件だったとき、その場でパラメータを外して1回だけ取り直し、対照が0件でなければ例外にする | ⏳ **未実装**（残作業） |
| 連続0件のバックストップ | サイト完了時に「過去に取れていたのに今回0件」ならエラーチャンネルへ警告 | ⏳ **未実装**（残作業） |

⚠ **上2層だけでは、SUUMO 以外のサイトを足したときに守れない。**
エラーページの判別はサイトごとに書く必要があり、判別できないサイトもある。
残る2層は他サイトの配線と同時に入れる。

---

## 代替案と、採らなかった理由

| 案 | 却下理由 |
|---|---|
| ADR 0003 を撤回して WANT も渡す | ランキングが成立しない。ADR 0003 の論拠はいまも正しい |
| 現状維持（何も渡さない） | 実測で母集団が57%削減できることが分かっている。増分スキャンの所要時間と詳細取得キューに直接効く |
| 定義をアダプタ内のコードだけに持つ | ドリフトは起きないが、DB設計・設定ファイル設計という要望に応えられず、実測値の更新もコード変更になる |
| 定義をシードSQLだけに持つ | 実測値を更新するたびにSQLを手編集することになり、選択肢の差分レビューがしにくい |

## 影響（2026-09-03 実測・SUUMO 足立区）

| 指標 | 絞り込みなし | フィルタあり |
|---|---:|---:|
| 母集団 | 62,030件 | **27,150件（57%削減）** |
| 1ページ目149件中のMUST通過 | 5件 | **12件** |
| 面積が30㎡未満 | — | **0件** |
| 徒歩が20分超 | — | **0件** |
| 間取りが対象外 | — | **0件** |

不等号の向きが3軸とも正しいことを実データで確認した。返る間取りは
`1SLDK` `2SLDK` `3SLDK` を含む**上位集合**で、これらはローカルの MUST で
落ちる（取りこぼしではなく、余分に取っているだけ）。

## 残る課題

- **配線済みは SUUMO だけ。** HOMES・GOO・APAMAN は資料にパラメータの
  当たりが付いているが、**実測していないので YAML に書いていない**。
  推測で書くと課題#29 を再発させる
- 対照取得と連続0件バックストップが未実装（上表）
- EHEYA は `detail.priceMax` が無視されることを実測済み。NIFTY・SMOCCA・賃貸EX は
  robots.txt がクエリ付きURLを禁じているため、そもそも渡せない
