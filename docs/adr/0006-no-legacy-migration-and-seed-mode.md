# 旧DBを移行せず、シードモードで再通知を防ぐ

**状態: 採用（2026-09-01・Phase 0 で実施）**

v1 の11テーブル（`properties` 24,944件・`notifications`・`scrape_logs` 等）を v2 スキーマへ
移行しない。pg_dump でアーカイブしたうえで drop し、v2 は空のテーブルから始める。
初回の全件取得は**通知を送らず記録だけ行う `--seed` モード**で走らせる。

## 背景・検討した選択肢

通知履歴を捨てると「既に掲載されている全物件が新着として再通知される」問題が起きる。
これを避ける方法として次を検討した。

1. `notifications` を v2 の `t_notifications` へ移行する
2. **初回取得を通知なしの記録専用モードで走らせる**（採用）

1 は移行スクリプトの作成・検証コストがかかるうえ、`t_properties` 側も一緒に移さないと
`property_id` の参照が壊れる。そして v1 の物件データは `last_seen_at` の最大値が **2026-06-19**
（約2.5ヶ月前）で、掲載状態としては既に信用できない。移してもほぼ全件を取り直すことになる。

2 は移行を一切不要にしたうえ、**パターンを新規追加したとき・長期停止から再開したとき**にも
同じ問題が起きるため、どのみち必要になる汎用機能である。1 は今回限りの使い捨てだが
2 は繰り返し使う。

## Consequences

- **旧データは復元しない限り参照できない。**
  アーカイブ: `F:\backups\searching-for-houses-legacy\db_20260901.dump`
  （11テーブル・2.5MB。`pg_restore -l` で内容を検証済み）
- drop は「新スキーマ適用 → マスタデータ移送 → 旧新の突き合わせで欠落0を確認」の後に実施した。
  移送したのは条件マスタ128件・市区町村947件・条件×種別434件・サイト検索値1181件で、
  いずれも欠落0を確認している
- 初回全件スキャンは3〜8時間の見込み（Phase 5）。
  **エージェントのバックグラウンドから起動しない**（標準出力がパイプになり、
  進捗の `print` がブロックして例外も出さずに止まる）。`Start-Process` で切り離し、
  stdout/stderr を別ファイルへ落とす専用スクリプトを用意する
- `--seed` 実行中も `t_scrape_runs` にはチェックポイントを書くため、中断・再開はできる
