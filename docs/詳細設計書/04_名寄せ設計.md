# 名寄せ設計

**最終更新**: 2026-09-02（Phase 4）
**実装**: `src/house_search/dedup/`
**判断の記録**: [ADR 0012](../adr/0012-dedup-normalization.md)

同じ住戸が複数サイト・複数掲載で重複するため、ランキング上位が同一物件で埋まる。
v2 ではこれを将来課題ではなく**本体要件**として扱う（再設計計画 §6）。

---

## 1. 全体の流れ

```
一覧 upsert ─┐
             ├→ refresh_dedup_keys → sync_groups → 採点 → 通知
詳細 保存 ───┘        (キー計算)      (グループ化)
```

- **キー計算は2回呼ぶ。** 階数・住所は詳細ページで初めて埋まる掲載があり、
  一覧の時点では作れなかったキーが詳細取得後に作れるようになる
- **グループ同期は採点の前。** 設備の和集合も「順位は代表にだけ振る」も、
  採点時にグループが確定していることを前提にしている
- `check-sold` の後にも同期する（代表が成約したら次の代表へ移す）

モジュールは3層に分かれ、**前2層はDBに触らない純関数**なのでDBなしでテストできる。

| モジュール | 役割 |
|---|---|
| `dedup/address.py` | 住所の正規化・粒度の分類 |
| `dedup/key.py` | `dedup_key`（SHA256 hex 64桁）の合成 |
| `dedup/groups.py` | キー計算のDB反映・グループ同期・代表選定・実測 |

## 2. `dedup_key` の構成

```
sha256("v1|{ファミリ}|{正規化住所}|{ファミリ別の構成要素}")
```

| ファミリ | 構成要素 |
|---|---|
| `CHINTAI` / `MANSION_BUY` | 間取り ＋ 専有面積 ＋ 所在階 |
| `KODATE_BUY` | 土地面積 ＋ 建物面積 ＋ 間取り |

- **ファミリ識別子を混ぜる**のは、分譲賃貸が「賃貸」と「中古マンション売買」で
  二重にグループ化されるのを防ぐため
- **先頭の `v1` はキーの世代。** 正規化ルールを変えたら上げて `regroup` で全再計算する
- **構成要素が1つでも欠けたらキーを作らない**（`dedup_key = NULL`）。
  グループ化されず単独でランキングに残る（安全側）
- 間取りは `scoring/property_view.normalize_layout` を再利用する（`1SLDK` → `1LDK`）
- **面積は丸めない。** 小数第2位の固定表記（`f"{Decimal:.2f}"`）にして、
  float / Decimal / str のどれで渡しても同じキーになるようにしている
- **戸建てに専有面積を流用しない。** 存在しないため名寄せ事故になる

キーに**含めない**もの（→ ADR 0012）: 建物名・築年月・総階数・賃料。

## 3. 住所の正規化

サイトが実際に返す形（2026-09-02 実測）。

| サイト | 実際の表記 | 正規化後 |
|---|---|---|
| ABLE | `東京都足立区梅田７丁目周辺地図` | `東京都足立区梅田7丁目` |
| APAMAN | `東京都 足立区 南花畑 ４丁目 35-15` | `東京都足立区南花畑4丁目` |
| いい部屋ネット | `東京都足立区伊興四丁目` | `東京都足立区伊興4丁目` |
| goo不動産 | `東京都足立区古千谷本町１` | `東京都足立区古千谷本町1丁目` |
| LIFULL HOME'S | `東京都足立区谷中1丁目28-1` | `東京都足立区谷中1丁目` |
| SUUMO | `千葉県長生郡白子町剃金` | `千葉県長生郡白子町剃金` |
| SUUMO | `埼玉県比企郡川島町大字上伊草` | `埼玉県比企郡川島町上伊草` |

処理順:

1. NFKC 正規化 → 空白の除去
2. 末尾の付随文字列（`周辺地図` など）を除去
3. ハイフン類（`‐ ‑ ‒ – — ― ー −`）を `-` へ統一
4. **都道府県が無ければ前置する**（賃貸EX は `足立区竹の塚６` と書く。
   `resolve_city` が解決した `prefecture` を渡す）
5. `大字` を除去、`町`/`村` に続く `字` を除去
6. `ヶ` `ケ` → `が`（霞ヶ関/霞が関）
7. 漢数字の丁目をアラビア数字へ（`四丁目` → `4丁目`。1〜99 に対応）
8. **最初の「丁目」で打ち切る。** 丁目表記が無ければ最初の数字塊を丁目とみなす

⚠ **`ノ/の` `ツ/つ` の置換はしない。** 町名固有の表記を壊す偽陽性リスクがあり、
実測で必要と分かってから足す。

⚠ **設備テキスト用の `extract/normalize.py` と分けてある。**
住所固有の規則を設備の照合に持ち込まない。

## 4. グループ同期（`sync_groups`）

**差分管理をせず、全体を冪等な集合演算として作り直す。** 掲載の消失・代表の交代・
住所の後追い補正はすべて「次の同期で自然に直る」形になり、
イベント駆動の張り替えを書かずに済む。

1. 未登録のキーを `t_property_groups` へ INSERT（`ON CONFLICT (dedup_key) DO NOTHING`）
2. `t_properties.group_id` を張り替える。キーが消えた物件は未グループへ戻す
3. メンバーが居なくなったグループを DELETE
   （`t_notifications.group_id` は `ON DELETE SET NULL` なので履歴は壊れない）
4. `member_count` を更新
5. 代表を選び直し、**交代した分を `GroupChange` として返す**

### 代表選定の順序

```
COALESCE(rent_total, price) 昇順 NULLS LAST   -- 月額が最安
→ 設備抽出数 降順                              -- 情報が多い掲載
→ m_sites.representative_priority 昇順         -- サイト優先順（SUUMO=10 … スモッカ=110）
→ property_id 昇順                             -- 同点でも順位が揺れないように
```

- 対象は `status = 'active'` のメンバーのみ。掲載中が0件なら**代表を NULL にする**
  （成約済みの物件を代表に据えたままにしない）
- 比較は **`rent_total`（賃料＋管理費）**。管理費の計上方法がサイトで違うため、
  賃料だけで比べると実支出と逆転する

## 5. 採点への反映

**`t_property_scores` は物件単位のまま。** グループ単位のスコアテーブルは作らない。
変更したのは次の2点だけで、`rescore` も `config_hash` もそのまま動く。

### 5.1 設備はグループ内の和集合

`load_property_views` が、同じ `group_id` のメンバー全員の
`t_property_features` を各メンバーへ配る。サイトAでしか判らない設備と
サイトBでしか判らない設備がマージされる。

`detail_fetched` も同様に「グループ内の誰かが詳細取得済みなら真」にする
（未確認扱いの過剰な `unknown` を防ぐ）。

### 5.2 順位は代表と未グループ物件にだけ振る

`update_ranks` がいったん全ての `rank_in_pattern` を NULL にしてから、
`group_id IS NULL OR representative_property_id = property_id` の行にだけ振り直す。

`digest` は `rank_in_pattern` を起点に引くので、**この一手だけで
ランキングがグループ単位になる**（Phase 4 の完了条件）。

## 6. 通知

| 種別 | グループでの扱い |
|---|---|
| `new` | **グループ単位で抑制**。同一住戸の別サイト掲載を二重に送らない |
| `price_down` / `price_up` | 同上 |
| `cheaper_listing` | 代表が交代し、新代表の月額が旧代表より**安い**ときに送る |

- 通知済み判定は `t_notifications` に**現在の所属を JOIN** して行う。
  履歴テーブルは追記専用のままにしたいので、過去行の `group_id` は書き換えない。
  グループ構成が後から変わっても常に「いまの構成」で判定される
- `cheaper_listing` は**金額まで見て重複を避ける**。さらに安くなれば再通知され、
  同額の再検出（グループの作り直しなど）では送らない
- 個別通知の順位は、非代表メンバーには**代表の順位**を見せる
  （順位は代表にしか振らないので、そのまま引くと「順位未確定」になる）
- `member_count > 1` のときは Embed に「同一条件の掲載 n件（サイト一覧）」を出す。
  ダイジェストの行末には `(SUUMO ほか2サイト)` と付ける

## 7. コマンド

| コマンド | 用途 |
|---|---|
| `house-search regroup` | キーを全件作り直してグループを同期する。**ネットワーク不要** |
| `house-search dedup-stats` | サイト別のキー充足率・クロスサイト重複率・ユニーク率・住所粒度 |

⚠ **`regroup` は通知を送らない。** 既存データへ初めて適用したときに
`cheaper_listing` が大量発火するのを避けるため、候補の件数だけを表示し、
実際の通知は次回の `scan` の差分に任せる。

`coverage`（設備抽出の充足）とは測るものが違うので `dedup-stats` は別コマンドにしてある。

## 8. 実測（2026-09-02・301掲載）

301掲載 → **253グループ**（15.9%圧縮）。キー充足率は SUUMO の1件を除き100%。

| サイト | 掲載 | 代表 | 他サイトにも掲載あり | ユニーク率 |
|---|---:|---:|---:|---:|
| スモッカ | 88 | 88 | 2 | 98% |
| SUUMO | 60 | **33** | 4 | 93% |
| いい部屋ネット | 53 | 38 | 2 | 96% |
| ニフティ | 32 | 32 | 1 | 97% |
| APAMAN | 28 | 25 | 0 | 100% |
| goo不動産 | 17 | 15 | 3 | 82% |
| 賃貸EX | 11 | 10 | 1 | 91% |
| ABLE | 6 | 6 | 0 | 100% |
| LIFULL HOME'S | 6 | 6 | 0 | 100% |

**重複の主因はクロスサイトではなくサイト内だった。** SUUMO は60掲載中27件（45%）が
重複で、これが課題#13 の実態である。クロスサイト重複は13掲載にとどまる。

### ランキングへの効き

Phase 1 のダイジェストでは上位10件のうち6枠が3物件の重複で占められていた。
Phase 4 適用後の上位15件では、6グループが**計18掲載を6枠に集約**している。

```
 1 フレンズハイツ        掲載2件を1枠に集約
 2 ベル・グラース        掲載2件を1枠に集約
 3 フレンズハイツＡ       掲載2件を1枠に集約   ← 別棟なので分かれている（面積 43.00 vs 40.92）
 4 パレス湘南I           掲載3件を1枠に集約
 5 グリーンパークKEITEI   掲載4件を1枠に集約
12 ＪＲ相模線 上溝駅…     掲載3件を1枠に集約   ← 匿名掲載と建物名付き掲載が同じグループ
15 アムールヒルズ         掲載4件を1枠に集約
```

### 住所の粒度

| サイト | 丁目まで | 町名まで |
|---|---:|---:|
| SUUMO | 16 | **44** |
| スモッカ | 79 | 9 |
| いい部屋ネット | 45 | 8 |
| ニフティ | 30 | 2 |
| APAMAN / ABLE | 全件 | 0 |

SUUMO は町名までしか出さない掲載が多く、名寄せの粗さの主因になっている。
面積・間取り・階数が識別を担っており、実測では偽陽性0件だった。

## 9. まだやっていないこと

- **曖昧一致の候補フラグ**。完全一致だけを自動グループ化しており、
  「近いが一致しない」ものを候補として持つ仕組みは作っていない
- **売買の名寄せ精度の実測**。戸建ての `land_area_sqm` / `building_area_sqm` を
  使う経路は実装済みだがデータが無い（Phase 8 で実測 → 課題#11）
- **賃貸EX の本採用判断**。ユニーク率91%は実測できたがサンプルが11掲載と少ない。
  初回全件スキャン（Phase 5）後に測り直す（→ 課題#5）
