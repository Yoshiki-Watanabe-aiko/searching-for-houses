# 検索パターンをエリア帯で分割する

**状態: 採用（2026-09-02・Phase 5）**
**関連: 再設計計画 §4（スコアリングモデル）／要件定義書 §5／CONTEXT.md／課題#5・#24**

v2 は「4都県を1つの検索パターンで見て、MUST で絞り WANT で採点する」設計だった。
初回全件スキャン（8,429掲載）の実測でこれが破綻していることが分かったので、
**エリア帯**という単位を導入してパターンを分割する。

---

## 何が起きていたか

パターン名は「東京賃貸一人暮らし」。対象は東京・千葉・埼玉・神奈川の4都県。
毎日20:00に届く上位15件の内訳が以下だった。

| 範囲 | 埼玉 | 千葉 | 神奈川 | 東京 |
|---|---:|---:|---:|---:|
| 母集団（MUST通過8,158件） | 3,202 | 1,954 | 1,500 | **591** |
| 上位100件 | 80 | 19 | 1 | **0** |
| 上位15件（ダイジェスト） | 12 | 3 | 0 | **0** |

上位100件の市区は千葉県茂原市11・埼玉県本庄市9・毛呂山町7・上里町7・美里町6・
越生町6・行田市5・加須市5…と、**群馬/栃木県境の埼玉県北西部と房総半島**で
占められていた。本庄市は高崎の隣、神川町は群馬県境、茂原市は外房である。

原因は2つ重なっている。

1. **スコアに立地の概念が無い。** weight 200点のうち `rent_total` 40 と
   `area_sqm` 20 が「安くて広い」に配分される一方、**どこに住むかには1点も
   配点されていない**。エリアは `search`（サイトへ渡す条件）にしかなく、
   MUST にも WANT にも存在しない
2. **母集団が郊外に偏る。** 東京は591件で埼玉の1/5。7万円・30㎡・徒歩20分を
   東京で満たす掲載がそもそも少ない（23区は足立区19件・葛飾区11件だけ）

当初の要望は「優先度の高い条件順にランク付けして家を探したい」だった。
**最も優先度が高いはずの条件がモデルに無い**ため、安くて広い郊外が構造的に勝つ。

---

## 決定1: **エリア帯**を導入し、1パターン＝1帯にする

**エリア帯**は「賃料相場が一様とみなせる地理的範囲」（→ CONTEXT.md）。
相場の違う範囲を1帯に混ぜると、安い側が構造的に上位を独占して順位が意味を失う。

- 帯1「東京23区賃貸」: 23市区
- 帯2「近郊45分圏賃貸」: 63市区

ダイジェストは帯ごとに1通ずつ届く（`digest_group: "賃貸"` でラベルを揃える）。

## 決定2: 帯は**行政区画では切らない**。市区を明示列挙する

「東京都／3県」で切っても解決しない。実測では東京都519件のうち上位を占めるのは
あきる野市53・青梅市49・東大和市29…と多摩地域で、23区は出てこない。
同様に「埼玉県」には都心30分の川口市と群馬県境の神川町が同居する。

そこで帯は**通勤の許容時間**で市区を選び、`search.cities` に列挙する。

⚠ **この市区リストは通勤時間の近似であり、駅データに基づくものではない。**
物件→最寄駅の名寄せと駅→所要時間のデータが無いため、決定4の
「通勤時間 metric」を採らずに市区リストで代用している。

## 決定3: 帯どうしは**重ならない**

重なると同じ掲載が2つのランキングに出て、通知も二重になる。
`tests/test_pattern.py` が2帯の `cities` に共通要素が無いことを回帰テストする。

## 決定4: 帯ごとに MUST と `best`/`worst` を変える

相場が違うのだから、同じ閾値では片方が死ぬ。

| | 帯1（23区） | 帯2（45分圏） |
|---|---|---|
| `rent_total_max` | **120,000**（暫定） | 70,000 |
| `rent_total` の best/worst | 70,000〜120,000 | 50,000〜70,000 |

帯1で帯2と同じ 50,000〜70,000 を使うと、23区の掲載はほぼ全て0点になり
**weight 40 が丸ごと死ぬ**（順位が賃料を反映しなくなる）。

⚠ **帯1の 120,000 は暫定値。** 7万円では23区に30件しか無くランキングが
成立しないため、**広めに取ってから `rescore` で締める**方針にした。
締める方向はネットワーク不要のDBバッチで試せるが、緩める方向は取り直しになる
（MUST 1段目で `fail` の掲載はDBにも入らないため）。

## 決定5: **採点も帯に閉じる**

エリア帯は取得URLを絞るだけなので、これだけでは足りない。
`load_property_views` は `property_type` と `site_codes` でしか絞っておらず、
そのままだと**DBに残っている帯外の掲載にも帯のスコアが付く**。
23区パターンのランキングが本庄市で埋まり、分割した意味が消える。

`scan` と `rescore` の双方で `pattern.search.cities` を渡す。
市区を解決できなかった掲載（`city_id IS NULL`）は帯の取得URLから来たものと
みなして残す（除くと新規の取りこぼしになる）。

## 決定6: **新着監視**と**在庫棚卸し**を分ける

同じスキャンに両立しない要求を負わせていた。実測では並び順が
**新着順（SUUMO・HOMES）／賃料が安い順（ABLE）／制御していない（残り6サイト）**
の3系統に割れており、「5ページで打ち切る」の意味がサイトごとに別物だった。
結果として SUUMO は「直近150件の新着だけ見る速報サイト」、ABLE は
「在庫の安い側2,102件を持つ棚卸しサイト」として動いていた。

- **新着監視**: 増分 `scan`（一覧1ページ）・2時間ごと
- **在庫棚卸し**: `scan --full`（一覧5ページ）・週1

市区単位なら1ページ30件で2時間ぶんの新着は収まる。

## 却下した案

| 案 | 却下の理由 |
|---|---|
| 立地を WANT の数値 metric にする（都心までの所要時間） | 最も本質的だが、**駅→所要時間の外部データと物件→最寄駅の名寄せが新たに要る**。MetricRegistry と DDL にも手が入り Phase 5 の範囲を超える。将来ここへ移行する余地は残す |
| 重み配分だけ見直す（`rent_total` 40→20 など） | `rescore` だけで済むが、**エリアの概念は依然として無い**ので郊外バイアスの根本が残る |
| MUST でエリアを絞る（1パターンのまま `cities` を列挙） | 実装ゼロで母集団は絞れるが、相場の違う23区と近郊が同じスコア関数で比較され続ける（帯1の best/worst を分けられない） |
| 東京都全域を1帯にする | 実測で東京都519件のボリューム帯はあきる野市・青梅市。帯を分けても上位は多摩で埋まり23区は出てこない |
| 23区を対象外にする | 予算的な現実には合うが、「23区は無理」と実データで確かめないまま切り捨てることになる |

## 副次的な効果

- **対象市区が216→86に減り、増分スキャンが約72分→約53分に短縮する。**
  空いた時間に `check-sold`・`digest`・`backup` を並走させずに置ける
- **`requires_city=False` のサイトも市区展開される。** `cities` を明示すると
  `resolve_areas` が市区で引くため、都道府県4本しか叩いていなかった
  SUUMO・HOMES・EHEYA の母集団が増える。SUUMO は一覧で2,248件しか見ておらず、
  APAMAN（37,163件）の**1/17**だった
- **賃貸EXの評価が変わった**（→ 課題#5）。全体ではユニーク率26%だが、
  45分圏では63%・69代表と GOO に迫る。26%は216市区を舐めて
  市区必須サイトと重なった結果であり、通勤圏では独自性がある

## どこまでやらないか

- **売買の帯は決めていない。** 売買は通勤より学区・資産性が効くため、
  賃貸の帯をそのまま流用しない（Phase 8 で決める）
- **帯の数は2つに留める。** 3帯（23区／準都心／それ以遠）も検討したが、
  「それ以遠」は結局いま上位を占めている本庄・茂原で埋まり、見る価値が薄い
- **市区より細かい単位（町丁目・沿線）では切らない。** サイト側の検索が
  市区単位のため、沿線で切ると市区内の非沿線物件を落とす後処理が要る
