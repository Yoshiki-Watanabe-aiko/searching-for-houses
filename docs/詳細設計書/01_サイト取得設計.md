# サイト取得設計

**最終更新**: 2026-09-02（Phase 3）
**実装**: `src/house_search/scrape/`

v1 の `01_検索条件マッピング設計.md`（廃止済み）を置き換えるもの。
v2 ではサイトの検索フォームへ渡すのを**エリア・物件種別・価格上限の3つだけ**に限定し、
サイト別コードは「取得と解析」だけを担う（→ [ADR 0003](../adr/0003-local-filtering.md)）。

---

## 1. サイトへ渡す条件

| 渡すもの | 由来 | 理由 |
|---|---|---|
| エリア（都道府県・市区町村） | `search.prefectures` / `search.cities` | 母集団を絞らないと取得量が非現実的になる |
| 物件種別 | `property_type` | 賃貸と売買でURLの系統が違う |
| 価格上限 | `search.price_max_hint` | 同上。MUST上限の2〜3割増しをバッファとして渡す |

**設備条件・間取り・面積・築年数・徒歩分数はサイトへ渡さない。**
WANT条件（オートロック無しでも減点で残ってほしい）をサイト側フィルタに渡すと、
対応サイトでは物件が除外されて順位に現れず、非対応サイトでは素通りする。
ランキングを入れる以上、この2つは両立しない。

`price_max_hint` にバッファを持たせるのは、管理費を別計上するサイトで
「賃料は上限内だが管理費込みだと超える」物件を取りこぼさないため。
上限判定そのものはローカルの MUST（`rent_total_max`）で行う。

## 2. 2段判定によるコスト緩和

一覧ページに載る項目だけで MUST を先に評価し、**`fail` の掲載はDBにも入れず詳細も取りに行かない**。

```
一覧取得 → MUST(1段目) → fail なら破棄
                       → pass/unknown なら upsert → 詳細取得 → 抽出 → MUST(2段目) → 採点
```

- 1段目で判定できる項目は `MetricRegistry` の `available_on_list=True`
  （賃料・間取り・面積・築年・徒歩）
- 判定できない項目（`features` / `floor_min` / `monthly_cost_max`）は `unknown` になり、
  **`unknown` では詳細取得をスキップしない**
- 実測（2026-09-01・SUUMO 4都県）: 一覧177件 → 1段目通過22件。詳細取得を **87%削減**

詳細取得は1回の実行あたりサイト単位で上限を設ける
（既定40件 / `--full` は400件。`scrape/scan.py` の `DEFAULT_DETAIL_LIMIT`）。
取り残しは `detail_fetched_at IS NULL` のキューに残り、次回実行で拾われる。

## 3. エリア検索方式（サイト別）

実装は `src/house_search/scrape/area.py`。アダプタが2つの性質を宣言し、
`resolve_areas` がそれを見て対象エリアを組み立てる。

| 宣言 | 意味 |
|---|---|
| `requires_city` | 都道府県だけでは一覧が0件になるか。`True` なら `search.cities` が空でも全市区へ展開する |
| `city_value_source` | 市区の検索値の出どころ。`jis`＝JIS5桁コード / `mapping`＝`m_city_site_values` の登録値 |

| サイト | 市区必須 | 値の出どころ | 一覧URLの形 |
|---|:---:|---|---|
| SUUMO | — | JIS5桁 | `/jj/chintai/ichiran/FR301FC001/?ar=&bs=040&ta=&sc={JIS5}` |
| HOMES | — | マッピング | `/chintai/{tokyo/chiyoda-city}/list/` |
| GOO | ✅ | JIS5桁 | `/rent/{地方}_ap/area_{都道府県}/{JIS5}.html` |
| ABLE | ✅ | JIS5桁 | `/{都道府県}/area/{JIS5}/list/` |
| CHINTAI_EX | ✅ | JIS5桁 | `/search/city/{JIS5}` |
| ATHOME | — | マッピング | `/chintai/{tokyo/adachi-city}/list/` |
| EHEYA | — | JIS5桁 | `/{都道府県}/area/{JIS5}/search/` |
| NIFTY | ✅ | マッピング | `/rent/{都道府県}/{adachiku}_ct/` |
| APAMAN | ✅ | JIS5桁の**下3桁** | `/{都道府県}/{121}/` |
| SMOCCA | ✅ | JIS5桁 | `/search/{都道府県}/city/{JIS5}` |
| MINIMINI | — | スラグ | 未実装（reCAPTCHA → 課題#18） |

### 3.1 JIS5桁を `m_cities.jis_code` から導く理由

市区の検索値が JIS5桁そのものであるサイトは、`m_city_site_values` に行が無くても
`m_cities.jis_code` から値を作れる。マッピング表に縛ると**取りこぼしが大きい**:
対象4都県（東京/千葉/埼玉/神奈川）の253市区に対し `m_city_site_values` の行は
**67件しかなく**、東京都は23区だけで多摩地域が丸ごと落ちていた。

`m_cities.jis_code` も初版は947件中789件が NULL だったため、Phase 2 で
エイブルのエリア索引（`/{都道府県}/area/`）から実測して473件を補完し、
26件（大阪市・福岡市の区でコードがずれていた）を訂正した。
結果、対象4都県で **216/253市区**が指定できる。残りは課題#16。

### 3.2 市区の自動展開（課題#1）

`requires_city` のサイトは `search.cities` が空でも都道府県内の全市区へ展開する。
展開後に1つも値を解決できなかった場合、**都道府県へフォールバックせず空のまま返す**
（都道府県で引いても0件になるだけなので、`scan` が理由を残してスキップする）。
`requires_city` でないサイトは逆に、市区を解決できなければ都道府県単位へ落とす。

> **Phase 3 で EHEYA・SMOCCA の形式が確定した（どちらも JIS5桁）。**
> `m_city_site_values` の初版はこの2サイトについて、東京23区の行が JIS5桁、
> それ以外の行がスラグという矛盾した状態だった。実URLを確かめた結果
> **JIS5桁が正**で、`m_cities.jis_code` から導出する（この表は引かない）。
>
> 逆に **ATHOME・NIFTY は初版が JIS5桁で誤り**だった。実際はサイト固有スラグで、
> JISからは導出できない。各サイトのエリア索引から実測した値を
> `db/seed/08_city_site_values_slugs.sql` に置いてある
> （ATHOME は東京都のみ。理由は 課題#21）。
>
> APAMAN だけは JIS5桁の**下3桁**という第3の形式だった（新宿区 13104 → `104`）。
> JISから導出できるのでマッピング表は要らない。

## 4. SUUMO（Phase 1 実装済み）

### 4.1 URL

```
一覧: https://suumo.jp/jj/chintai/ichiran/FR301FC001/?ar={地方}&bs=040&ta={JIS2}&ct={万円}&sort=2&pc=30&pn={頁}
詳細: 一覧のリンク（/chintai/jnc_XXXXXXXX/?bc=YYYYYYYY）をそのまま使う
```

- `bs=040` が賃貸。`sort=2` は新着順
- `ct` は**万円単位・小数1桁**（90,000円 → `ct=9.0`）
- **`tc=`（設備条件）は送らない。** v1 は10条件を `tc=` で渡していたが v2 では全廃した
- `pc=30` が1ページの件数。これ未満しか返らなければ最終ページ

### 4.2 一覧のDOM

SUUMO は「1建物 = 複数住戸」の入れ子構造で、**住戸ごとに1掲載**になる。

| 項目 | セレクタ | 備考 |
|---|---|---|
| 建物 | `div.cassetteitem` | |
| 建物名 | `.cassetteitem_content-title` | |
| 住所 | `.cassetteitem_detail-col1` | |
| 駅情報 | `.cassetteitem_detail-text`（複数） | 徒歩分数は**最短**を採る |
| 築年・階建 | `.cassetteitem_detail-col3` | 「築40年 2階建」 |
| 住戸行 | `.js-cassette_link` | |
| 物件ID | `input[name=bc]` の `value` | URLの `bc=` と同値 |
| 所在階 | クラス無しの `td` | 「N階」に一致するセルを拾う |
| 賃料 | `.cassetteitem_price--rent` | |
| 管理費 | `.cassetteitem_price--administration` | **v1 は取得していなかった** |
| 敷金 / 礼金 | `.cassetteitem_price--deposit` / `--gratuity` | |
| 間取り / 面積 | `.cassetteitem_madori` / `.cassetteitem_menseki` | |

⚠ **管理費・敷金・礼金の「-」は「無し」を意味するので 0 として扱う。**
`None` のままにすると `rent_total`（賃料＋管理費）が「管理費不明」となり、
実際には管理費0円の物件が MUST 判定で `unknown` に落ちる。

実測の充足率（2026-09-01・49掲載）: 賃料・面積・間取り・築年・徒歩・住所・管理費・敷金・礼金
はいずれも **100%**、所在階は 100%。

### 4.3 詳細のDOM

- **設備ブロック**: `ul.inline_list` のうち**読点区切りの語が最も多いもの**を採る
  （契約期間・備考など別用途の `ul.inline_list` が混ざるため、位置では選ばない）
- **th/td の項目**: 所在地 / 駅徒歩 / 構造 / 階建 / 階 / 築年月 / 向き / 駐車場 / 入居 /
  契約期間 / 条件 / 建物種別

⚠ **構造化フィールドはアダプタ側で正規化してから `raw_features_text` に載せる。**
「駐車場: 近隣205m16500円」は語彙が無く辞書で照合できないため、
値が `-` 以外なら「駐車場あり」という派生トークンへ寄せる。
欄の意味づけ（`-` が無しを意味する 等）はサイト固有なのでアダプタが吸収し、
辞書側は語彙の対応だけを持つ。
**建物種別（アパート/マンション）は対応する条件が無く未知表記を汚すだけなので載せない**
（`type_specific_attrs` には残す）。

## 5. Phase 2 で追加したサイト

いずれも実HTMLフィクスチャ（`tests/fixtures/{site}/`）でパーサを回帰テストしている。

### 5.1 LIFULL HOME'S

| 項目 | 内容 |
|---|---|
| 一覧 | `/chintai/{エリアスラグ}/list/?cond[sortby]=newdate&cond[monthmoneyroomh]={万円}` |
| ページ | `?page=N`（建物30件/ページ） |
| 建物 | `div.moduleInner.prg-building`。名前 `.bukkenName` / スペック表 `div.bukkenSpec th` |
| 住戸 | `tr.prg-room`。`data-kykey` が物件ID、`data-href` が詳細URL |
| 金額 | `td.price` の `span.priceLabel`＝賃料、その tail＝管理費、`<br>` の tail＝「敷/礼/保証/敷引」 |

⚠ **敷金・礼金が月数表記**（「1ヶ月」）。円へ直すには賃料が要る（`parse_months_fee`）。
⚠ **築年数に「築」が付かない**（「8年 / 8階建」）。共通の `parse_age_years` では読めない。
⚠ `tr.prg-room` には**業者名だけの行**（`memberDataRow`）が混ざる。`data-kykey` の有無で除く。
⚠ **詳細ページの人気条件アイコンは非該当も並ぶ。** `<span class="sr-only">(該当)</span>` で
選別しないと、辞書が「オートロック(非該当)」から「オートロック」を拾う。
⚠ 詳細の設備は Tailwind のユーティリティクラスで組まれ class 名に意味が無いため、
**ラベル文字列**（「設備・サービス」「キッチン/バス・トイレ」等）で引き当てる。
口コミも `dt/dd` を使うのでラベルの白名簿が要る。

**取得できるかは不安定。** 既定の自己申告UAだと 403、ブラウザ相当UAだと 200 だったが、
実スキャンを重ねると AWS WAF のボットチャレンジ（202＋空ボディ）に切り替わった → 課題#17。

### 5.3 エイブル

| 項目 | 内容 |
|---|---|
| 一覧 | `/{都道府県}/area/{JIS5}/list/?o=1` |
| ページ | `&i=N`（30件/ページ） |
| 建物 | `section.m-list_cassette`。名前 `h2` / th-td に 住所・交通・築年・階建・構造 |
| 住戸 | `tr.detail-inner`。`a.js-detailLink[data-bkkey]` が物件ID |

⚠ **賃料上限のクエリ（`ct`）が効かない。** 実測で `ct=9` を付けても 23.9万円の掲載が返る。
代わりに `o=1`（賃料が安い順）で並べ、限られたページ数でも MUST を通る価格帯が

⚠ **詳細リンクの href は `javascript:void(0)`。** 住戸ごとの実URLは
`onclick` の `clickBukkenInfoArea('...')` の中にしかない。
建物見出しの `a.js-detailLinkUrl` にも同形のURLがあるが建物あたり1本しか無い。
⚠ 面積が **㎡（U+33A1）**、敷金が「23.9万」と円を省く、管理費が「--」。
いずれも共通パーサ側で吸収した（NFKC正規化・`万円?`・記号だけの欄は0円）。
⚠ 詳細の「築年」は「築20年」で年月が無い。年月は「築年/築年月」にだけ入る。

### 5.4 賃貸EX

| 項目 | 内容 |
|---|---|
| 一覧 | `/search/city/{JIS5}` |
| ページ | `/page/N`（**パス形式**） |
| 詳細 | `/dwelling/show/{ハッシュ}` |

⚠ **robots.txt が `Disallow: *?*` でクエリ付きURLを全面的に禁じている**
（`/search/results` も禁止）。価格上限をサイト側へ渡せないので、
市区の全掲載を取ってローカル判定する。ページ送りがパス形式なのは幸い。
⚠ **同じURLでも一覧レイアウトが3通り返る**（実測）。
項目名つきの表を `table` で包む形・`tr` で包む形・項目名の無い圧縮行の3種。
`parse_list` はタグではなく `js-bukken` クラスで拾い、`th` の有無で分岐する。
圧縮行では住所・駅・階建・築年月が建物ヘッダ側にしかないので親を辿る。
⚠ 圧縮行の住所は「足立区竹の塚６」と**都道府県が付かない**。
`resolve_city` は前置の都道府県が無いとき、**全国で一意な市区名だけ**を引き当てる
（「北区」のように複数県にある名前は解決しない）。
⚠ 詳細は同一物件の他社掲載と近隣物件が続けて並ぶため、`th/td` は最初の出現だけを採る。
⚠ 「本物件について」は設備を説明する生成文で語彙が最も多い（抽出数が3倍になる）一方、
未知表記に文断片が入る → 課題#19。

## 5A. Phase 3 で追加したサイト

**5サイトとも HTTP 取得**（→ [ADR 0010](../adr/0010-http-only-fetch.md)）。
v1 と再設計計画は Playwright 前提としていたが、実測ではいずれも
サーバレンダリング済みHTMLを返した。v1 がブラウザを使っていたのは
検索フォームを操作していたためで、URLを直接組み立てる v2 では不要だった。

### 5A.1 アットホーム

| 項目 | 内容 |
|---|---|
| 一覧 | `/chintai/{エリアスラグ}/list/?SORT=7&PRICETO={コード}` |
| ページ | `/list/page{N}/`（**パス形式**・建物30件/ページ） |
| 建物 | `div.p-property--building`。名前 `h2.p-property__title--building` |
| 住戸 | `div.p-property__room--detailbox`。`a[href]` の `/chintai/{数字}/` が物件ID |

⚠ **建物ヘッダの項目名がテキストではなくアイコン**（`dl.p-property__information-hint`
の `dt i.u-icon--map-mini` 等）。ラベル文字列では引けないのでアイコンのクラスで振り分ける。
⚠ **賃料上限はセレクトのコード体系**（`PRICETO=kc113`）。3万円の `kc101` から
0.5万円刻みの連番。選択肢に無い額は**1つ上の帯へ切り上げる**（取りこぼしを作らないため）。
⚠ 「部屋番号・階」の欄は掲載によって号室（`２０５`）だったり階（`2階`）だったりする。
⚠ **完成前の建物は築年数の括弧が付かず年月だけ**（`3階建 2026年12月`）。年月から数える。
⚠ **パズル認証のボット検知がある**（→ 課題#20）。200 のまま認証ページが返るため、
掴んだら**黙って0件にせずエラーにする**。

### 5A.2 いい部屋ネット

| 項目 | 内容 |
|---|---|
| 一覧 | `/{都道府県}/search/` または `/{都道府県}/area/{JIS5}/search/` |
| ページ | `?page={N}`（建物20件/ページ） |
| 掲載データ | **`<script id="__NEXT_DATA__">` のJSON**（`buildingSearchResult.buildings`） |
| 詳細 | `/detail/{propertyFullId}/`。同じくJSONの `property` |

⚠ **DOMを読まない。** HTMLのクラス名は CSS Modules のハッシュ付き
（`styles_cassette__UCHok`）でビルドのたびに変わる。JSON が正典。
⚠ `__NEXT_DATA__` が無ければ**例外にする**。App Router へ移行するとこの経路は消えるため、
「取れているつもりで0件」を最も避けたい。
⚠ **賃料上限をクエリで渡せない**（`?detail.priceMax=` も `?priceMax=` も無視される実測）。
⚠ 設備は `propertyFeatures[].label` に並ぶ。**`remarks`・`salesPoint` は生成文なので載せない**。

### 5A.3 ニフティ不動産

| 項目 | 内容 |
|---|---|
| 一覧 | `/rent/{都道府県}/{市区スラグ}_ct/` |
| ページ | `/{N}/`（**パス形式**・建物40件/ページ） |
| 建物 | `li.result-bukken-list`。住戸 `tbody.click-area` |
| 詳細 | `a[data-detail-link]` の `/rent/…/detail_{ハッシュ}/` |

⚠ **他社サイトの掲載を集約するポータル。** 詳細リンクが外部ドメイン
（`sumaisagashi-madoguchi.com` 等）へ向く掲載が混ざるので**取り込まない**。
⚠ そのため **1ページの掲載数では最終ページを判定できない**（掲載数が建物数を下回る）。
0件のときだけ打ち切る。
⚠ **築年数に「築」が付かない**（`1年7ヶ月`）。
⚠ 住所の行に項目名が無く、`svg title` が「地図マーカー」であることだけが目印。
⚠ 値に案内文言が続く（`無 質問 駐車場について詳しく教えてほしい`）。「質問」以降を切る。
⚠ 詳細は主要スペックが `dt/dd`、細目が `th/td` と**2系統に分かれている**。

### 5A.4 アパマンショップ

| 項目 | 内容 |
|---|---|
| 一覧 | `/{都道府県}/{JIS下3桁}/` |
| ページ | `?page={N}`（建物20件/ページ） |
| 建物 | `article.mod_box_section_bdt`。ヘッダ `div.box_head_result` |
| 詳細 | `/{都道府県}/{市区}/b{建物CD}/{住戸CD}/` |

⚠ **robots.txt が全パスを禁止している**（`Disallow: /`）。
ユーザーの明示的な判断で取得している（→ [ADR 0011](../adr/0011-apaman-robots-exception.md)）。
取得間隔は他サイトより長い4秒。
⚠ **ヘッダ行の列位置が使えない。** ヘッダは先頭に余分な空セルがあり
データ行より1列多い（ヘッダ8列 / データ行7列）。列位置で対応させると
間取りの欄に「お気に入り」を読む。クラス名が付いている `td.chinryo`（賃料）を
起点に前後の相対位置で読む。
⚠ 詳細は項目名が `span.heading` の系統（所在地・交通・築年月・建物階）と
`th/td` の系統（賃料・設備・構造）に**二分されている**。
⚠ 同じ住戸がPR枠と通常枠の両方に出ることがある。物件IDで重複を落とす。
⚠ 「お問い合わせ」リンク（`/inquiry/bukkenentry/{ID}/`）は詳細ページではない。

### 5A.5 スモッカ

| 項目 | 内容 |
|---|---|
| 一覧 | `/search/{都道府県}/city/{JIS5}`（**1ページ90件・ページ送り不可**） |
| 建物 | `div.item_list01`。詳細 `/bukken/detail/{ハッシュ}` |

⚠ **robots.txt がページ送りを禁止**（`Disallow: /*/page/`）。`is_last_page` を常に
True にして2ページ目を取りに行かせない。`/search/results` も禁止のため
**賃料上限も渡せない**（→ 課題#22）。
⚠ **一覧のレイアウトが2種類ある。** 通常表示は1住戸=1行の表で、列位置は
ヘッダ行のラベルから決める。グループ表示（`building-group-container`）は
同一建物の住戸を1つの `td` に畳み、賃料・管理費・敷金・礼金まで同じセルへ入れる。
⚠ **金額セルの `<br>` だけを区切りにする。** `itertext` で分けると
`<span><span>12.8</span>万円</span>` が「12.8」と「万円」に割れて金額として読めない。
⚠ 建物欄に築年数が載らない（`地上3階建 / 2014年04月 / 賃貸アパート`）。築年月から数える。
⚠ 所在地に「◯◯区の賃貸を探す」の導線が付く。

## 6. レート制御・robots.txt

`src/house_search/scrape/fetch.py`。設定は `m_sites` から読む。

| 項目 | 既定 | 備考 |
|---|---|---|
| リクエスト間隔 | 2.5秒 ± 30%のジッタ | `m_sites.min_interval_sec` |
| 1回の実行のページ数 | 5 | `m_sites.max_pages_per_run`（`--full` 時のみ使う） |
| 日次リクエスト上限 | なし | `m_sites.daily_request_cap` |
| リトライ | 429/5xx を最大3回・4秒から倍々 | |
| 打ち切り | 5回連続失敗でサイト中止 | `SiteAborted` |

- **User-Agent は既定で `.env` の `USER_AGENT`**（自己申告）。
  アダプタが `user_agent` を宣言したサイトだけ差し替える。
  LIFULL HOME'S は robots.txt が当該パスを許可しているのに自己申告UAを 403 で拒否するため、
  このサイトにだけブラウザ相当のUAを使う。**取得間隔と robots.txt の尊重は変えない**
- **能動的なボット検知は突破しない。** MINIMINI の reCAPTCHA（課題#18）、
  HOME'S の AWS WAF チャレンジ（課題#17）、ATHOME のパズル認証（課題#20）が該当する。
  Phase 3 で MINIMINI を素の Chromium でも試したが通らなかった。
  通すにはフィンガープリント偽装が要るため、**ブラウザに替えても方針は変わらない**
- ⚠ **ボット検知のページは 200 で返ることがある。** そのまま解析すると
  掲載0件になるだけでエラーにならず「取れているつもり」で気づけない。
  検知ページを判別できるサイトは**アダプタが例外にする**（ATHOME で実装済み）
- **robots.txt を無視するのは APAMAN だけ**（`SiteFetcher.ignore_robots`）。
  アダプタが明示的に宣言したサイトにしか効かず、既定は `False`。
  取得間隔・日次上限・バックオフはこのフラグでも緩めない
  （→ [ADR 0011](../adr/0011-apaman-robots-exception.md)）
- **robots.txt はオリジンごとに起動時1回だけ取得**し、Disallow のURLは取りに行かない
- robots.txt が取れない場合も取得は続ける（控えめな間隔は維持する）
- SUUMO の robots.txt 実測（2026-09-01）: `/jj/chintai/ichiran/FR301FC001/`（一覧）と
  `/chintai/bc_*/`（詳細。`/printout/` を除く）は `User-agent: *` に対して**許可**。
  `Crawl-delay` は bingbot にのみ 30秒の指定があり `*` には無い

## 7. 中断・再開

`t_scrape_runs` に `(run_id, mode, pattern, site, phase, cursor, status)` を記録する。
詳細取得は `detail_fetched_at IS NULL` のキュー型なので、**再開はSQLの自然な帰結**になる
（部分インデックス `ix_t_properties_detail_pending` がそのまま効く）。
upsert はすべて冪等で、二度流しても壊れない。

## 8. アダプタの追加手順（Phase 3〜）

0. **着手前に robots.txt と実HTMLを1回ずつ実測する。** 「v1 がブラウザを使っていた」
   「資料にこう書いてある」は根拠にならない（Phase 3 で5サイトとも覆った）
1. `src/house_search/scrape/{site}.py` に `SiteScraper` プロトコルを満たすクラスを書く
   - メソッド: `list_urls` / `page_url` / `is_last_page` / `parse_list` / `detail_url` /
     `parse_detail` / `is_sold`
   - クラス属性: `site_code` / `requires_city` / `city_value_source` / `user_agent` /
     `ignore_robots`
     （`user_agent` は既定UAを拒否するサイトだけ宣言する。既定は `None`。
     `ignore_robots` の既定は `False` で、変えてよいのはユーザーが明示的に
     そう決めたサイトだけ → ADR 0011）
2. `src/house_search/scrape/__init__.py` の `SCRAPERS` へ登録する
3. `tests/fixtures/{site}/` に実HTMLを保存し、`tests/test_scrape_{site}.py` を書く
4. `house-search coverage` で充足率を実測する。
   **詳細取得済みなのに設備が0件のサイトは警告として出る**ので、
   「アダプタは足したが抽出が配線されていない」状態を検出できる

**未登録のサイトは `scan` が「スキップ（アダプタ未実装）」と明示的に報告する。**
黙って無視すると「実装済みだが未配線」を見逃すため。
