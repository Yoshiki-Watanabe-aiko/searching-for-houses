# 土地を独立したファミリ（TOCHI_BUY）として足し、BUY_TYPES は「建物を伴う売買」に固定する

**状態: 採用（2026-09-11・課題#61）**
**関連: 課題#4（売買・土地の設計）／課題#61（土地の追加）／
[ADR 0012](./0012-dedup-normalization.md)（名寄せキー）／
[ADR 0020](./0020-address-master-chome-guard.md)（名寄せキーの版 v2）／
計画書 [`docs/計画_Phase9_土地.md`](../計画_Phase9_土地.md)／要件定義書 §3・§5.3・§5.4・§8**

土地（`TOCHI`）を6種別目として足す（Phase 9）。土地は**建物を伴わない**ので、
間取り・専有面積・建物面積・築年数・所在階のどれも持たない。既存の売買4種別と同じ枠に
入れると、建物前提の項目が**黙って土地にも開き**、書けても判定されず例外にもならない。

9a（本 ADR の範囲）はスキーマの骨格だけを入れる。ネットワークにも既存データにも
触れず、**既存6パターンの `config_hash` と既存3ファミリの名寄せキーは1ビットも変わらない**
（→ `tests/test_buy_foundation.py`・`tests/test_dedup_key.py` が基準値で固定）。
アダプタ（9b）・辞書（9c）・相場比（9d）・運用投入（9e）は、実サイトの実測の後に分ける。

---

## 決定1: `TOCHI_BUY` ファミリを足し、`BUY_TYPES` には TOCHI を入れない

| 定数 | 中身 | 意味 |
|---|---|---|
| `ALL_PROPERTY_TYPES` | 6種別 | 土地を含む全種別 |
| `BUY_TYPES` | 新築M・中古M・新築K・中古K | **建物を伴う**売買 |
| `TOCHI_TYPES` | 土地 | 新設 |

土地へ広げる項目は `BUY_TYPES | TOCHI_TYPES` のように**明示的に書く**（`price`・`price_max`）。
土地面積は戸建てと共有する（`KODATE_TYPES | TOCHI_TYPES`）。

⚠⚠ **`BUY_TYPES` に TOCHI を入れてはいけない。** `layouts`（間取り）と
`market_rate_ratio`（相場比）が `{CHINTAI} | BUY_TYPES` で定義されているので、
その瞬間に土地パターンへ間取り MUST や相場比 WANT が書けてしまう。
書けても間取りは全件 unknown・相場比は全件 missing になるだけで、**例外にならない**。

結果として土地で使えるのは **metric 8つ**（price・land_area_sqm・walk_minutes・
commute_minutes・ハザード4つ）と **MUST 7つ**（price_max・land_area_min・walk_minutes_max・
commute_minutes_max・flood_rank_max・landslide_special_ratio_max・features）。

⚠ **レジストリの対応表はリテラルで丸ごと固定する**（`tests/test_metrics.py` のスナップショット）。
右辺に `m.ALL_PROPERTY_TYPES` を使ったテストは、定数の中身が変わると**左右が同時に変わって
検出できない**。実際に3箇所（`price == BUY_TYPES` ほか）がこの形だった。

⚠ `TochiBuyPattern` は discriminated union の4つ目のクラスにする。建物系の MUST は
`TochiBuyMust` に置かないので、YAML に書くと `extra="forbid"` で**読み込みの段で弾かれる**。

## 決定2: 土地の名寄せキーは「住所（丁目まで）＋土地面積」。版は v2 のまま

```text
sha256("v2|TOCHI_BUY|{正規化住所}|{土地面積（小数第2位）}")
```

- ⚠ **`DEDUP_KEY_VERSION` は上げない。** 土地のキーは `v2|TOCHI_BUY|…` という
  新しい名前空間なので既存のキーと交わらない。上げると全掲載の `regroup` が要る
- ファミリをハッシュに混ぜるので、**同じ住所・同じ土地面積の中古戸建てとは別キー**になる
  （古家付きの土地と中古戸建てを同一視しない）
- ⚠⚠ **知らないファミリは例外にする**（住所の有無より先に判定する）。
  旧実装は `KODATE_BUY` 以外を `else` で「間取り＋専有面積＋階」として扱っており、
  土地は間取りが無いので**キーが常に None になり、例外も出ずに名寄せされない**形だった

⚠ **既知の限界**: 分譲地の同一丁目・同一面積の隣接区画は1グループに潰れる。
賃貸で「同一仕様の別住戸は潰す」とした判断（→ 課題#13）と同型として扱う。

## 決定3: 設備条件（`features`）は全種別に置き、辞書に無い条件コードは validate-config が弾く

MUST の `features` は「詳細取得済みで抽出結果に無ければ fail」で判定する。
土地の設備抽出辞書はまだ無いので、土地パターンに1つでも書くと
**詳細取得済みの掲載が全件 fail になる**。WANT に書けば全件 miss で分母にだけ乗る。

- `features` を `MustBase` から降ろす案（間取りと同じ扱い）は採らない。MUST 側は構造的に
  塞がるが、**WANT 側の穴が残る**うえ、既存ファミリの取り違えは拾えない
- 代わりに `validate-config` が、WANT（`any_of` も展開）と MUST の条件コードを
  **そのファミリの辞書＋導出コード（`DERIVED_CODES`）**と突き合わせ、無ければ NG にする
  （`extract/pattern_check.py`）。全ファミリに効く
- ⚠ 照合先は**パターンのファミリの辞書**にする（賃貸の辞書と売買のパターンを突き合わせると、
  抽出できている売買固有の条件が偽陽性で落ちる → 課題#4）
- ⚠ 導出コードは `extract/extractor.py` の公開定数にし、導出関数の出力と突き合わせて固定する
  （導出を足して定数を直し忘れると validate-config が偽陽性を出す）
- `tests/test_dictionary_coverage.py` も同じ関数を通し、対象を**雛形 YAML と MUST** まで広げた
  （検証の側が実装と別の規則を持つと、正しい実装を誤診する → 課題#46）

## あわせて直したこと

⚠ **`validate-config --configs-dir <別ディレクトリ>` が、稼働中の全パターンを「孤児」と判定して
DELETE 文まで案内していた。** 孤児スコアの確認が「渡されたディレクトリのパターン名」を基準に
動くため。計画書が勧める「雛形だけを置いた一時ディレクトリで検証する」手順で実際に出た
（従うと約5.7万行の採点が消える）。実運用の configs を検証したときだけ確認するようにした。

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 土地を `KODATE_BUY` に含める | 建物面積・間取り・築年数が必須の MUST・metric・名寄せキーと衝突する。例外にならず全件 unknown / None になる |
| `BUY_TYPES` に TOCHI を入れて、建物系の項目を個別に外す | 外し忘れた項目が黙って土地に開く。追加する側を明示するほうが、忘れたときの結果が「使えない」（目に見える）で済む |
| 9a〜9e を1つの PR で入れる | アダプタは実サイトの実測なしに書けない（ADR 0015）。ハッシュや順位が動いたときの原因が2系統になる |
