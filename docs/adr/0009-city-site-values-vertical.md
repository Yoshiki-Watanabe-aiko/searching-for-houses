# 市区町村×サイトの検索値を縦持ちにする（ADR 0001 の撤回）

**状態: 採用（2026-09-01・Phase 0 で実施）**
**関連: [ADR 0001](./0001-city-site-mappings-wide-table.md) を撤回する**

「市区町村ごとのサイト別検索値」を、サイトごとに列を固定するワイドテーブル
（`city_site_mappings.suumo` / `.homes` / ...）から、
`m_city_site_values(city_id, site_id, value)` の縦持ちへ転換する。

## 背景・検討した選択肢

ADR 0001 は「**対応サイト数は10で固定**されており、新サイト追加の頻度は低い」ことを
前提にワイドテーブルを選んだ。この前提が崩れた。

- v2 で賃貸EX（`CHINTAI_EX`）を11サイト目として追加することが決まった
- サイト追加のたびに `ALTER TABLE ... ADD COLUMN` が要る。しかも DB規約は
  監査カラム（`created_at`/`updated_at`）を最終列に保つことを求めるため、
  **列追加はテーブル再作成（退避 → 新テーブル作成 → 再投入 → drop → rename → 制約再設定）を伴う**。
  「1サイト増やすだけ」の変更としてはコストが釣り合わない

ADR 0001 が挙げていたワイドテーブルの利点は、いずれも v2 では成立しないか代替がある。

| ADR 0001 の論拠 | v2 での評価 |
|---|---|
| サイト追加は scraper パッケージ新設を伴うのでDBだけ動的にしても意味がない | v2 のサイト別コードは「取得と解析」だけになり（→ ADR 0003）、追加コストが下がった |
| 「非対応」を NULL で表せてフォールバック判定が素直に書ける | 縦持ちでは**行の欠如**がそのまま「未登録 → 都道府県フォールバック」を意味する。`LEFT JOIN` で同じく素直に書ける |
| 1都市×10サイトを `SELECT *` 一発で取れる | 実際の使い方は「あるサイトの、ある市区の値」の単発参照が主。主キー `(city_id, site_id)` で引ける |

## Consequences

- **以後のサイト追加は行の挿入だけで済む。** DDL変更もテーブル再作成も不要
- 列名（`suumo` 等）と `site_master.code` を手で一致させる運用（ADR 0001 の懸念）が
  FK 制約に置き換わり、機械的に保証される
- 1都市の全サイト値を横に並べたい場合は PIVOT か `GROUP BY` が要る。
  現状そのクエリは使っていないため実害はない
- 移送時に実データを確認したところ、v1 の `docs/requirements.md` が記載していた
  値のフォーマットに誤りがあった（EHEYA・SMOCCA はスラグではなくJIS5桁コード、
  MINIMINI はJISコードではなくスラグ）。正しい対応は要件定義書 §11.2 に記載した
