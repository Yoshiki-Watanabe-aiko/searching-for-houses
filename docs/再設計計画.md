## 1. 再設計の動機

ユーザー要望は「**優先度の高い条件順にランク付けし、その順にソートして家を探したい**」。現行システムにランク付けの概念はなく、条件モデルそのものの作り直しが必要になる。

### 1.1 現行システムの構造的問題

| 問題 | 内容 |
|---|---|
| ランク付け不能 | 全条件AND絞り込み型で、優先度・重みの概念がない |
| 条件対応の不均一 | 10サイト中6サイト（HOMES/GOO/APAMAN/MINIMINI/EHEYA/SMOCCA）が設備条件をURLに反映できない |
| 条件が黙って無視される | 上記6サイトでは条件が素通りし全件通知される。ローカル判定は現行コードに存在しない |
| 課題#1〜#3の温床 | いずれも「サイト側の検索フォームで絞る」方針に起因 |

### 1.2 調査で判明した既存ドキュメントの誤り（本計画で訂正する）

| 箇所 | 誤りの内容 | 実測による事実 |
|---|---|---|

## 2. 確定した方針

| 論点 | 決定 |
|---|---|
| 実装言語 | **Python**（Playwright / httpx＋lxml / SQLAlchemy 2.x＋psycopg / Alembic / pydantic / uv） |
| DB・通知 | PostgreSQL・Discord Webhook を継続 |

## 3. アーキテクチャの転換

### 3.1 「サイト側で絞る」→「サイト側は粗く取り、判定・採点はローカル」

**この転換はランキング導入と論理的に不可分**である。WANT条件（オートロック無しでも減点で残ってほしい）をサイト側フィルタに渡すと、対応サイトでは物件が除外されて順位に現れず、非対応サイトでは素通りする。ランキングを入れる以上、設備条件のURL反映は全サイトで使ってはならない。

**サイトに渡すのは「エリア＋物件種別＋価格上限（バッファ付き）」の3つだけ。**

| 観点 | 旧方針 | 新方針 |
|---|---|---|
| 条件対応の均一性 | サイトごとにバラバラ（課題#1〜#3） | 全サイト同一の判定器 |
| 保守性 | 10サイト×条件マッピングの維持 | サイト別コードは「取得と解析」だけ |
| 取得件数 | 少ない | 増える（2段判定で緩和） |
| WANT条件との整合 | 不可能 | 自然に実現 |

副産物として課題#1（ABLE/SMOCCAの市区必須）は市区自動展開で解消、課題#2・#3は「対応不要」としてクローズできる。

### 3.2 2段判定によるコスト緩和

1. 賃料・間取り・面積・築年・徒歩は全サイトの**一覧ページに載っている**。ここでMUST判定し、`fail` の物件は詳細ページを取得しない
2. 既知物件（`external_id` 一致）は詳細を再取得しない
3. 市区町村指定で母集団自体を縮小できる

### 3.3 MUST判定の3値化

MUST判定は `pass` / `fail` / `unknown` の3値とし、**詳細取得をスキップするのは `fail` のみ**。

売買では管理費・修繕積立金・権利形態が一覧に出ず、詳細を見ないと判定できない。この問題は賃貸の敷金礼金でも潜在しているため、**Phase 1 から3値で実装する**。

## 4. スコアリングモデル

### 4.1 YAMLスキーマ v2

```yaml
name: "東京賃貸一人暮らし"
property_type: "CHINTAI"
webhook_ref: "CHINTAI_ALONE"       # .env の DISCORD_WEBHOOK_CHINTAI_ALONE を参照
sites: [SUUMO, HOMES, ATHOME, GOO, ABLE, MINIMINI, EHEYA, NIFTY, APAMAN, SMOCCA, CHINTAI_EX]

search:                             # サイト側へ渡す唯一の条件
  prefectures: ["東京都", "千葉県", "埼玉県", "神奈川県"]
  cities: []                        # 空ならABLE/SMOCCAは都道府県内全市区へ自動展開
  rent_max_hint: 90000              # MUST上限の2〜3割増し（管理費別サイト対策のバッファ）

must:                               # 未充足なら除外
  rent_total_max: 70000
  layouts: ["1LDK", "2K", "2DK", "2LDK", "3LDK"]
  area_min: 30.0
  walk_minutes_max: 20
  features: []
  unknown_policy: keep              # 判定不能なMUSTを keep=通す / drop=除外

want:
  features:                         # 該当なら weight 満点を加点
    - { code: INT_LAUNDRY,   weight: 10 }
    - { code: BATH_SEPARATE, weight: 9 }
    - { code: SEC_AUTOLOCK,  weight: 8 }
  numeric:                          # 線形正規化
    - { metric: rent_total, weight: 10, best: 50000, worst: 70000 }
    - { metric: area_sqm,   weight: 6,  best: 45,    worst: 30 }
    - { metric: age_years,  weight: 4,  best: 0,     worst: 30 }

ranking:
  top_n: 15
  digest_group: null                # 同一グループのパターンをダイジェストに並記（スコアは混ぜない）
```

### 4.2 スコア計算

- 正規化: `s = clamp((worst - x) / (worst - best), 0, 1)`（方向は metric ごとに定義）
- 合計: `score = 100 × Σ(wᵢ × sᵢ) / Σ(wᵢ)` の0〜100点
- 単位の異なる条件は `s` で無次元化されるため、weight だけで相対優先度を表現できる
- **欠損metricは分子・分母の双方から除外して再正規化**し、内訳に `"missing": true` を記録（新築マンションの価格未定を0点扱いにすると不当に沈むため）
- WANTの判定不能は0点＋「未確認」表示。中間値補完はしない
- **決定性**: 条件コード順にソートしてから加算（`PYTHONHASHSEED` を変えたサブプロセス間比較でテスト）

### 4.3 説明可能性

`t_property_scores.score_breakdown`（JSONB）に全項目の `{code, name, weight, s, points, status: hit|miss|unknown}` を保存。

- 即時通知: スコア・パターン内順位・得点上位3項目・未確認項目数
- ダイジェスト: 順位・スコア・価格・間取り/面積・市区・URL（Discord embed制約 description 4096字/1embed、6000字/1メッセージ、10embed/1メッセージ）

### 4.4 再スコアリング

スコアは「DB保存済みの物件属性＋抽出済みfeatures」からの純関数のため、**再計算はネットワーク不要のDBバッチ**。YAMLのスコア関連部分のハッシュを `config_hash` として保存し、不一致なら自動再スコア。CLI `rescore` も用意する。

### 4.5 種別ごとのmetric体系

物件種別は実質**3ファミリ**（賃貸／マンション売買／戸建て売買）に分かれる。

| metric | 方向 | 賃貸 | 新築M | 中古M | 新築K | 中古K |
|---|---|:---:|:---:|:---:|:---:|:---:|
| `rent_total` | 低いほど良 | ○ | - | - | - | - |
| `price` | 低いほど良 | - | ○ | ○ | ○ | ○ |
| `monthly_cost`（管理費+修繕積立金） | 低いほど良 | - | △ | ○ | - | - |
| `area_sqm`（専有面積） | 高いほど良 | ○ | ○ | ○ | - | - |
| `building_area_sqm` | 高いほど良 | - | - | - | ○ | ○ |
| `land_area_sqm` | 高いほど良 | - | - | - | ○ | ○ |
| `age_years` | 低いほど良 | ○ | - | ○ | - | ○ |
| `walk_minutes` | 低いほど良 | ○ | ○ | ○ | ○ | ○ |

- **戸建てに `area_sqm` を流用しない**。専有面積が存在せず土地面積・建物面積の2軸になるため、混線と名寄せ事故を避けて別metricにする
- **坪単価・㎡単価は metric にしない**。price と area に既に weight を配れる以上、二重に重みが掛かり解釈が濁る。`price_per_sqm` は表示用の派生カラムとしてのみ保持

### 4.6 スキーマ表現（pydantic）

**discriminated union を3ファミリ粒度で採用**する。`property_type` を discriminator に `ChintaiPattern` / `MansionBuyPattern` / `KodateBuyPattern` へ分岐し、共通部（name / search / webhook_ref / want.features）は基底モデルに置く。

metric・MUST項目は **MetricRegistry**（metric名 → 適用種別集合・抽出元カラム・単位・方向）で一元管理し、`model_validator` がレジストリを引いて検証する。種別追加はレジストリ1行で済む。

5種別を5クラスに割らない理由: 新築/中古の差は `age_years`・価格未定・リノベ関連の数項目だけで、クラスを分けるほどの構造差がない。

## 5. 設備情報のローカル抽出

### 5.1 パイプライン

1. **原文保存**: 詳細ページの設備ブロックを**テキストのまま** `t_properties.raw_features_text` に保存（詳細HTML全体は保存しない）
2. **辞書マッチング**: NFKC正規化→小文字化→トークン化→辞書照合→`t_property_features` 生成

**原文保存が要**。辞書を改善したら再スクレイピングせずDB内の原文から全件再抽出できる（`re-extract`）。これがないと辞書運用が回らない。

### 5.2 辞書の持ち方

**Git管理YAML（正）→ DB同期** を採用。`data/feature_dictionary.yaml` を `sync-dict` コマンドで `m_condition_synonyms` へupsertする。

```yaml
SEC_AUTOLOCK:
  patterns: ["オートロック", "オートロック付"]
  negative_patterns: ["オートロックなし"]
  site_overrides:
    SUUMO: ["オートロック"]
```

Git履歴でdiffレビューでき、実行時はDB参照でJOINできる。**賃貸ブロックと売買ブロックの2部構成**にする（証明書・性能評価系の語彙は賃貸と別体系のため）。

### 5.3 未知表記の運用ループ

どのパターンにもマッチしなかったトークンを `t_unknown_tokens`（token・site・出現回数・例示URL）へ記録。`report-unknown` で出現回数順に一覧し、辞書YAMLへ追記→`sync-dict`→`re-extract` で反映する。

## 6. クロスサイト名寄せ

ランキング上位が同一物件のサイト違いで埋まるため、**将来課題ではなく本体要件**とする。

- **キー**: 正規化住所＋間取り＋面積＋階数 の SHA256（`dedup_key`）
- **完全一致のみ自動グループ化**。曖昧一致は候補フラグ止まり（名寄せの誤爆はランキングから物件を1件消すことを意味し、偽陽性のコストが高い）
- **建物名はキーに含めない**（賃貸では非公開・伏字が多く偽陰性の主因）
- **種別ファミリで構成要素を変える**:
  - 賃貸/マンション: 住所＋間取り＋専有面積＋階数
  - 戸建て: 住所＋土地面積＋建物面積＋間取り（階数・部屋番号の概念がない）
  - ハッシュ入力に**ファミリ識別子を混ぜる**（分譲賃貸が「賃貸」と「中古売買」で二重グループ化されるのを防ぐ）
- **代表選定**: 月額/価格が最安 → 設備抽出数が最多 → サイト優先順
- **スコアはグループ内の抽出情報の和集合**で計算（サイトAで判明した設備＋サイトBで判明した設備をマージ）
- **通知**: グループ単位で重複抑制。代表より安い掲載が出たら「他サイトで安値掲載」として通知

### 7.2 `t_properties` の売買対応

**ハイブリッド方式**（metric/MUSTの入力になる数値は型付き列、正規化未確立の文字列系はJSONB）を採用。全部JSONBにするとスコアリングエンジンが型保証のない値を読むことになりMUST判定の信頼性が下がる。全部列にすると接道「南6m公道」のような表記揺れの激しい項目でスキーマ変更が頻発する。

追加列（**Phase 0 のDDL初版に含める**。後からの列追加はテーブル再作成になるため）:

| 列 | 用途 |
|---|---|
| `land_area_sqm` NUMERIC | 土地面積㎡（戸建て。metric入力） |
| `building_area_sqm` NUMERIC | 建物面積㎡（戸建て。metric入力） |
| `mgmt_fee_monthly` BIGINT | 管理費 円/月（マンション売買） |
| `repair_reserve_monthly` BIGINT | 修繕積立金 円/月（マンション売買） |
| `price_min` / `price_max` BIGINT | 価格レンジ（新築対応） |
| `price_per_sqm` NUMERIC | ㎡単価（マンションのみ。表示用派生値） |
| `raw_features_text` TEXT | 設備ブロック原文 |
| `dedup_key` / `group_id` | 名寄せ |
| `detail_fetched_at` | 詳細取得済み判定 |
| `type_specific_attrs` JSONB | 接道・建ぺい率/容積率・権利形態・引渡時期・建築条件付きフラグ等 |

### 7.3 新築物件の掲載粒度

賃貸・中古が「1物件=1住戸」なのに対し、**新築マンション・新築分譲戸建ては「1物件=1棟/1プロジェクト」で価格がレンジ表示**（「3,500万円台〜」「価格未定」）される。

- 新築系は棟/プロジェクト単位で1レコード。`price` にレンジ下限、`price_min`/`price_max` にレンジ
- 価格未定は `price NULL` ＋ `type_specific_attrs.price_undecided = true`
- スコアはレンジ下限で計算し内訳に `"range": true` を記録。価格未定は price metric 欠損として再正規化
- 通知は棟単位（「新価格帯検出」）。住戸タイプ別の追跡はしない

### 7.4 旧データの扱い

**移行せず、シードモードで副作用を消す。**

通知履歴を捨てると再掲載が全部「新着」として再通知される問題は、**初回全件取得を通知なしの記録専用モード（`--seed`）で走らせる**ことで構造的に発生しなくなる。パターン新規追加時・長期停止からの再開時にも使える汎用機能とする。

旧DBは pg_dump でアーカイブ済み（`F:\backups\searching-for-houses-legacy\db_20260901.dump`、11テーブル・2.5MB）。

### 7.5 テストDB分離（課題#7）

`searching_for_houses_test` を作成し `.env` に `DATABASE_TEST_URL` を追加。統合テストは未設定時スキップ。DB・ロール作成は `~/.claude/.env` の管理者パスワードを読む冪等スクリプトで行う。

## 8. 通知設計

| 系統 | トリガー | 形式 |
|---|---|---|
| 新着 | DB未登録の物件を検出（グループ単位で重複抑制） | 個別Embed。スコア・順位・得点上位3項目 |
| 価格変動 | 前回価格と差分 | 個別Embed |
| ランキングダイジェスト | 日次 | 1メッセージにスコア上位N件 |
| エラー | サイト失敗・YAML読込失敗 | `.env` の `DISCORD_WEBHOOK_ERRORS` |

**種別横断ランキングは作らない。** 価格帯も面積の意味も違う種別のスコアは正規化基準が異なり、混ぜると数字が意味を失う。「中古マンションと中古戸建てを並べて見たい」ニーズには `digest_group` によるダイジェストの**セクション並記**で応える（スコアは混ぜずパターンごとに上位Nを並べる）。実装差分は通知フォーマッタのみ。

## 9. 実行・運用

### 9.1 初回全件取得

規模: MUST事前判定通過が2〜3万件、サイト内直列2.5秒間隔・サイト間並列で**3〜8時間**の見込み。

- **エージェントのバックグラウンドから起動しない**（パイプ詰まりで例外なく停止する）。`scripts/run_initial_scan.ps1` を用意し `Start-Process` で切り離し、**stdout/stderrを別ファイル**へ落とす
- 進捗は `t_scrape_runs` とログファイルで観測。**停止判断をCPU使用率でしない**
- 日本語コメント入り `.ps1` は BOM付きUTF-8 で保存

### 9.2 中断・再開

`t_scrape_runs` に `(run_id, mode, pattern, site, phase, cursor, status)` を記録。詳細取得は `detail_fetched_at IS NULL` のキュー型なので**再開はSQLの自然な帰結**になる。upsertは全て冪等。

### 9.3 レート制御

サイトごとに `min_interval_sec`（既定2.5秒＋±30%ジッタ）・`max_pages_per_run`・`daily_request_cap`。429/5xxは指数バックオフ、連続失敗でサイト打ち切り＋エラー通知。robots.txt は起動時取得しDisallowならスキップ。

### 9.4 タスクスケジューラ

- タスク用スクリプトは `-Wait` で子として待たせる（`Start-Process` 切り離し版の流用禁止。タスクが即完了扱いになり二重起動する）
- 登録は `Register-ScheduledTask` でなく **XMLをUTF-16で書き出して `schtasks /create /XML`**
- 構成: ①毎時 増分スキャン ②毎日9:00 成約確認 ③毎日20:00 ダイジェスト ④毎日3:30 pg_dump（課題#8解消）
- すべて `.venv\Scripts\python.exe` をフルパス起動

### 15.1 Phase 1 で採用した設計上の追加判断

| 判断 | 理由 |
|---|---|
| `want.features` に **`any_of`（排他グループ）** を追加 | RC と SRC に別々の weight を振ると片方は必ず miss になるのに分母には両方が乗り、全物件のスコア上限が構造的に下がる。順位は壊れないが 0〜100点という数字の意味が濁る |
| `FEAT_WITH_PHOTO` / `FEAT_WITH_LAYOUT` を WANT から除外 | 掲載の充実度であって物件の質ではない。加点すると写真の無い優良物件が平凡だが写真付きの物件の下に沈む |
| 閾値条件を型付き列から導出（`source='DERIVED'`） | 「2階以上」は文字列照合で表現できない。辞書に頼ると weight 5 が常に miss になり無駄になる |
| 辞書照合を**本文全体への部分一致**にした | 区切り文字がサイトごとに違い、中黒で切ると「バス・トイレ別」を取りこぼす |
| 雛形YAMLを `configs/examples/` へ退避 | `configs/` 直下にあると実パターンとして走り、同じWebhookへ二重通知される（実際に発生した） |

#### 着手前の実測で確定させた設計（→ ADR 0012）

再設計計画 §6 は「正規化住所＋間取り＋面積＋階数」と定めていたが、
**住所の粒度と面積の丸め幅が未確定**だった。実データ301掲載で測って決めた。

| 論点 | 決定 | 実測の根拠 |
|---|---|---|
| 住所の粒度 | **丁目まで切り詰め** | HOME'S は番地・SUUMO は丁目すら出さない。切り詰めないと原理的に一致しない |
| 面積 | **丸めない**（小数第2位） | クロスサイト一致5件は全て小数第2位まで一致。丸めても一致は増えず、隣接住戸を余分に潰すだけ |
| 築年月・総階数 | **キーに入れない** | 入れると真の一致2件が分断され 5→4 に減る |

### 16.10 Phase 5B サイト側MUST（2026-09-03・基盤とSUUMOのみ完了）

#### ADR 0003 は撤回せず「補強」した

ADR 0003（サイト側フィルタ全廃）の論拠は **WANT についての議論**だった。
WANT は「満たさなくても対象から外れない」条件なので、サイト側で落とすと定義が壊れる。

**MUST は違う。** MUST を満たさない掲載はローカルでも `fail` になり
DBにも入らず採点もされない。サイト側で落としても結果は1件も変わらず、
変わるのは取得量だけである。この一点が本Phaseの全体を支えている。

⚠ **設備条件（`must.features`）だけは永久に送らない。** 辞書抽出とサイトのタグ付けは
判定が食い違い、こちらが `unknown` として残したい掲載をサイトが落としてしまう。

#### 実測でキーと選択肢を確定させた（推測で書かない）

資料 `資料_サイト別検索条件一覧.md` には SUUMO 賃貸の**フォームの選択肢**は
載っているが、**URLのクエリキーは載っていない**。推測で書くと課題#29 を再発させるので、
実サイトで測って確定させた（足立区 `sc=13121`・基準 62,030件）。

⚠ **測り方に一手間かけた。** 先に存在しないキー `zzz=1` を送って件数が
62,030件のまま変わらないことを確かめ、「**件数が動く＝キーが認識されている**」と
言えるようにしてから測った。これが無いと「効いていないのに効いたつもり」になる。

| `mb` / `mt` | 専有面積 下限/上限 | 20〜100㎡・5刻み。`mb=30` で 31,861件 |

| psycopg3 は匿名複合型（タプル）の配列を渡せない | 同期の DELETE で `(code, code, axis)` の配列比較が `FeatureNotSupported` になる。文字列キーへ連結して比較する |

### 16.12 Phase 5D 通勤時間の実ダイヤ化（2026-09-03 完了）

**完了条件「上位15件の通勤時間が実ダイヤの値になる」を達成**
（全1,155駅を4時間48分で取得し、上位15件は帯1で13件・帯2で14件が実ダイヤ）。
591テスト緑。→ [ADR 0017](./adr/0017-navitime-real-timetable.md)・課題#34

#### ODPT を使わないと決めた

第0歩として ODPT（公共交通オープンデータセンター）のカバー範囲を実測し、
スパイク一式まで用意してあった。それでも使わない判断にした。

| 論点 | 実測・判断 |
|---|---|
| 登録 | 開発者登録とトークン発行に日数がかかり、**着手を待たせる** |
| カバー範囲 | 列車時刻表10社・駅時刻表のみ5社。**京成・北総・東葉高速・埼玉高速・東京モノレールは未参加** |
| 再配布 | 基本ライセンスが生データの再配布を制限し、原典を Git 管理下に置けない |

⚠ **穴が残るのが致命的だった。** 時刻表のある区間と無い区間が混ざると、
1つの経路の中で「実ダイヤの区間」と「回帰式の区間」を足すことになり、
どちらの精度でもない値が出る。**しかも結果を見てもどちらだったか分からない。**

NAVITIME の乗換案内は登録不要で、優等列車・直通・乗換待ちを織り込んだ結果を
そのまま返す。スパイク一式は将来の一括生成に備えて残した。

#### 設計を1つ変えた（区間の集積 → O-D の直接取得）

前セッションの設計は「列車の連続停車ペアを全部辺にしてダイクストラ」
（スキップ辺方式）だったが、**必要なのは1,154駅グループ → 目的地1つ**である。
O-D を直接引けば取得1,154回で厳密な答えが出る。

⚠ **乗換案内で隣接駅を引くと待ち時間が混ざる。** 2駅ぶんの検索結果は
「次の列車を待つ時間＋乗車時間」なので、区間を足し上げると大きく過大になる。
スキップ辺方式そのものは残っており、**O-D の経路明細から乗車区間を副産物として貯める**
（`t_rail_segments`）。目的地が変わったらこの辺で計算し直せば取得のやり直しが要らない。
